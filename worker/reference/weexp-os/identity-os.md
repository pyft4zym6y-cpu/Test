# identity-os · eCom OS / weexp

**Уровень:** УР0 · **Полнота (на момент сборки плагина):** 65/100 · внедрён внешний материал: _competitive-intel (claude-skills)_

## 01 · Purpose
Определяет тип бизнеса, отрасль, масштаб, Commerce DNA. Задаёт, какие скилы включены, какие эталоны применимы, объём протоколов, с чего начинать.

**Чего скил не делает:** решения вне своей зоны ответственности передаёт соседнему скилу или synthesis-os. Не ведёт собственных нумераций реестров — читает и пополняет реестры ядра commerce-os.

## 02 · Objects
Владеет: Business Entity · Channel · Competitor
Владение объектом — ровно одно на объект. Второй владелец объекта = дефект архитектуры.

- Данные от data-os (жёсткая связь, если применимо)

## 04 · Methods
**Протокол определения типа бизнеса (L0, без клиента):** по сайту, реестрам, вакансиям и выдаче — производитель / дистрибьютор / реселлер / marketplace seller, D2C или опт, число рынков.

**Протокол построения поля Competitor (5-слойный, адаптация competitive-intel):**
1. **Идентификация.** Прямые конкуренты (тот же ICP, та же задача, сравнимая цена) → поисковый + товарный методы. Косвенные (тот же бюджет покупателя, другое решение) → метод «по потребности». Канальные (свой же товар у чужих) → канальный метод.
2. **Battlecard по каждому значимому конкуренту.** Поля: позиционирование, сильные/слабые стороны, типичные возражения против нас, типичный сценарий, где мы выигрываем/проигрываем.
3. **Win/Loss-срез** — если есть данные CRM/продаж: по каким причинам теряем/выигрываем сделки против конкретного конкурента.
4. **2×2 карта позиционирования** — оси задаются identity-os под тип бизнеса (обычно цена/сегмент или ассортимент/сервис).
5. **Мониторинг обновлений** — фиксируется в каталоге конкурентов с полем `checked_at`, пересмотр раз в квартал (не реже — список полугодовой давности вводит в заблуждение).

Результат уходит в `knowledge/registries/17-competitor-catalog.md` по схеме карточки (см. `docs/competitor-object.md`).

**Расширение поля Competitor (gtm-agents/competitive-intelligence, второй источник после competitive-intel):** `battlecard-library` — библиотека battlecard хранится централизованно, не по одному файлу на конкурента; `market-signal-tracker` — регулярный мониторинг публичных сигналов конкурента (не только цена/ассортимент — найм, партнёрства, PR); `win-loss-dataset` — структурированный сбор причин побед/поражений сделок, обязательное поле при закрытии сделки в CRM (интеграция с people-os/CRM).

**Протокол выбора рынка (раунд 5, источник: nexscope-ai/eCommerce-Skills cross-border-ecommerce, подтверждён независимо в noique/cross-border-ecommerce-skills, уровень доказательства E2):** закрывает разрыв, зафиксированный на прогоне сценария международной экспансии — «клиент просит выбрать рынок за него, методики не было».
1. **Сбор вводных.** Стадия бизнеса по обороту, текущие рынки продаж, целевые рынки экспансии — закрытым списком с вариантом «другое».
2. **Один уточняющий вопрос множественным выбором** вместо цепочки открытых — снижает число итераций с клиентом.
3. **Оценка по матрице.** Каждый целевой рынок получает 1–10 по восьми взвешенным измерениям: размер рынка, проникновение e-commerce, конкуренция, регуляторная сложность, логистическая инфраструктура, платёжная экосистема, культурная дистанция, защита интеллектуальной собственности. Взвешенная сумма даёт композитный балл и ранжирование.
4. **Проверка готовности.** Обязательное предусловие — домашний рынок уже прибылен по вкладу в маржу. Без этого экспансия не начинается независимо от балла рынка.
5. **Разбор топ-2–3 рынков**, сравнение пяти моделей фулфилмента (прямая отправка, 3PL, FBA/FBT/WFS, дропшип, консолидация) с реальной стоимостью и сроками.
6. **Дорожная карта по фазам** с KPI на каждый рынок.

Честная оговорка источника: налоговые ставки и платёжные предпочтения — региональные ориентиры, требуют проверки на актуальность перед использованием как финального документа.

## 05 · Evidence
Вес доказательства — по общей иерархии (см. `knowledge/base/04-crosscheck/evidence-hierarchy.md`).

## 06 · Standards
Эталон определения типа бизнеса — по 16 ролям цепочки (см. Objects). Эталон battlecard — 6 обязательных полей (позиционирование/сильные/слабые/возражения/сценарий/where-we-win). Источник метода: адаптация competitive-intel (внешний скилл, уровень доказательства 4 — отраслевая практика без нашей собственной проверки, требует прогона на проекте для перехода на уровень 2).

## 07 · Findings
Пишутся по единому контракту находки (см. `knowledge/registries/findings-contract.md`). Единица обмена с synthesis-os.

## 08 · Outputs
Артефакт `IDN-01 Competitor Field` (поле конкурентов), `IDN-02 Battlecard` (по одному на значимого конкурента), `IDN-03 Positioning Map` (2×2).

## 09 · Quality Gates
Определяется по мере заполнения Methods/Standards. Пример условия: AQC выше порога, все блоки эталона разобраны.

## 10 · Metrics
Срок проявления эффекта — обязательное поле, заполняется по мере прогонов.

## 11 · Maturity
5 уровней: нет процесса · чек-лист · стандарт · измеряется · данные.

## 12 · Dependencies

- **Исходящие:** commerce-os, все профильные скилы (конфигурация)

## Статус готовности
Скил считается черновиком, пока не пройдены все 5 условий: заполненность, исполнимость, связность, совместимость, проверенность (прогон на реальном проекте). Черновик не подключается к synthesis-os.
