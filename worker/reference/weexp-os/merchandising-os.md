# merchandising-os · eCom OS / weexp

**Уровень:** УР4 · **Полнота:** 42/100 · раунд 7: написаны четыре протокола и эталоны с источниками. Было 15/100

## 01 · Purpose
Отвечает на вопрос «в каком порядке и как показан товар», отдельно от вопроса «какой товар вообще есть». Владеет выдачей категории, фасетной навигацией, сортировками, коллекциями, рекомендательными блоками и внутренним поиском сайта.

**Чего скил не делает:** не решает, что вводить в ассортимент и по каким атрибутам он описан — это `product-os`; не проектирует внешний вид страницы и её конверсионные элементы — это `ux-os`; не занимается внешним поиском и посадочными под запросы — это `seo-os`. Граница с seo-os проходит по источнику трафика: фасет, попавший в индекс и получающий трафик из выдачи, — совместная зона, где merchandising владеет логикой, а seo — индексацией.

## 02 · Objects
Владеет: `Listing` (выдача категории, правила ранжирования, фасеты, сортировки, коллекции), `SearchQuery` (внутренний запрос, его обработка и результат).
Меняет у чужих: читает `Product` (наличие, атрибуты, маржа) у `product-os`, `Price` у `pricing-os`, поведенческие события у `data-os`. Не меняет ни один из них.

## 03 · Inputs
| вход | тип | что делаем, если входа нет |
|---|---|---|
| Конфигурация identity-os (тип × отрасль × масштаб) | жёсткий | не запускаемся: правила выдачи у производителя и реселлера разные |
| Атрибутная модель от product-os | жёсткий | фасеты строить не из чего — фиксируем как блокирующую находку в product-os, а не в своём домене |
| Логи внутреннего поиска | жёсткий для M2 | M2 не выполняется, статус выводов «оценочные», в КП помечаем как уточняемое после доступов |
| События просмотра и добавления в корзину от data-os | мягкий | ранжирование разбираем без персонализации, только детерминированные правила |
| Остатки и маржинальность | мягкий | правило «наличие → маржа → релевантность» проверяем частично |

## 04 · Methods

### M1 · Аудит фасетной навигации
1. Снять список категорий и для каждой — набор фасетов, их порядок и число значений внутри каждого.
2. Для каждой категории выписать атрибуты, по которым покупатель реально выбирает (из отзывов, вопросов в поддержку, запросов внутреннего поиска), и сверить с фактическим набором фасетов. Разрыв между «по чему выбирают» и «по чему можно отфильтровать» — основная находка модуля.
3. Проверить пять дефектов, каждый — отдельная находка: фасет с одним значением; фасет, ведущий в нулевой результат; группа значений длиннее экрана без сворачивания и поиска внутри; отсутствие счётчика количества товаров у значения; потеря выбранных фильтров при переходе на вторую страницу и назад.
4. Проверить поведение на мобильном отдельно: фасеты за кнопкой, применение выбора (сразу или по кнопке «Показать»), возможность снять фильтр не открывая панель заново.
5. Зафиксировать состояние As-Is по каждой категории и сопоставить с эталоном из блока 06. Разрыв — в находку.

**Граница передачи человеку:** решение о том, какие атрибуты категории считать выборочными, принимает человек вместе с категорийным менеджером клиента. Агент готовит кандидатов, не утверждает набор.

### M2 · Разбор внутреннего поиска
1. Выгрузить запросы за период не менее 90 дней с полями: запрос, число обращений, число результатов, доля выходов, доля конверсии.
2. Разделить на четыре корзины: нулевые результаты; результаты есть, но конверсия ниже средней по сайту; топ по частоте; запросы с указанием артикула или кода.
3. Нулевые результаты разобрать по причинам — товара нет вообще; товар есть, но назван иначе (синоним); опечатка; запрос на категорию, а не товар; запрос по свойству, не занесённому в атрибуты. Пятая причина уходит находкой в `product-os`, не решается здесь.
4. Топ-запросы проверить вручную: попадает ли ожидаемый товар в первые пять позиций. Отдельно — поиск по артикулу и по коду производителя: для реселлера и дистрибьютора это основной способ поиска, и его отказ стоит дороже всех остальных дефектов.
5. Проверить поддержку поиска внутри текущей категории. Сформировать словарь синонимов как артефакт, а не как рекомендацию.
6. Завести повторяемость: разбор нулевых результатов — ежемесячный отчёт с владельцем, а не разовая находка.

### M3 · Правила выдачи и сортировка по умолчанию
1. Определить фактическую сортировку по умолчанию в каждой категории и то, задана ли она осознанно.
2. Проверить порядок правил ранжирования: наличие → маржинальность → релевантность → персонализация. Товар без остатка на первой позиции — блокирующая находка.
3. Разобрать поведение «мёртвых» позиций: высокий трафик при отсутствии остатка. Правило: из индекса не убирать, CTA менять на подписку о поступлении, из выдачи опускать, но не скрывать.
4. Проверить, не конфликтует ли правило выдачи с ценовой дисциплиной канала: продвижение вверх позиций с высокой маржой при разной цене в каналах — развилка уровня собственника, выносится в `synthesis-os`, здесь не решается.
5. Зафиксировать правила как документ, а не как настройку в админке. Настройка без документа не переживает смену менеджера.

### M4 · Коллекции и рекомендательные блоки
1. Инвентаризовать все блоки рекомендаций на сайте: где стоят, чем наполняются, кто владеет правилом.
2. Для каждого определить назначение: допродажа, замена отсутствующего, навигация по ассортименту. Блок без назначения — находка.
3. Проверить наполнение вручную на пяти карточках разных категорий: аксессуар к товару, а не тот же товар другого цвета.
4. Коллекции (подборки) проверить на срок годности: сезонная подборка, не снятая после сезона, — типовой дефект.

## 05 · Evidence
Что считается доказательством в домене, по убыванию веса:
- **E4** — данные систем клиента: логи внутреннего поиска, конверсия по позициям выдачи, доля выходов с категории. Основной источник домена.
- **E3** — крупные независимые исследования юзабилити с раскрытой методикой и выборкой (см. блок 06). Применимость проверяется: чужой рынок и чужая категория.
- **E2** — материал `external/merchandising-os/`, статус кандидата.
- **E1** — практика площадок и наблюдение на конкурентах.
Confidence находки не может быть выше уровня доказательства, на которое она опирается.

## 06 · Standards

**Эталон фасетной навигации.** Источник: Baymard Institute, исследование product lists & filtering — крупномасштабное юзабилити-тестирование с раскрытой методикой (think-aloud, бенчмарк топовых сайтов США и Европы), уровень **E3**. Ключевой ориентир: доля сайтов с хорошим фильтрующим опытом мала, а типичный дефект — не малое число фасетов, а нерелевантный набор, отсутствие приоритизации и слишком длинные группы значений. Отсюда правило эталона: **качество набора важнее количества** — несколько релевантных категории фасетов сильнее длинного списка редко используемых.

**Эталон внутреннего поиска.** Источник: то же учреждение, отдельное исследование поиска с бенчмарком; уровень **E3**. Ориентиры эталона: поддержка поиска внутри текущей категории (по бенчмарку подавляющее большинство мобильных сайтов её не имеют — значит это дифференцирующий, а не гигиенический элемент); фасеты, относящиеся к запросу, а не общий набор категории; обработка артикула и кода производителя как отдельного типа запроса.

**Оговорка по применимости.** Оба источника построены на крупных сайтах США и ЕС. Для украинского рынка и для узких категорий ориентиры принимаются как заимствованные и помечаются соответственно, пока не перебиты собственным экспериментом (E5) или тремя сходящимися наблюдениями в наших проектах (E3 внутренний).

**Разрез по типам бизнеса.** Производитель — фасеты строятся от свойств производства и применения, ассортимент узкий, поиск по названию модели. Реселлер — фасеты от бренда и совместимости, поиск по артикулу и коду производителя обязателен. Дистрибьютор — поиск по коду и по накладной, фасет «наличие на складе» первым. Marketplace seller — правила выдачи не наши, домен активируется частично.

**Антипаттерны домена:** фасет с одним значением; сортировка по умолчанию «по новизне» в категории, где новизна не критерий выбора; рекомендательный блок, показывающий тот же товар в другом цвете; нулевые результаты без предложения альтернативы; словарь синонимов, живущий в голове одного человека.

## 09 · Quality Gates
Работа считается законченной, когда выполнено всё:
1. Разобраны все категории, дающие суммарно не менее 80% трафика каталога.
2. По каждой разобранной категории набор фасетов сопоставлен с эталоном и разрыв зафиксирован.
3. Нулевые результаты разобраны по пяти причинам, каждая причина имеет владельца-скил.
4. Правила выдачи существуют как документ, а не как описание настройки.
5. Для каждой находки указана категория и доля трафика — без этого приоритизация в synthesis-os невозможна.

## 10 · Metrics
| метрика | что показывает | срок проявления эффекта |
|---|---|---|
| доля сессий с применением фильтра | пользуются ли фасетами вообще | 2–4 недели после изменения |
| доля нулевых результатов от всех запросов поиска | качество словаря и атрибутов | 1 месяц |
| конверсия сессий с поиском против сессий без него | работает ли поиск как канал | 1–2 месяца |
| глубина просмотра категории | адекватность сортировки по умолчанию | 2–4 недели |
| доля выходов с категорийной страницы | релевантность выдачи | 1 месяц |
Определения и формулы — из `knowledge/registries/03-metrics-catalog.md`, а не заводятся здесь.

## 11 · Maturity
0 — нет процесса: фасеты как получилось при установке шаблона, логи поиска не смотрят.
1 — чек-лист: набор фасетов пересматривают руками при добавлении категории.
2 — стандарт: правила выдачи и набор фасетов описаны документом, есть словарь синонимов.
3 — измеряется: нулевые результаты разбираются регулярно, есть владелец и отчёт.
4 — данные: ранжирование опирается на поведение, изменения проверяются экспериментом.

## 12 · Dependencies
- **Жёсткие:** `product-os` (атрибутная модель — без неё фасеты не из чего строить), `identity-os` (конфигурация), `data-os` (логи поиска и поведение)
- **Мягкие:** `ux-os` (подача выдачи на странице), `pricing-os` (маржинальность как правило ранжирования), `seo-os` (индексация фасетов)
- **Циклические:** с `seo-os` — фасет одновременно инструмент выдачи и посадочная. Разрешается правилом: логика фасета — наша, решение об индексации — seo-os.
- **Без чего не запускается:** без атрибутной модели product-os и без конфигурации identity-os.

## 13 · Аудит-модуль
**Модуль 07 · Подача товара в каталоге.** Слой доступа: L0 для фасетов, сортировок и рекомендательных блоков (видно снаружи); L2 для внутреннего поиска (нужна выгрузка логов).
Чек-лист L0: набор фасетов в трёх крупнейших категориях; сортировка по умолчанию; поведение при нулевом результате поиска по трём тестовым запросам, включая опечатку и артикул; наличие товаров без остатка в первой строке выдачи; наполнение блока рекомендаций на трёх карточках.
Выход в отчёт: раздел «Подача товара», оценка 0–5 по каждому из пяти пунктов, находки по контракту.

## 14 · AI Layer
Кандидат в агенты: **Разбор нулевых результатов** — вход: выгрузка запросов; выход: классификация по пяти причинам с маршрутизацией находок по скилам; guardrail — не правит словарь синонимов сам, только предлагает; escalation — при доле нулевых выше порога сигнал о дефекте атрибутной модели в product-os, а не в своём домене.
Паспорт не заполнен: по правилу страницы 12 архитектуры агент заводится от написанного протокола. Протокол M2 написан в этом раунде — паспорт можно собирать следующим.

## Статус готовности
