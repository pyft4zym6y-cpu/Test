Архитектурная рекомендация

7.5 Data Layer Specification (Корпоративная спецификация Data Layer)
Назначение раздела
Data Layer Specification определяет единый стандарт формирования, структуры и использования Data Layer во всех цифровых продуктах организации.
Data Layer является промежуточным слоем между бизнес-логикой приложения и аналитическими платформами. Он обеспечивает независимость аналитики от реализации пользовательского интерфейса, стандартизирует передачу данных и снижает связанность между системами.
Все события, передаваемые в GTM, Server GTM или другие аналитические платформы, должны формироваться через Data Layer.

Цели Data Layer
Использование единой спецификации позволяет:
отделить бизнес-логику от аналитики;
унифицировать реализацию между проектами;
сократить объём изменений при внедрении новой аналитики;
обеспечить совместимость с Measurement Plan;
упростить тестирование;
уменьшить технический долг.

Основные принципы
Спецификация строится на следующих принципах:
единая структура событий;
неизменяемость обязательных параметров;
канонические имена событий;
отсутствие вычислений внутри GTM;
вся бизнес-логика реализуется до помещения данных в Data Layer;
одно бизнес-событие — одна запись в Data Layer.

Правила формирования событий
Каждое событие должно:
публиковаться только один раз для одного бизнес-действия;
иметь уникальный event_id;
содержать обязательные параметры;
соответствовать Global Event Schema;
проходить автоматическую валидацию перед публикацией.

Версионирование схемы
Поле schema_version обязательно.
Пример:
schema_version: "2.3"
Это позволяет одновременно поддерживать несколько версий аналитической схемы в период миграции.

Запрещённые практики
Не допускается:
вычисление стоимости заказа в GTM;
генерация transaction_id в GTM;
изменение данных после публикации события;
использование разных названий для одного параметра;
помещение персональных данных (PII) в Data Layer без отдельного правового основания и утверждённой политики обработки.

Автоматическая валидация
Перед публикацией каждое событие рекомендуется проверять автоматически.
Контролируются:
наличие обязательных полей;
корректность типов данных;
допустимые значения справочников;
соответствие версии схемы;
уникальность event_id;
наличие обязательных объектов.
При ошибке событие должно быть отклонено либо направлено в журнал ошибок в соответствии с принятой архитектурой.

Критерии приёмки
Data Layer Specification считается внедрённой, если:
Определена единая структура Data Layer.
Для всех объектов утверждены обязательные поля и типы данных.
Используются канонические имена событий и параметров.
Каждое событие содержит event_id и schema_version.
Реализована автоматическая валидация структуры.
Спецификация синхронизирована с Measurement Plan, Event Catalog и Data Dictionary.
Любые изменения структуры проходят через процесс Change Management.

Архитектурная рекомендация
Для проектов уровня Enterprise рекомендуется хранить спецификацию Data Layer в машиночитаемом формате (например, JSON Schema или OpenAPI-подобной модели) наряду с текстовой документацией. Это позволит автоматически проверять корректность реализации в процессе CI/CD, генерировать документацию, создавать тестовые сценарии и предотвращать публикацию событий, не соответствующих утверждённой схеме. Такой подход значительно снижает количество ошибок при развитии аналитической платформы и обеспечивает единый стандарт реализации для всех команд.

Отлично. После Data Layer Specification логично перейти к самому ожидаемому разделу для аналитиков и разработчиков — официальному справочнику событий GA4. Но в отличие от документации Google, он должен быть не справочным, а инженерным: объяснять не только что отправлять, но и зачем, когда, откуда, что сломается при ошибке и как проверить корректность.
Это как раз тот раздел, которого не хватает большинству методологий.

Архитектурная рекомендация
Для проектов уровня Enterprise SQL Cookbook рекомендуется хранить в системе контроля версий (например, Git) и сопровождать автоматическим тестированием. Каждый запрос должен иметь уникальный идентификатор, историю изменений, сведения об авторе и версию схемы данных, с которой он совместим. Дополнительно рекомендуется разделить библиотеку на Production SQL (утверждённые запросы, используемые в отчётности) и Analytical SQL (исследовательские и экспериментальные запросы). Это обеспечивает воспроизводимость расчётов, упрощает сопровождение и снижает риск использования неподтверждённых аналитических сценариев.
