AP-011
Использование локальных UTM-правил
Разные команды используют различные соглашения по именованию кампаний и каналов.
Последствия:
неконсистентная классификация трафика;
невозможность агрегировать отчётность;
ошибки в анализе ROAS.
Правильный подход:
единый корпоративный UTM Naming Convention с автоматической проверкой соответствия.

AP-012
Отсутствие Data Contracts
Изменения в DataLayer или API внедряются без формального согласования.
Последствия:
неожиданные поломки GTM, ETL и BI;
рост количества инцидентов после релизов;
высокий технический долг.
Правильный подход:
использовать версионируемые Data Contracts между владельцами источников и потребителями данных.

Engineering Note
Анти-паттерны — это концентрированный опыт неудачных внедрений. Их ценность заключается не в описании ошибок как таковых, а в предотвращении повторения уже известных сценариев. В зрелой организации каталог Anti-Patterns используется как обязательный справочник при проектировании, код-ревью, аналитическом QA и архитектурных обсуждениях. Это позволяет снижать количество инцидентов, уменьшать технический долг и поддерживать единые инженерные стандарты на протяжении всего жизненного цикла аналитической платформы.

Что я бы добавил следующим
Следующий логичный раздел — Enterprise Analytics Design Patterns.
Если Anti-Patterns отвечают на вопрос «как делать нельзя», то Design Patterns отвечают на вопрос «как строить правильно».
Именно связка Patterns + Anti-Patterns делает методологию практически законченной и превращает её в полноценный инженерный стандарт для e-commerce аналитики.

Engineering Note
Design Patterns — это библиотека проверенных инженерных решений. Они позволяют не изобретать архитектуру заново для каждого проекта, а использовать повторяемые, документированные подходы, доказавшие свою эффективность. Вместе с разделом Enterprise Analytics Anti-Patterns они формируют единый инженерный справочник: один показывает, каких решений следует избегать, другой — какие решения рекомендуется применять. Именно эта связка обеспечивает единообразие архитектуры, снижает технический долг и делает аналитическую платформу устойчивой к росту бизнеса, команды и технологического ландшафта.
Отлично.
На мой взгляд, мы уже вышли за рамки обычного Playbook. Сейчас не хватает последнего уровня — Operating Model.
Это то, что есть у Amazon, Booking, Spotify, Netflix.
Не “как настроить GA4”, а как должна работать аналитическая организация каждый день.
Именно этот раздел связывает людей, процессы, технологии и данные.

Enterprise Analytics Principles
Все решения должны соответствовать следующим принципам:
Data First — решения принимаются на основе проверенных данных.
Single Source of Truth — для каждой сущности существует один официальный источник.
Standard Before Custom — сначала используются корпоративные стандарты, затем исключения.
Automation Over Manual Work — автоматизация предпочтительнее ручных операций.
Quality by Design — качество данных закладывается на этапе проектирования.
Observability by Default — каждая критическая система должна быть наблюдаемой.
Documentation as Code — документация поддерживается как часть жизненного цикла продукта.
Business Value First — изменения оцениваются прежде всего по влиянию на бизнес.
