client_id
Назначение
client_id идентифицирует экземпляр браузера или приложения.
Он используется для:
анализа поведения;
построения пользовательских путей;
объединения событий одной сессии;
передачи данных в GA4.
Важно понимать:
client_id ≠ пользователь.
После очистки cookies или смены устройства значение изменится.

Требования
client_id:
создаётся автоматически;
не изменяется в течение срока жизни клиента;
не используется как постоянный идентификатор пользователя;
передаётся во все клиентские события.

session_id
Назначение
Используется для объединения событий одной пользовательской сессии.
Каждая новая сессия получает новый идентификатор.

Используется для:
расчёта поведения;
анализа последовательности событий;
построения воронок;
анализа отказов.

user_id
Назначение
Используется только после авторизации пользователя.
Главное преимущество:
один пользователь
↓
несколько устройств
↓
один user_id
Именно этот идентификатор позволяет строить Cross-device аналитику.

Требования
После авторизации:
все новые события получают user_id;
ранее собранные данные не переписываются;
объединение выполняется аналитической платформой.

transaction_id
Назначение
Идентифицирует коммерческую операцию.
Используется:

event_id
Назначение
Идентифицирует конкретное событие.
Используется исключительно для:
дедупликации;
Retry Logic;
трассировки обработки;
аудита.
Каждое событие получает новый event_id.

Правила изменения идентификаторов
Запрещается:
изменять уже выданный transaction_id;
генерировать новый event_id при Retry;
использовать один event_id для разных событий;
использовать client_id как постоянный идентификатор клиента;
использовать разные идентификаторы заказа в разных системах.

Контроль качества
Необходимо регулярно проверять:
совпадение transaction_id между CRM и аналитикой;
отсутствие повторного использования event_id;
корректную передачу user_id после авторизации;
корректное объединение событий разных устройств;
отсутствие «разрывов» в цепочке идентификаторов.

Для каждого типа сущности используется собственный идентификатор.
Все идентификаторы согласованы между клиентскими, серверными и корпоративными системами.
transaction_id остаётся неизменным на протяжении всего жизненного цикла заказа.
event_id уникален и сохраняется при повторной отправке.

Все правила управления идентификаторами задокументированы и утверждены.

Архитектурная рекомендация
Для проектов уровня Enterprise рекомендуется создать единый реестр идентификаторов (Identity Registry), который документирует назначение, владельца, источник формирования, правила хранения и срок жизни каждого идентификатора. Такой реестр должен использоваться всеми командами — разработкой, аналитикой, CRM, BI и интеграциями — как единый стандарт. Это предотвращает появление несовместимых идентификаторов, упрощает интеграцию новых систем и обеспечивает целостность данных на протяжении всего жизненного цикла клиента.

2.10 Очереди событий и Retry Logic (Event Queues & Retry Strategy)
Назначение раздела
Современная аналитическая платформа должна гарантировать доставку критически важных событий даже при временной недоступности отдельных компонентов инфраструктуры.
Сетевые ошибки, перегрузка API, временная недоступность внешних сервисов, обновления инфраструктуры и кратковременные сбои не должны приводить к потере аналитических данных.
Для обеспечения надёжности используется механизм очередей событий (Event Queue) и контролируемой повторной отправки (Retry Logic).
Основными задачами данного механизма являются:
предотвращение потери событий;
гарантированная доставка;
управление повторными попытками;
сохранение порядка обработки;
контроль отказов;
защита от появления дублей.

Принципы работы очередей
Каждое событие после успешной проверки помещается в очередь.
Очередь должна обеспечивать:
сохранность события;
сохранение порядка обработки (если это требуется бизнес-процессом);
возможность повторной обработки;
возможность масштабирования;
контроль времени жизни сообщения.

Каждый переход фиксируется в журнале обработки.

Retry Logic
Повторная отправка должна выполняться только для временных ошибок.
Типичный алгоритм:
первая попытка;
при временной ошибке — ожидание;
повторная попытка;
увеличение интервала;
достижение максимального числа попыток;
перенос события в Dead Letter Queue.
Интервалы и максимальное количество попыток определяются требованиями проекта.

Идемпотентность
Повторная обработка одного события не должна изменять итоговое состояние системы.
Основные правила:
сохраняется исходный event_id;
запрещено создавать новое событие при повторной отправке;
обработчик должен распознавать уже обработанные события;
успешная повторная доставка не должна приводить к повторной регистрации конверсии.
Идемпотентность является обязательным свойством серверной аналитической инфраструктуры.

Dead Letter Queue (DLQ)
Если событие не удалось доставить после всех предусмотренных попыток, оно переводится в специальную очередь ошибок.
DLQ используется для:
хранения необработанных событий;
расследования инцидентов;
повторной обработки после устранения причины;
анализа качества интеграций.
Удаление событий из DLQ без анализа причины не допускается.

Масштабирование
Очереди должны поддерживать горизонтальное масштабирование.
При росте нагрузки допускается:
увеличение числа обработчиков;
разделение очередей по типам событий;
выделение отдельных очередей для критически важных событий (purchase, refund);
независимая обработка различных направлений доставки (GA4, Meta, CRM, BI).
Это позволяет избежать ситуации, когда проблемы одной интеграции блокируют всю систему.

Критерии приёмки
Механизм очередей считается реализованным корректно, если:
Все критически важные события проходят через очередь.
Реализован механизм повторной отправки для временных ошибок.
Повторные отправки сохраняют исходный event_id.
Настроена Dead Letter Queue для необработанных событий.
Реализован мониторинг очередей и автоматические уведомления.
Обеспечена идемпотентность обработки.
Документированы правила повторной отправки, хранения и восстановления событий.

Архитектурная рекомендация
Для проектов уровня Enterprise очередь событий следует рассматривать как обязательный компонент аналитической платформы, а не как дополнительный механизм повышения надёжности. Все критически важные события (purchase, refund, payment_received, order_completed) должны обрабатываться через управляемый конвейер с поддержкой идемпотентности, повторной доставки и Dead Letter Queue. Такой подход обеспечивает устойчивость аналитики к сбоям инфраструктуры, позволяет безопасно масштабировать систему и гарантирует воспроизводимость обработки событий даже при временной недоступности отдельных сервисов.

Retry Logic
Повторная отправка должна выполняться только для временных ошибок.
Типичный алгоритм:
первая попытка;
при временной ошибке — ожидание;
повторная попытка;
увеличение интервала;
достижение максимального числа попыток;
перенос события в Dead Letter Queue.
Интервалы и максимальное количество попыток определяются требованиями проекта.

Идемпотентность
Повторная обработка одного события не должна изменять итоговое состояние системы.
Основные правила:
сохраняется исходный event_id;
запрещено создавать новое событие при повторной отправке;
обработчик должен распознавать уже обработанные события;
успешная повторная доставка не должна приводить к повторной регистрации конверсии.
Идемпотентность является обязательным свойством серверной аналитической инфраструктуры.

Dead Letter Queue (DLQ)
Если событие не удалось доставить после всех предусмотренных попыток, оно переводится в специальную очередь ошибок.
DLQ используется для:
хранения необработанных событий;
расследования инцидентов;
повторной обработки после устранения причины;
анализа качества интеграций.
Удаление событий из DLQ без анализа причины не допускается.

Масштабирование
Очереди должны поддерживать горизонтальное масштабирование.
При росте нагрузки допускается:
увеличение числа обработчиков;
разделение очередей по типам событий;
выделение отдельных очередей для критически важных событий (purchase, refund);
независимая обработка различных направлений доставки (GA4, Meta, CRM, BI).
Это позволяет избежать ситуации, когда проблемы одной интеграции блокируют всю систему.

Критерии приёмки
Механизм очередей считается реализованным корректно, если:
Все критически важные события проходят через очередь.
Реализован механизм повторной отправки для временных ошибок.
Повторные отправки сохраняют исходный event_id.
Настроена Dead Letter Queue для необработанных событий.
Реализован мониторинг очередей и автоматические уведомления.
Обеспечена идемпотентность обработки.
Документированы правила повторной отправки, хранения и восстановления событий.

Архитектурная рекомендация
Для проектов уровня Enterprise очередь событий следует рассматривать как обязательный компонент аналитической платформы, а не как дополнительный механизм повышения надёжности. Все критически важные события (purchase, refund, payment_received, order_completed) должны обрабатываться через управляемый конвейер с поддержкой идемпотентности, повторной доставки и Dead Letter Queue. Такой подход обеспечивает устойчивость аналитики к сбоям инфраструктуры, позволяет безопасно масштабировать систему и гарантирует воспроизводимость обработки событий даже при временной недоступности отдельных сервисов.

2.11 Мониторинг серверного трекинга (Monitoring & Observability)
Назначение раздела
Наличие корректно настроенного Server-side Tracking не гарантирует стабильную работу аналитической платформы. Любая распределённая система подвержена изменениям инфраструктуры, ошибкам интеграций, обновлениям API, изменениям клиентских приложений и человеческому фактору.
Поэтому серверный трекинг должен сопровождаться системой непрерывного мониторинга, которая позволяет:
контролировать доступность аналитической инфраструктуры;
отслеживать качество данных;
выявлять аномалии в режиме, близком к реальному времени;
обнаруживать потери событий;
контролировать производительность обработки;
своевременно уведомлять ответственных о возникновении инцидентов.
Мониторинг должен охватывать весь путь события — от момента его возникновения до появления в аналитических и BI-системах.

Алертинг
Система должна автоматически уведомлять ответственных при возникновении критических ситуаций.
Примеры триггеров:
резкое снижение количества событий;
увеличение числа ошибок валидации;
рост размера очередей;
накопление сообщений в Dead Letter Queue;
превышение допустимого времени обработки;
снижение успешности доставки.
Каждое уведомление должно содержать:
время возникновения;
компонент;
описание проблемы;
предполагаемое влияние;
ссылку на журнал событий или дашборд.

Обнаружение аномалий
Помимо статических порогов рекомендуется использовать анализ аномалий.
Примеры:
падение количества purchase на 40% относительно типичного значения;
двукратный рост refund;
исчезновение событий begin_checkout;
резкое увеличение числа дубликатов;
необычный рост времени обработки.
Аномалии позволяют выявлять проблемы, которые невозможно обнаружить простыми пороговыми значениями.
