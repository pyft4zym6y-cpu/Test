## Место в системе

Четвёртый и последний реестр. Три предыдущих отвечают на другие вопросы:

| Реестр | Что описывает | Когда |
| --- | --- | --- |
| `audit_deliverables.md` · AD-01…AD-16 | Документы аудита | До продажи |
| **этот файл** · KP / PR / FL | Документы сотрудничества | Продажа и ведение |
| `deliverables_registry.md` · D-01…D-62 | Результаты исполнения плейбуков | Внутри программы |
| `kp_master_structure.md` | Чертёж главного документа продажи (KP-01) | — |

**Ключевое различие PR и D.** D-коды — это содержательные результаты работы:
модель юнит-экономики, дерево категорий, retention-контур. PR-коды — управляющие
артефакты самой программы: устав, RACI, беклог, отчётность. Первые отвечают «что
построено», вторые — «как этим управляют». Путать нельзя: клиент, получивший
двадцать D-документов без PR-контура, не понимает, кто за что отвечает и когда всё
это закончится.

**Три двери — три пакета.** Форматы сотрудничества требуют разной обвязки:
Diagnostic Sprint закрывается пакетом AD, Program of Record — пакетами KP и PR,
Fractional Lead — пакетом FL. Пакеты не смешиваются: предлагать полный PR-контур на
фракционном сопровождении так же неверно, как вести программу трансформации без него.

## Пакет KP · Коммерческое предложение

Готовится сразу после аудита, опирается на его секции. Пять документов.

### KP-01 · Коммерческое предложение

| | |
| --- | --- |
| Формат | Deck / PDF |
| Источник | `kp_master_structure.md` — 20 секций |
| Питается | AD-01 секции 15, 16, 17; AD-15 |

Главный продающий документ. Логика: боль → цена боли → решение → доказательство →
как → сколько → выбор → управляемость.

**Готово, когда:** каждая цифра прослеживается до секции отчёта; итог кратно
превышает бюджет; рядом с основным сценарием стоит консервативный; в приложении есть
границы scope.

### KP-02 · Бюджет программы

| | |
| --- | --- |
| Формат | XLSX |
| Источник | `cost_base.md`, `deliverables_registry.md` |

Постатейный бюджет: работы отдельно от медиа-бюджета, капитальные затраты отдельно
от ретейнера, разбивка по волнам и этапам, график траншей.

**Готово, когда:** подтверждённые ставки из реальных КП отделены от рыночных вилок
пометкой; сумма по этапам сходится с итогом в KP-01; для каждой вилки указано, какое
значение взято и почему.

### KP-03 · Дорожная карта

| | |
| --- | --- |
| Формат | XLSX / Miro |
| Источник | AD-05, `routing.md` |

Три волны, этапы внутри волн, зависимости и Go/No-Go, сроки, D-коды результатов,
владелец у клиента по каждому этапу.

**Готово, когда:** блокирующие плейбуки стоят в первой волне; параллельно не более
4–5 плейбуков; каждый этап привязан к D-коду.

### KP-04 · Сценарии и чувствительность

| | |
| --- | --- |
| Формат | XLSX |
| Источник | `scripts/gap_calculator.py`, AD-04 |

Базовый, консервативный и сценарий «ничего не делать». Чувствительность результата к
каждому из восьми рычагов: что будет, если рычаг сработает наполовину.

**Готово, когда:** сценарий бездействия посчитан математикой, а не риторикой;
консервативный собран по нижней границе каждого рычага.

### KP-05 · Границы scope и SOW

| | |
| --- | --- |
| Формат | DOC |
| Источник | AD-05 лист «не вошло», `kp_master_structure.md` |

Что входит и что не входит, зона ответственности сторон, условия изменения scope,
что требуется от клиента, порядок приёмки.

**Готово, когда:** раздел «не входит» не пустой; названы обязательства клиента —
доступы, люди, скорость решений; описан порядок изменения объёма работ.

## Пакет PR · Program of Record

Управляющий контур программы. Одиннадцать документов, живут всё время исполнения.

| Код | Документ | Формат | Что внутри | Готов, когда |
| --- | --- | --- | --- | --- |
| PR-01 | Устав программы | DOC | Цели, границы, спонсор со стороны клиента, порядок эскалации, принципы принятия решений | Спонсор назван поимённо и подтвердил роль |
| PR-02 | RACI и матрица ролей | XLSX | Роли внутренней команды и подрядчиков, кто ответственный, кто утверждает, кого информируют | У каждой работы ровно один Accountable |
| PR-03 | KPI-дерево | XLSX | Метрика → владелец → частота съёма → источник данных → целевое значение | Каждая метрика имеет источник и владельца, а не только цель |
| PR-04 | График траншей под DoD | XLSX | Платёж привязан к принятому результату этапа, а не к календарю | Ни один транш не выплачивается без принятого DoD |
| PR-05 | Спринт-беклог и календарь | XLSX / трекер | Двухнедельные циклы, приоритезация, состав спринта | Беклог приоритизирован, а не отсортирован по доменам |
| PR-06 | Реестр deliverables программы | XLSX | Все D-коды в scope: статус, срок, исполнитель, ссылка на файл | Каждая строка ведёт на конкретный документ |
| PR-07 | Реестр рисков и допущений | XLSX | Риск, вероятность, влияние, владелец, меры, триггер срабатывания | Есть владелец у каждого риска и указан триггер, а не только «мониторим» |
| PR-08 | Регламенты и процессы | DOC, комплект | Процессы, внедрённые плейбуками: кто, что, когда, по какому правилу | Регламент написан для исполнителя, а не для отчёта |
| PR-09 | BI-дашборд и его спецификация | дашборд + DOC | Метрики, источники, формулы, права доступа, частота обновления | Цифры на дашборде сходятся с бэкендом; расхождение измерено |
| PR-10 | Acceptance-лог | XLSX | DoD-гейт по каждому этапу: критерий, дата, кто принял | Нет строк «принято условно» |
| PR-11 | Статусная отчётность | шаблон | Еженедельный статус и ежемесячный отчёт: план/факт, риски, решения | Отчёт содержит решения, а не только активности |

**Правило DoD-гейта.** Следующий этап не стартует, пока предыдущий не принят по
PR-10. Это не бюрократия, а защита бюджета клиента: без гейта программа накапливает
незавершённые работы и теряет измеримость.

## Пакет FL · Fractional Lead

Фракционное лидерство. Четыре документа, лёгкий контур вместо полного PR.

| Код | Документ | Формат | Что внутри | Готов, когда |
| --- | --- | --- | --- | --- |
| FL-01 | Ежемесячный отчёт | Deck / PDF | P&L, метрики против baseline, что сделано, что решено, что дальше | Отчёт читается собственником за 10 минут |
| FL-02 | Лог решений | XLSX | Решение, дата, на каких данных принято, ожидаемый эффект, фактический результат | Заполнена колонка фактического результата, а не только ожидаемого |
| FL-03 | Квартальный ревью план/факт | Deck | Сверка целей квартала с фактом, пересмотр приоритетов | Расхождения объяснены, а не сглажены |
| FL-04 | Оргструктура и план найма | XLSX / Miro | Целевая структура, роли, компетенции, последовательность найма, что закрывают подрядчики | Каждая роль имеет зону ответственности и метрику |

**Почему FL-02 важнее остальных.** Лог решений с колонкой фактического результата —
единственный документ, который делает работу фракционного лидера измеримой. Без него
сопровождение оценивается по присутствию, а не по эффекту.

## Сквозной документ

### XX-01 · Сверка прогноза с фактом

| | |
| --- | --- |
| Формат | XLSX |
| Слой | Месяцы 3, 6, 12 после старта |
| Источник | AD-04, AD-13, фактические данные |

По каждому рычагу: прогноз из экономики разрыва → факт на дату → отклонение →
объяснение отклонения.

**Зачем.** Весь метод построен на прогнозе недоотриманого оборота. Публичная сверка
прогноза с фактом превращает Commerce OS из продающего инструмента в проверяемый.
Это дороже для консультанта и сильнее любых оговорок о допущениях: клиент видит, что
цифры, которыми ему продавали программу, потом проверяются теми же руками.

**Обязателен для всех трёх пакетов.** Заявляется в KP-01 как обязательство, ведётся
в ходе программы, входит в FL-03 при фракционном сопровождении.

**Готов, когда:** отклонения показаны честно, включая отрицательные; для каждого
крупного расхождения назван механизм, а не «рынок изменился».
