# Commerce OS · Decision Engine

Слой принятия решений поверх диагностики: превращает «что мы узнали» в
«что делать первым и почему». Реализован в портале (`src/lib/engine.ts`,
`src/data/engine.ts`); этот документ — первоисточник подхода.

## 1. Движок решений

Решение — это правило вида:

```
IF   условия над ответами / рычагами baseline / замерами (PSI, скрининг) / болями
THEN решение { Impact 1–10 · Difficulty 1–10 · срок, дней · плейбуки · ROI }
WHY  список сработавших условий с фактическими значениями и кодами вопросов
```

Пример (DE-01):

```
IF  выручка из email < 10% (CR-001)
AND сегментации базы нет (CR-004 = «Нет»)
AND активная база > 1000 при повторных < 10%/мес (baseline)
THEN «Построить CRM-контур» · Impact 9 · Difficulty 3 · 30 дней · PB-08 · ROI High
```

**Ранжирование:** отношение Impact/Difficulty, при равенстве — Impact.
**Квадранты Cost-vs-Impact:** Impact ≥ 7 и Difficulty ≤ 4 → Quick win;
Impact ≥ 7 и Difficulty > 4 → Стратегическое; остальное → Поддерживающее.
**ROI-класс:** Impact/Difficulty ≥ 2.5 → High; ≥ 1.2 → Medium; иначе Long-term.

**Объяснимость (Explainable AI):** правило обязано отдавать трассу WHY —
каждое условие с фактическим значением и источником (код вопроса, рычаг,
замер). Рекомендация без трассы в выдачу не попадает. Это же правило
распространяется на любой будущий LLM-слой: вывод без цепочки
«вопросы → метрики → правило → доказательство» не показывается клиенту.

**Блокеры внутри решения:** если условие-пререквизит нарушено, решение
не скрывается, а несёт явный блокер («⚠ сначала PB-12, иначе маржа в ЕС
неизвестна») — консультант видит и решение, и порядок.

## 2. Confidence Score — доверие к выводам

Отчёт при 120 ответах и при 620 — разные документы. Confidence считается
из фактов о самих данных:

| Фактор | Вклад |
| --- | --- |
| Заполненность опросника | до +40 (пропорционально) |
| Выданные доступы и выгрузки | до +15 (насыщение на 12 позициях) |
| Baseline из данных систем (не «оценка клиента») | до +20 (по 8 рычагам) |
| Внешние замеры сделаны (PSI / скрининг) | +8 |
| Бриф ЛПР и рамки заполнены | +7 |
| Противоречия в ответах | −3 за каждое, до −15 |
| Проверено консультантом (финал) | +10 |

Шкала соотносится с методной шкалой уверенности 100/75/50/25 из
`working_core.md`. Показывается и консультанту (с разложением по факторам),
и клиенту (одной строкой с объяснением, как поднять).

## 3. Evidence Levels — достоверность каждого факта

| Уровень | Значение | Соответствие шкале метода |
| --- | --- | --- |
| E0 | догадка | 25 |
| E1 | со слов клиента | 50 |
| E2 | документ | 75 |
| E3 | данные системы (GA4, CRM, выгрузка) | 90 |
| E4 | подтверждено несколькими источниками | 100 |

Правила присвоения в портале: ответ в опроснике без фактов → E1; ответ с
приложенными фактами/файлом → E2; рычаг baseline с источником GA4 / CRM /
выгрузка / кабинет → E3; совпадение двух независимых источников → E4
(фиксирует консультант). CR «со слов» и CR «из GA4» — разные факты, и
интерфейс обязан показывать разницу.

## 4. Причинно-следственные цепочки

Формат: `Симптом → корневые причины (каждая с контрольными вопросами) →
бизнес-влияние → рычаг модели выручки`. Лечим причину, не симптом:
«мало повторных» может быть следствием CRM, ассортимента или опыта
доставки — и это три разных плейбука. Цепочка активируется болью клиента
и подтверждается (или нет) ответами на контрольные вопросы; неподтверждённые
корни уходят в вопросы к интервью, а не в отчёт.

Граф зависимостей метрик (`METRIC_DEPS`): SEO→Трафик, Скорость→CR,
CRM→Повторные→LTV→допустимый CAC и т.д. — используется для объяснения,
почему рычаг решения именно этот.

## 5. Зрелость процессов (Capability Maturity)

Модель L1 Хаос → L2 Повторяемо → L3 Определено → L4 Управляемо →
L5 Оптимизировано (из `maturity_health_score.md`) конкретизирована
лестницами по доменам: для CRM, аналитики, финансов, SEO, операций,
маркетинга, платформы и бренда описано, что означает каждый уровень
в терминах e-commerce. Портал выводит текущий уровень из health домена
(<20% → L1, <40% → L2, <60% → L3, <80% → L4, иначе L5) и показывает
описание следующего уровня — это и есть «куда расти» без абстракций.

## 6. Деньги решений

- **Цена бездействия по разрыву:** консервативный годовой потенциал
  распределяется по сработавшим критическим разрывам пропорционально их
  штрафам → каждый разрыв получает ≈ ₴/год. Показывается в карточках
  разрывов отчёта и в КП.
- **Прогноз 12 месяцев:** «без изменений ≈ текущий годовой оборот» против
  «с программой ≈ оборот + консервативный потенциал (+N%)». Всегда
  консервативный сценарий, всегда со сверкой XX-01.

## 7. Слой гипотез (Continuous Consulting)

Каждая рекомендация после старта программы — гипотеза:
`Гипотеза · Доказательство · Уверенность (25/50/75/100) · Способ проверки ·
Владелец · Дедлайн · Статус (открыта / подтверждена / отклонена)`.
Стартовый набор генерируется из топ-решений движка; проверка — А/Б или
до/после по метрике рычага; сверка на 3, 6 и 12 месяце (XX-01).

## 8. Learning Loop

Диагностика → План → Внедрение → Результат → Обновление модели →
Следующий аудит. Обновление модели — конкретные действия:

1. Подтверждённые/отклонённые гипотезы правят Impact/Difficulty правил
   движка (отклонённые дважды — правило пересматривается).
2. Расхождения «оценка L0 vs факт по данным» фиксируются — там внешний
   обход систематически ошибается.
3. Фактические эффекты плейбуков пополняют «Источники эталонов» в
   `gold_standards.md` — эталон получает собственный подтверждённый источник.
4. Подтверждённые ставки подрядчиков пополняют `cost_base.md`.

## 9. Зависимости плейбуков

`PB_PREREQS`: ERP (PB-18) — после карты интеграций (PB-16); Amazon EU
(PB-22) — после юнит-экономики (PB-12) и PIM (PB-17); лояльность (PB-09) —
после retention-контура (PB-08); ценовая архитектура (PB-13) и финмодель
(PB-53) — после PB-12; коммуникации (PB-47) — после бренд-платформы
(PB-46); дизайн-система (PB-52) — после визуальной системы (PB-51);
планирование закупок (PB-29) — после чистки ассортимента (PB-28).
Если пререквизит не в scope — движок требует добавить, а не молчит.

## 10. Экономика вопросов

У каждого вопроса фреймворка есть вес (1–5) и домен; вес × вес домена
из матрицы зрелости = вклад вопроса в Health Score, а принадлежность
домена связывает его с рычагом модели выручки через граф метрик. Цепочка
«вопрос → метрика → KPI → деньги» формализована на уровне доменов в
`ontology.md`; поштучная разметка 643 вопросов Impact/Difficulty — этап
следующей итерации (заготовка: наследовать от домена, переопределять
точечно).
