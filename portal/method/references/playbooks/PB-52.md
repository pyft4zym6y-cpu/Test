# PB-52 · Design System (сайт)

| Домен | Платформа / IT |
| --- | --- |
| Срабатывает по правилам | R41 |
| Вопросы-источники | VI-008, VI-009, PL-011 |
| Длительность | 6 недель |
| Deliverable | D-18 Дизайн-система сайта (Figma) |
| Владелец у клиента | Дизайн-лид / фронтенд |


### 1  Зачем нужен этот плейбук
Когда каждая страница проектируется с нуля, а макеты расходятся с кодом, разработка медленная, а интерфейс непоследовательный. Design System создаёт единый язык интерфейса: переиспользуемые компоненты, токены и паттерны, синхронизированные между дизайном и кодом.
Плейбук строит дизайн-систему сайта на основе визуальной идентичности: токены, компоненты, паттерны и их синхронизацию с фронтендом.

|  | Корневая проблема Нет дизайн-системы при активной разработке. Каждая страница проектируется заново, макеты расходятся с кодом, интерфейс непоследователен. Разработка медленная, а UX страдает от несогласованности. |
| --- | --- |

### 3  Что нужно на входе
Полный список требований к данным и доступам — в документе «Реестр данных и доступов». Ключевые входы:
Текущие макеты и компоненты сайта — Инвентаризация UI. [обязательно]
Визуальная система (из PB-51) — Токены и стиль. [обязательно]
Доступ к фронтенд-коду — Синхронизация с кодом. [обязательно]
Библиотека паттернов и состояний — Компоненты. [желательно]

### 4  Пошаговый процесс
Шаг 1. Инвентаризировать текущий UI
Собрать существующие компоненты и паттерны.
Выявить дубли и несогласованности.
Оценить разрыв между макетами и кодом.
Шаг 2. Задать дизайн-токены
Определить токены: цвета, типографика, отступы, тени (из PB-51).
Обеспечить единство с визуальной идентичностью.
Задать адаптивные правила.
Шаг 3. Спроектировать компоненты
Спроектировать базовые компоненты и их состояния.
Задать правила использования каждого.
Собрать библиотеку компонентов.
Шаг 4. Задать паттерны
Спроектировать составные паттерны: карточка, форма, чекаут.
Обеспечить консистентность паттернов.
Связать с UX/CRO-находками (PB-15).
Шаг 5. Синхронизировать с кодом
Обеспечить соответствие дизайн-системы и фронтенд-компонентов.
Задать процесс поддержания синхронизации.
Определить, как вносятся изменения.
Шаг 6. Оформить и внедрить
Собрать дизайн-систему в Figma как источник истины.
Задать процесс использования командой.
Связать с платформой (PB-14) и визуалом (PB-51).

### 5  Формулы и определения

| Показатель | Формула | Ориентир / комментарий |
| --- | --- | --- |
| Переиспользование | Компонентов из системы / всего UI | Зрелость системы |
| Design-code parity | Соответствие макетов и кода | Синхронизация |
| Скорость сборки | Время создания новой страницы | Эффект системы |
| Консистентность | Единообразие UI across страниц | Качество опыта |


### 6  Что получается на выходе (Deliverable)
D-18 «Дизайн-система сайта» (Figma):
Аудит UI — текущие компоненты и несогласованности.
Дизайн-токены — цвета, типографика, отступы.
Библиотека компонентов — компоненты с состояниями и правилами.
Паттерны — составные паттерны интерфейса.
Синхронизация с кодом — процесс parity дизайна и фронтенда.

### 7  Критерии приёмки
Работа считается выполненной, когда выполнены все условия ниже.
✓  Инвентаризирован UI, выявлены дубли и несогласованности.
✓  Заданы дизайн-токены на основе визуальной идентичности.
✓  Спроектирована библиотека компонентов с состояниями.
✓  Заданы составные паттерны интерфейса.
✓  Настроена синхронизация дизайна и кода.
✓  Система связана с PB-51 и PB-14.

### 8  Типовые ошибки

| Ошибка | Чем грозит | Как избежать |
| --- | --- | --- |
| Дизайн-система без токенов | Несогласованность сохраняется | Начать с токенов из PB-51 |
| Компоненты без правил | Используются неправильно | Задать правила использования |
| Нет синхронизации с кодом | Макеты и код расходятся | Процесс design-code parity |
| Система без владельца | Устаревает и умирает | Задать процесс поддержания |
