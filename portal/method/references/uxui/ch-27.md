# Глава 27. Forms & Data Entry

## 27.1 Роль форм в eCommerce
Формы являются одним из наиболее критичных элементов пользовательского опыта.
Практически каждый ключевой сценарий включает ввод данных:
регистрация;
авторизация;
оформление заказа;
поиск;
подписка;
оформление возврата;
добавление адреса;
оплата;
отзыв;
обращение в поддержку.
Каждое дополнительное поле увеличивает вероятность отказа.
Каждое непонятное поле увеличивает когнитивную нагрузку.
Каждая ошибка увеличивает риск незавершённого сценария.
Главная задача UX — максимально сократить усилия пользователя при вводе данных.

## 27.2 Принципы проектирования форм
Все формы должны соответствовать пяти фундаментальным принципам.

### Минимум полей
Запрашивается только информация, действительно необходимая для выполнения задачи.
Каждое поле должно иметь бизнес-обоснование.
Если поле не используется — его следует удалить.

### Минимум решений
Пользователь не должен принимать лишние решения.
Например, вместо выбора страны вручную можно определить её автоматически и предложить изменить только при необходимости.

### Минимум ошибок
Интерфейс должен предотвращать ошибки, а не только сообщать о них.
Используются:
маски ввода;
ограничения;
автодополнение;
списки выбора;
проверки в реальном времени.

### Прозрачность
Пользователь должен понимать:
зачем нужны данные;
какие поля обязательны;
сколько осталось заполнить;
что произойдёт после отправки формы.

### Последовательность
Все формы продукта используют единые компоненты, правила и поведение.

## 27.3 Архитектура формы
Каждая форма должна состоять из стандартных элементов.
Label
↓
Input
↓
Helper Text
↓
Validation
↓
Error Message
↓
Success State
Отсутствие любого элемента должно быть осознанным решением.

## 27.4 Label
Label всегда отображается отдельно от Placeholder.
Например.
Имя
[____________]
а не
[Введите имя]
После ввода Placeholder исчезает.
Следовательно, пользователь теряет контекст.
Поэтому Placeholder никогда не заменяет Label.

## 27.5 Placeholder
Placeholder используется исключительно как дополнительная подсказка.
Например.
Введите email
или
example@email.com
Placeholder не должен содержать критически важную информацию.

## 27.6 Helper Text
Используется для пояснений.
Например.
Пароль должен содержать минимум 8 символов.
или
Мы никогда не передадим ваш email третьим лицам.

## 27.7 Required Fields
Количество обязательных полей должно быть минимальным.
Рекомендуется использовать:
●
или
(обязательно)
Не следует помечать необязательные поля как обязательные.

## 27.8 Input Types
Для каждого поля необходимо использовать корректный тип.
Например.
Email.
↓
email
Телефон.
↓
tel
Дата.
↓
date
Количество.
↓
number
Поиск.
↓
search
Это улучшает мобильный UX и работу автозаполнения.

## 27.9 Input Masks
Маски используются там, где формат данных заранее известен.
Например.
Телефон.
Дата.
Банковская карта.
ИНН.
Почтовый индекс.
Маска должна помогать пользователю, а не ограничивать его.

## 27.10 Autofill
Формы должны поддерживать:
Browser Autofill.
Apple Autofill.
Google Autofill.
Password Managers.
Saved Addresses.
Saved Cards.
Каждое автоматически заполненное поле повышает вероятность завершения формы.

## 27.11 Validation
Валидация должна происходить максимально рано.
Используются три уровня.

### Inline Validation
Во время ввода.
Наиболее предпочтительный вариант.

### On Blur
После выхода из поля.
Используется для большинства форм.

### On Submit
После отправки.
Используется только для финальной проверки.

## 27.12 Error Messages
Сообщение об ошибке должно содержать:
что произошло;
как исправить ошибку.
Например.
❌ Неправильно.
Ошибка.
✅ Правильно.
Введите корректный адрес электронной почты.

## 27.13 Success Messages
После успешного действия пользователь должен получить подтверждение.
Например.
Адрес успешно сохранён.
Пароль изменён.
Заказ оформлен.
Не следует использовать успех только через изменение цвета элемента.

## 27.14 Password UX
Современные формы должны поддерживать:
показать/скрыть пароль;
проверку сложности;
индикатор надёжности;
вставку из менеджеров паролей;
генерацию пароля (где применимо).
Не рекомендуется требовать чрезмерно сложные комбинации без необходимости.

## 27.15 Multi-step Forms
Если форма длинная, рекомендуется разбивать её на этапы.
Каждый этап должен содержать логически связанные поля.
Пользователь должен видеть прогресс выполнения.

## 27.16 Mobile Forms
На мобильных устройствах необходимо:
использовать подходящую клавиатуру;
увеличивать область касания;
избегать горизонтальной прокрутки;
автоматически переходить между полями при необходимости;
сохранять введённые данные при смене ориентации экрана.

## 27.17 Accessibility
Каждая форма должна поддерживать:
навигацию с клавиатуры;
корректный порядок фокуса;
ARIA-атрибуты;
озвучивание ошибок экранными дикторами;
достаточный контраст;
понятные названия полей.

## 27.18 Международные сценарии
При проектировании необходимо учитывать:
различные форматы адресов;
разные номера телефонов;
различные валюты;
локальные способы оплаты;
особенности имён и фамилий;
разные форматы дат.
Нельзя проектировать форму исключительно под одну страну, если продукт работает международно.

## 27.19 Analytics
Для форм рекомендуется фиксировать:
Form View;
Field Focus;
Field Blur;
Validation Error;
Form Abandonment;
Form Completion;
Time to Complete;
Autofill Usage;
Password Visibility Toggle;
Submit Success;
Submit Failure.

## 27.20 KPI Forms
Рекомендуемые показатели.

| KPI | Назначение |
| --- | --- |
| Form Completion Rate | Процент успешно заполненных форм |
| Form Abandonment Rate | Процент незавершённых форм |
| Average Completion Time | Среднее время заполнения |
| Validation Error Rate | Частота ошибок |
| Autofill Usage | Использование автозаполнения |
| Field Drop-off Rate | Поля, на которых пользователи прекращают заполнение |
| Submit Success Rate | Успешные отправки |
| Submit Failure Rate | Неудачные отправки |


## 27.21 Типичные ошибки
Использование Placeholder вместо Label.
Запрос избыточных данных.
Отсутствие автозаполнения.
Валидация только после отправки формы.
Очистка всех полей после ошибки.
Непонятные сообщения об ошибках.
Использование неподходящих типов клавиатуры на мобильных устройствах.
Слишком длинные формы без разбивки на этапы.
Отсутствие поддержки менеджеров паролей.
Игнорирование требований Accessibility.

## 27.22 Forms QA Checklist
Перед выпуском необходимо проверить:
количество обязательных полей минимально;
все поля имеют Label;
Placeholder используется только как подсказка;
поддерживается Autofill;
ошибки отображаются своевременно;
данные не теряются при ошибках;
корректно работают мобильные клавиатуры;
соблюдены требования Accessibility;
аналитика настроена;
форма протестирована на Desktop, Tablet и Mobile.
