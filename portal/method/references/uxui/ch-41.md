# Глава 41. Accessibility (WCAG) & Inclusive Design

## 41.1 Почему Accessibility — это обязательное требование
Accessibility — это способность цифрового продукта быть доступным для максимально широкого круга пользователей независимо от их физических, сенсорных, когнитивных или временных ограничений.
Для eCommerce доступность влияет не только на соответствие требованиям законодательства, но и на:
Conversion Rate;
Customer Satisfaction;
SEO;
Retention;
Brand Trust.
Доступность должна проектироваться с первого дня разработки продукта.

## 41.2 Inclusive Design
Inclusive Design значительно шире Accessibility.
Accessibility отвечает на вопрос:
Может ли пользователь пользоваться системой?
Inclusive Design отвечает на вопрос:
Насколько комфортно пользователь может пользоваться системой?
Интерфейс должен учитывать максимально широкий спектр пользователей.
Например:
нарушения зрения;
нарушения слуха;
моторные ограничения;
когнитивные особенности;
возрастные изменения;
временные ограничения (например, использование одной рукой).

## 41.3 Принципы WCAG
В основе WCAG лежат четыре принципа.
Perceivable
↓
Operable
↓
Understandable
↓
Robust
Любое нарушение хотя бы одного принципа ухудшает доступность продукта.

## 41.4 Perceivable (Воспринимаемость)
Пользователь должен иметь возможность воспринимать информацию.
Необходимо обеспечить:
альтернативный текст для изображений;
субтитры для видео;
достаточный контраст;
масштабирование текста;
визуальные подсказки.
Информация не должна передаваться исключительно цветом.

## 41.5 Operable (Управляемость)
Все элементы интерфейса должны быть доступны без использования мыши.
Поддерживаются:
клавиатурная навигация;
логичный порядок Tab;
видимый Focus;
отсутствие Keyboard Trap;
возможность пропустить повторяющиеся блоки.

## 41.6 Understandable (Понятность)
Интерфейс должен быть предсказуемым.
Необходимо:
использовать понятные названия;
избегать неоднозначных терминов;
одинаково оформлять одинаковые действия;
заранее предупреждать о последствиях важных операций.

## 41.7 Robust (Надёжность)
Интерфейс должен корректно работать:
со Screen Readers;
с различными браузерами;
с Assistive Technologies;
с будущими версиями технологий.
Использование стандартных HTML-элементов предпочтительнее самописных компонентов без необходимости.

## 41.8 Контрастность
Минимальные требования.
Обычный текст.
Минимальный коэффициент контрастности — 4.5:1.
Крупный текст.
Минимум — 3:1.
Не рекомендуется использовать светло-серый текст на белом фоне.

## 41.9 Typography
Рекомендуется:
минимальный читаемый размер текста;
достаточный межстрочный интервал;
ограниченная длина строки;
возможность масштабирования без потери функциональности.
Текст должен оставаться читаемым при увеличении масштаба.

## 41.10 Keyboard Navigation
Пользователь должен иметь возможность выполнить все основные действия только клавиатурой.
Например.
Tab
↓
Shift + Tab
↓
Enter
↓
Space
↓
Esc
↓
Arrow Keys
Нельзя блокировать стандартное поведение клавиатуры без объективной причины.

## 41.11 Focus Management
Каждый интерактивный элемент должен иметь:
видимый Focus;
логичный порядок;
сохранение фокуса после действий;
корректный возврат после закрытия модальных окон.
Пользователь никогда не должен терять текущую позицию.

## 41.12 Forms Accessibility
Все формы должны содержать:
Label.
↓
Helper Text.
↓
Error Message.
↓
ARIA Description.
↓
Autocomplete.
↓
Required Indicator.
Placeholder не заменяет Label.

## 41.13 Images
Все изображения подразделяются.
Информативные.
↓
ALT обязателен.
Декоративные.
↓
ALT пустой.
Не следует использовать одинаковый ALT для всех изображений.

## 41.14 Icons
Если иконка несёт смысл, она должна иметь текстовое описание.
Например.
Удалить.
Поиск.
Избранное.
Корзина.
Иконка без подписи допустима только при очевидном контексте.

## 41.15 Tables
Таблицы должны содержать:
заголовки;
структурированные строки;
корректную разметку;
логичный порядок чтения.
Таблицы не должны использоваться исключительно для построения макета страницы.

## 41.16 Modals
Модальные окна должны:
получать Focus после открытия;
блокировать фон;
закрываться клавишей Esc;
возвращать Focus в исходный элемент после закрытия.

## 41.17 Notifications
Все уведомления должны быть доступны для Screen Reader.
Например.
Ошибка.
↓
Успех.
↓
Предупреждение.
↓
Информационное сообщение.

## 41.18 Screen Readers
Интерфейс необходимо тестировать с использованием Screen Reader.
Проверяются:
структура документа;
порядок чтения;
названия элементов;
ARIA Labels;
ARIA Live Regions.

## 41.19 Mobile Accessibility
Особенности мобильных устройств.
Размер зоны касания.
Минимум 44×44 px.
Поддержка VoiceOver.
Поддержка TalkBack.
Корректная работа при увеличенном размере шрифта.

## 41.20 Accessibility для PDP
Карточка товара должна поддерживать:
альтернативный текст изображений;
описание видео;
доступность галереи с клавиатуры;
понятные характеристики;
корректную работу выбора вариантов.

## 41.21 Accessibility для Checkout
Checkout требует особого внимания.
Необходимо обеспечить:
логичный порядок полей;
понятные ошибки;
автоматическое перемещение Focus к ошибке;
работу Autofill;
совместимость с Screen Readers.

## 41.22 Accessibility Testing
Проверка включает:
ручное тестирование;
автоматическое сканирование;
клавиатурную навигацию;
Screen Reader;
проверку контрастности;
проверку масштабирования;
тестирование на мобильных устройствах.
Автоматические инструменты выявляют только часть возможных проблем.

## 41.23 Accessibility Governance
В компании должны быть определены:
стандарты разработки;
чек-листы;
обязательные проверки;
владельцы процесса;
обучение команды;
регулярные аудиты.
Accessibility не должна зависеть только от энтузиазма отдельных сотрудников.

## 41.24 Analytics
Рекомендуется отслеживать:
использование клавиатурной навигации;
увеличение масштаба;
использование режима высокой контрастности (если доступно);
ошибки доступности;
успешность выполнения ключевых сценариев пользователями вспомогательных технологий (при наличии специализированных исследований).
При этом необходимо соблюдать требования конфиденциальности и не собирать чувствительные данные о состоянии здоровья пользователей.

## 41.25 KPI Accessibility

| KPI | Назначение |
| --- | --- |
| WCAG Compliance Score | Соответствие требованиям WCAG |
| Accessibility Defects | Количество выявленных проблем |
| Keyboard Success Rate | Успешность сценариев без мыши |
| Screen Reader Compatibility | Совместимость со Screen Reader |
| Contrast Compliance | Соответствие требованиям контрастности |
| Accessibility Issue Resolution Time | Скорость устранения проблем |
| Accessibility Audit Score | Результат регулярного аудита |
| Accessible Component Coverage | Доля компонентов, соответствующих стандартам доступности |


## 41.26 Типичные ошибки
Использование Placeholder вместо Label.
Недостаточный контраст текста.
Отсутствие видимого Focus.
Невозможность работы с клавиатуры.
Неправильное использование ARIA.
Отсутствие ALT у изображений.
Использование цвета как единственного способа передачи информации.
Слишком маленькие зоны касания.
Неправильный порядок Tab.
Игнорирование тестирования со Screen Reader.

## 41.27 Accessibility QA Checklist
Перед выпуском необходимо проверить:
все интерактивные элементы доступны с клавиатуры;
Focus отображается корректно;
изображения имеют корректные ALT;
формы содержат Label и понятные сообщения об ошибках;
контрастность соответствует требованиям WCAG;
модальные окна правильно управляют Focus;
интерфейс протестирован с использованием Screen Reader;
поддерживается масштабирование текста;
Accessibility-аудит успешно пройден;
требования законодательства целевых рынков соблюдены.

## 41.28 Deliverables
По результатам проектирования должны быть подготовлены:
Accessibility Strategy;
WCAG Compliance Guide;
Inclusive Design Guidelines;
Accessibility Component Checklist;
Forms Accessibility Guide;
Keyboard Navigation Specification;
Screen Reader Testing Guide;
Accessibility QA Checklist;
Accessibility Audit Report Template;
Accessibility KPI Dashboard;
Accessibility Governance Policy.
