# Глава 42. Performance Engineering & Core Web Vitals

## 42.1 Производительность как фактор прибыли
Производительность (Performance) — это способность eCommerce-платформы быстро реагировать на действия пользователя, минимизируя задержки при загрузке страниц, взаимодействии с интерфейсом и выполнении операций.
Для интернет-магазина производительность напрямую влияет на:
Conversion Rate;
Bounce Rate;
Average Order Value;
SEO;
Customer Satisfaction;
Revenue.
Каждая лишняя задержка увеличивает вероятность потери пользователя.
Производительность должна рассматриваться как часть пользовательского опыта, а не только как техническая задача.

## 42.3 Core Web Vitals
Core Web Vitals — ключевые пользовательские метрики производительности.
В настоящее время основными являются:
LCP (Largest Contentful Paint);
INP (Interaction to Next Paint);
CLS (Cumulative Layout Shift).
Они отражают восприятие скорости пользователем.

## 42.4 Largest Contentful Paint (LCP)
LCP измеряет время загрузки крупнейшего видимого элемента страницы.
Для eCommerce это обычно:
Hero Banner;
главное изображение товара;
основной заголовок;
первый блок каталога.
Целевое значение:
≤ 2.5 секунды
Основные способы улучшения:
оптимизация изображений;
CDN;
Server Side Rendering;
preload критических ресурсов;
уменьшение времени ответа сервера.

## 42.5 Interaction to Next Paint (INP)
INP измеряет скорость реакции интерфейса на действия пользователя.
Например:
клик;
выбор фильтра;
Add to Cart;
открытие меню;
изменение количества товара.
Целевое значение:
≤ 200 мс
Причины ухудшения:
тяжёлый JavaScript;
длительные вычисления;
блокировка главного потока;
сложные обработчики событий.

## 42.6 Cumulative Layout Shift (CLS)
CLS измеряет неожиданное смещение элементов интерфейса.
Например:
кнопка “Купить” сместилась после загрузки изображения;
баннер появился позже и сдвинул контент вниз.
Целевое значение:
≤ 0.1
Причины:
изображения без фиксированных размеров;
динамические баннеры;
асинхронная реклама;
изменение размеров компонентов после загрузки.

## 42.7 Performance Budget
Для каждого проекта рекомендуется определить Performance Budget.
Например.
HTML.
≤ 100 KB
CSS.
≤ 200 KB
JavaScript.
≤ 300 KB
Hero Image.
≤ 250 KB
Fonts.
≤ 150 KB
Third-party Scripts.
≤ 250 KB
Performance Budget позволяет контролировать рост технического долга.

## 42.8 Rendering Strategies
Современный eCommerce использует несколько стратегий рендеринга.

### CSR
Client Side Rendering.
Преимущества:
простота разработки.
Недостатки:
долгая первая загрузка.

### SSR
Server Side Rendering.
Преимущества:
быстрый First Paint;
лучшее SEO.
Недостатки:
увеличение нагрузки на сервер.

### SSG
Static Site Generation.
Подходит для:
контентных страниц;
категорий с редкими изменениями.

### ISR
Incremental Static Regeneration.
Позволяет обновлять страницы постепенно без полной пересборки проекта.
Особенно эффективен для крупных каталогов.

## 42.9 Image Optimization
Изображения являются крупнейшим источником нагрузки.
Рекомендуется:
современные форматы (AVIF, WebP при наличии поддержки);
адаптивные размеры;
Lazy Loading для некритичных изображений;
preload первого изображения;
CDN;
автоматическое сжатие.

## 42.10 Font Optimization
Шрифты должны:
загружаться быстро;
использовать ограниченное количество начертаний;
поддерживать font-display: swap;
предварительно загружаться только при необходимости.

## 42.11 CSS Optimization
Рекомендуется:
удалять неиспользуемые стили;
разделять критический и некритический CSS;
минимизировать файлы;
использовать кэширование.

## 42.12 JavaScript Optimization
JavaScript чаще всего становится главным источником задержек.
Рекомендуется:
Code Splitting.
↓
Tree Shaking.
↓
Lazy Loading.
↓
Dynamic Import.
↓
Минификация.
↓
Удаление неиспользуемых библиотек.
↓
Оптимизация Third-party Scripts.

## 42.13 API Performance
API должны обеспечивать:
минимальное время ответа;
сжатие данных;
кэширование;
пагинацию;
частичную загрузку данных;
устойчивость к высоким нагрузкам.

## 42.14 Database Performance
Для каталога eCommerce особенно важны:
индексация;
оптимизация SQL-запросов;
кэширование результатов;
репликация;
оптимизация полнотекстового поиска.

## 42.15 CDN
Content Delivery Network позволяет:
уменьшить задержку;
распределить нагрузку;
ускорить загрузку изображений;
ускорить доставку JavaScript и CSS.
CDN рекомендуется использовать для всех публичных ресурсов.

## 42.16 Caching Strategy
Используются несколько уровней кэширования.
Browser Cache
↓
CDN Cache
↓
Application Cache
↓
Database Cache
Стратегия должна учитывать актуальность данных и частоту их изменения.

## 42.17 Lazy Loading
Lazy Loading применяется для:
изображений вне первого экрана;
видео;
второстепенных блоков;
рекомендаций;
отзывов.
Первый экран не должен зависеть от Lazy Loading.

## 42.18 Skeleton Screens
Вместо Spinner рекомендуется использовать Skeleton.
Skeleton:
сохраняет структуру страницы;
уменьшает ощущение ожидания;
снижает вероятность отказа.

## 42.19 Third-party Scripts
Необходимо регулярно анализировать влияние сторонних сервисов.
Например:
аналитика;
онлайн-чаты;
пиксели рекламы;
виджеты отзывов;
A/B-платформы.
Каждый дополнительный скрипт увеличивает время загрузки.

## 42.20 Real User Monitoring (RUM)
RUM измеряет производительность на устройствах реальных пользователей.
Отслеживаются:
LCP;
INP;
CLS;
время загрузки;
ошибки JavaScript;
скорость API.
RUM показывает реальные условия эксплуатации.

## 42.21 Synthetic Monitoring
Synthetic Monitoring выполняет автоматические проверки по заранее заданным сценариям.
Например:
Главная.
↓
Категория.
↓
Карточка товара.
↓
Checkout.
↓
Оплата.
Позволяет обнаруживать проблемы до появления жалоб пользователей.

## 42.22 Analytics
Необходимо отслеживать:
Core Web Vitals;
Time to First Byte (TTFB);
First Contentful Paint (FCP);
Speed Index;
JavaScript Errors;
API Response Time;
Cache Hit Rate;
CDN Hit Rate;
Page Weight;
Third-party Script Load Time.

## 42.23 KPI Performance

| KPI | Назначение |
| --- | --- |
| LCP | Скорость отображения основного контента |
| INP | Скорость реакции интерфейса |
| CLS | Стабильность макета |
| TTFB | Время ответа сервера |
| API Response Time | Скорость API |

| Average Page Weight | Средний вес страницы |

## 42.24 Типичные ошибки
Игнорирование Performance Budget.
Использование изображений большого размера.
Подключение десятков сторонних скриптов без оценки их влияния.
Отсутствие CDN.
Полная загрузка JavaScript при первом открытии страницы.
CLS из-за динамического контента.
Отсутствие кэширования.
Использование Spinner вместо Skeleton.
Отсутствие мониторинга производительности после релиза.

## 42.25 Performance QA Checklist
ДзеркалоПеред выпуском необходимо проверить:
Core Web Vitals соответствуют целевым значениям;
Performance Budget соблюдён;
изображения оптимизированы;
JavaScript разбит на чанки;
CSS минимизирован;
CDN используется для статических ресурсов;
кэширование настроено;
сторонние скрипты не блокируют загрузку;
RUM и Synthetic Monitoring настроены;
производительность протестирована на Desktop и Mobile.
