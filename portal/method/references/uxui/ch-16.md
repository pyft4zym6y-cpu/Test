# Глава 16. Wireframing & UX Prototyping

## 16.1 Назначение Wireframes
Wireframe — это схематическое представление будущего интерфейса, отображающее структуру страницы, расположение элементов, пользовательские сценарии и информационную иерархию без детальной визуальной проработки.
Основная задача Wireframe — проверить логику интерфейса до начала UI-дизайна и разработки.
На данном этапе не оценивается эстетика интерфейса.
Проверяется исключительно удобство использования.

## 16.2 Задачи Wireframing
Wireframes используются для:
проверки пользовательских сценариев;
проверки информационной архитектуры;
проверки навигации;
согласования структуры страниц;
подготовки технического задания;
проведения UX-тестирования;
оценки полноты функциональности.
Wireframe должен отвечать на вопрос:
Поможет ли данный экран пользователю выполнить свою задачу?

## 16.3 Когда создаются Wireframes
Последовательность проектирования должна быть следующей.

## 16.4 Fidelity
Wireframes подразделяются на несколько уровней детализации.

### Low Fidelity
Используются:
простые фигуры;
серые блоки;
условные изображения;
заглушки текста.
Основная задача —
структура.

### Mid Fidelity
Добавляются:
реальные размеры блоков;
реальные сценарии;
контентные зоны;
элементы управления.

### High Fidelity Wireframe
Максимально приближен к будущему интерфейсу.
Используется:
реальный контент;
реальные размеры;
компоненты;
состояния элементов.
При этом визуальный стиль ещё не разрабатывается.

## 16.5 Структура Wireframe
Каждый экран должен содержать одинаковый уровень детализации.
Например.
Header
↓
Navigation
↓
Search
↓
Content
↓
Sidebar
↓
Recommendations
↓
Footer
Каждый блок проектируется отдельно.

## 16.6 Grid System
До начала проектирования определяется единая сетка.
Desktop.
12 колонок.
Tablet.
8 колонок.
Mobile.
4 колонки.
Все страницы должны использовать одинаковую систему построения.

## 16.7 Правила проектирования

### Один экран — одна основная задача
Например.
Карточка товара.
Главная задача —
принятие решения о покупке.
Checkout.
Главная задача —
завершение покупки.
Личный кабинет.
Главная задача —
управление заказами.
Каждый экран должен иметь только одну основную цель.

### Приоритет сценария
Основной сценарий проектируется первым.
Только после этого добавляются дополнительные функции.

### Минимизация шума
Wireframe не должен содержать декоративных элементов.
Используются только:
структура;
логика;
информационная иерархия.

### Контент определяет размеры
Нельзя проектировать блоки без понимания реального объема информации.
Например.
Отзывы.
FAQ.
Характеристики.
SEO.

## 16.8 Информационная иерархия
Каждый экран должен иметь очевидную последовательность просмотра.
Типичный сценарий.
Заголовок
↓
Основная информация
↓
CTA
↓
Подробности
↓
Дополнительная информация
↓
Рекомендации
↓
FAQ
↓
SEO
Пользователь должен понимать:
что продаётся;
почему стоит купить;
что делать дальше.

## 16.12 Wireframes Checkout
Checkout проектируется отдельно.

↓

↓
Доставка
↓
Оплата
↓

Подтверждение
На этапе Wireframe должны быть предусмотрены все ошибки пользователя.

## 16.13 Состояния интерфейса
Каждый экран проектируется не только для успешного сценария.
Необходимо предусмотреть:
Loading.
Empty.
Success.
Warning.
Error.
Offline.
Permission Denied.
No Results.
Skeleton.
Каждое состояние должно иметь собственный Wireframe.

## 16.14 Edge Cases
Необходимо проектировать нестандартные ситуации.
Например.
Товар закончился.
Цена изменилась.
Ошибка оплаты.
Нет доставки.
Товар удалён.
Акция закончилась.
Нет соединения.
Каждый сценарий должен иметь отдельное решение.

## 16.15 Annotation
Каждый Wireframe сопровождается пояснениями.
Необходимо документировать:
логику работы;
условия отображения;
переходы;
состояния;
бизнес-правила;
аналитику.

## 16.16 Проверка качества Wireframes
До передачи в UI Design выполняется проверка.
Проверяется.
Все User Flow реализованы.
Все Task Flow завершены.
Нет тупиковых сценариев.
Все состояния предусмотрены.
Все CTA определены.
Все переходы описаны.
Нет противоречий IA.
Нет дублирования информации.
Все сценарии соответствуют JTBD.

## 16.17 Типичные ошибки
Начало работы с визуальным дизайном до завершения Wireframes.
Использование Lorem Ipsum вместо реального контента.
Игнорирование ошибок и нестандартных сценариев.
Проектирование только Desktop.
Игнорирование мобильной версии.
Отсутствие аннотаций.
Отсутствие связи с аналитикой.
Избыточная детализация Low-Fidelity макетов.
Изменение структуры уже после начала UI Design.
