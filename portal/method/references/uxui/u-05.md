## Глава 18. Design System

## 18.1 Что такое Design System
Design System — это централизованная система стандартов, компонентов, правил и процессов, обеспечивающая единообразное проектирование, разработку и развитие цифрового продукта.
Design System — это не UI Kit.
UI Kit является лишь небольшой частью Design System.
Полноценная Design System объединяет:
принципы проектирования;
визуальный язык;
токены дизайна;
библиотеку компонентов;
паттерны интерфейсов;
стандарты разработки;
документацию;
процессы сопровождения;
систему управления изменениями.
Для Enterprise eCommerce Design System становится самостоятельным продуктом.

## 18.2 Цели Design System
Design System должна обеспечивать:
единообразие интерфейсов;
ускорение проектирования;
ускорение разработки;
уменьшение количества ошибок;
масштабируемость продукта;
повторное использование компонентов;
единый пользовательский опыт;
снижение стоимости сопровождения.

## 18.4 Design Principles
Design System начинается не с компонентов.
Она начинается с принципов.

Модульность.
Каждый новый компонент должен соответствовать данным принципам.

Design Tokens являются минимальными строительными единицами интерфейса.
Они содержат не конкретные значения, а систему переменных.

## 18.22 Design System Maturity Model
Для оценки зрелости рекомендуется использовать пятиуровневую модель.

| Уровень | Характеристика |
| --- | --- |
| Level 1 | Разрозненные UI-элементы, отсутствуют стандарты |
| Level 2 | Сформирован UI Kit, используются базовые компоненты |
| Level 3 | Внедрена централизованная Design System с токенами и библиотекой компонентов |
| Level 4 | Design System интегрирована с фронтендом, автоматизированы процессы обновления, есть единое управление |
| Level 5 | Полностью масштабируемая Enterprise Design System с версионированием, аналитикой использования, governance-процессами и поддержкой нескольких продуктов и брендов |

## Глава 19. Typography System

## 19.1 Роль типографики в UX
Типографика — это система организации текстовой информации, обеспечивающая быстрое восприятие, понимание и принятие решений пользователем.
В интерфейсах eCommerce текст является основным носителем информации. Именно через текст пользователь получает сведения о товаре, условиях покупки, доставке, гарантии, наличии, цене и характеристиках.
Качественная типографическая система должна:
сокращать время поиска информации;
уменьшать когнитивную нагрузку;
облегчать сканирование страницы;
повышать читаемость;
поддерживать визуальную иерархию;
обеспечивать единообразие интерфейса.
Типографика является функциональным инструментом, а не декоративным элементом.

## 19.2 Принципы типографической системы
Типографическая система должна строиться на пяти фундаментальных принципах.

### Иерархия
Каждый уровень информации должен визуально отличаться.
Пользователь должен понимать приоритет информации без чтения всего текста.

### Последовательность
Все страницы используют одинаковые размеры, интервалы и стили.
Одинаковые сущности оформляются одинаково.

### Читаемость
Текст должен легко восприниматься при любых размерах экрана.

### Контраст
Необходимо обеспечить достаточную разницу между уровнями информации.

### Масштабируемость
Типографическая система должна работать:
Desktop;
Tablet;
Mobile;
Large Display.

## 19.3 Типографическая шкала
Рекомендуется использовать модульную шкалу.
Например.

| Стиль | Размер |
| --- | --- |
| Display XL | 64 px |
| Display L | 56 px |
| H1 | 48 px |
| H2 | 40 px |
| H3 | 32 px |
| H4 | 28 px |
| H5 | 24 px |
| H6 | 20 px |
| Body L | 18 px |
| Body | 16 px |
| Body S | 14 px |
| Caption | 12 px |
| Overline | 11 px |

Размеры являются частью Design Tokens и не должны задаваться произвольно.

## 19.4 Типографические роли
Каждый стиль имеет фиксированное назначение.

### Display
Используется:
Hero;
Landing;
рекламные баннеры.

### Heading
Используется:
заголовки страниц;
названия блоков.

### Body
Используется:
описания;
статьи;
характеристики;
инструкции.

### Label
Используется:
кнопки;
поля ввода;
формы;
фильтры.

### Caption
Используется:
подписи;
вспомогательная информация;
даты;
артикулы.

## 19.5 Вертикальный ритм
Вертикальный ритм определяет расстояния между строками, абзацами и блоками текста.
Правила:
Заголовок всегда ближе к связанному с ним контенту, чем к предыдущему блоку.
Абзацы отделяются интервалами, а не пустыми строками.
Межстрочный интервал должен обеспечивать комфортное чтение.
Нарушение вертикального ритма делает интерфейс визуально хаотичным.

## 19.6 Длина строки
Слишком длинные строки снижают скорость чтения.
Рекомендуемые значения.
Desktop.
60–90 символов.
Mobile.
30–45 символов.
Для карточек товара рекомендуется использовать ещё более короткие строки.

## 19.7 Межстрочный интервал
Рекомендуемый Line Height.
Заголовки.
110–130%.
Основной текст.
140–170%.
Инструкции.
150–180%.
Таблицы.
120–140%.

## 19.8 Типографика карточки товара
Карточка товара требует собственной системы.
Приоритет.
Название товара.
↓
Цена.
↓
Скидка.
↓
CTA.
↓
Основные преимущества.
↓
Характеристики.
↓
Описание.
↓
Дополнительная информация.
Название товара не должно конкурировать с ценой.
Цена не должна конкурировать с CTA.

## 19.9 Типографика каталога
Карточка товара в каталоге должна содержать минимальный объём текста.
Основные элементы.
Название.
Цена.
Рейтинг.
Наличие.
Badge.
CTA.
Любая дополнительная информация ухудшает скорость сканирования каталога.

## 19.10 Типографика Checkout
Checkout требует максимальной ясности.
Приоритет.
Название этапа.
↓
Основные поля.
↓
Ошибки.
↓
Подсказки.
↓
Кнопка подтверждения.
Ошибки должны быть заметны сразу после возникновения.

## 19.11 Типографика форм
Каждое поле должно иметь:
Label;
Placeholder (не вместо Label);
Helper Text;
Error Message;
Success Message.
Placeholder не может использоваться как единственный способ обозначения назначения поля.

## 19.12 Типографика ошибок
Сообщение об ошибке должно отвечать на три вопроса:
Что произошло?
Почему это произошло?
Что необходимо сделать?
Пример.
❌ Неправильно.
Ошибка.
✅ Правильно.
Не удалось выполнить оплату.
Проверьте данные карты или выберите другой способ оплаты.

## 19.13 Локализация
Типографическая система должна учитывать:
различные языки;
длину слов;
направление письма (LTR/RTL);
особенности чисел;
валюты;
единицы измерения.
Компоненты должны выдерживать увеличение длины текста без нарушения композиции.

## 19.14 Адаптивная типографика
Размеры текста не должны масштабироваться линейно.
Для мобильных устройств допускается уменьшение размеров, но сохраняется визуальная иерархия.
Проверяются:
переносы строк;
обрезка текста;
переполнение;
масштабирование при системных настройках.

## 19.15 Variable Fonts
Для современных проектов рекомендуется использовать Variable Fonts.
Преимущества:
уменьшение количества файлов;
плавное изменение насыщенности;
улучшение производительности;
гибкость адаптации.

## 19.16 Accessibility
Типографика должна соответствовать требованиям доступности.
Проверяется:
минимальный размер текста;
контраст;
масштабирование до 200%;
читаемость без потери функциональности;
поддержка экранных дикторов.
Недопустимо использовать изображение вместо текста там, где необходима машинная интерпретация.

## 19.17 Типичные ошибки
Использование более трёх гарнитур.
Случайные размеры текста.
Отсутствие типографической шкалы.
Использование Placeholder вместо Label.
Слишком маленький текст.
Недостаточный контраст.
Слишком длинные строки.
Слишком плотный межстрочный интервал.
Отсутствие адаптации под мобильные устройства.
Нарушение визуальной иерархии.

## 19.18 Typography QA Checklist
Перед выпуском интерфейса необходимо проверить:
соблюдение типографической шкалы;
корректность ролей текста;
читаемость на всех разрешениях;
соответствие Design Tokens;
отсутствие произвольных размеров;
соответствие Accessibility;
корректность локализации;
отсутствие переполнений и обрезки текста.

## Глава 20. Color System

## 20.1 Назначение цветовой системы
Цветовая система (Color System) — это стандартизированный набор цветов, правил их применения и взаимосвязей, обеспечивающий единообразие интерфейсов, поддержку бренда, визуальную иерархию и доступность.
В eCommerce цвет выполняет не декоративную функцию, а служит средством передачи информации, формирования доверия и управления вниманием пользователя.
Каждый цвет в интерфейсе должен иметь функциональное назначение.
Если цвет используется исключительно для украшения, необходимость его применения должна быть обоснована.

## 20.2 Цели Color System
Цветовая система должна обеспечивать:
единообразие интерфейсов;
поддержку брендинга;
формирование визуальной иерархии;
быстрое распознавание состояний;
поддержку Accessibility;
масштабируемость;
поддержку различных тем оформления;
совместимость с Design Tokens.

## 20.3 Архитектура Color System
Рекомендуемая архитектура состоит из четырех уровней.
Primitive Colors
↓
Semantic Colors
↓
Component Colors
↓
Product Theme
Каждый последующий уровень зависит только от предыдущего.

## 20.4 Primitive Colors
Primitive Colors представляют собой базовую палитру.
Например.
Blue 50
Blue 100
Blue 200
Blue 300
Blue 400
Blue 500
Blue 600
Blue 700
Blue 800
Blue 900
Аналогичные шкалы создаются для:
Gray.
Green.
Red.
Orange.
Yellow.
Purple.
Teal.
Primitive Colors никогда не используются напрямую в интерфейсе.

## 20.5 Semantic Colors
Интерфейс должен использовать семантические цвета.
Например.
Primary.
Secondary.
Success.
Error.
Warning.
Info.
Accent.
Disabled.
Border.
Background.
Surface.
Text.
Link.
Semantic Colors позволяют менять фирменную палитру без изменения компонентов.

## 20.6 Design Tokens
Цвета должны использоваться исключительно через токены.
Например.
Color.Primary
Color.Primary.Hover
Color.Primary.Active
Color.Secondary
Color.Background
Color.Surface
Color.Error
Color.Success
Color.Warning
Color.Link
Использование HEX-кодов непосредственно в макетах запрещается.

## 20.7 Цветовые роли
Каждый цвет имеет строго определённую функцию.

### Primary
Главное действие.
Основная CTA.
Активные элементы.

### Secondary
Второстепенные действия.

### Success
Успешное выполнение операции.
Например.
Заказ оформлен.
Оплата выполнена.

### Warning
Предупреждение.
Например.
Заканчивается товар.

### Error
Ошибка.
Например.
Не удалось выполнить оплату.

### Info
Информационные сообщения.

### Neutral
Фоновая информация.
Текст.
Границы.
Контейнеры.

## 20.8 Цвет и визуальная иерархия
Цвет является одним из инструментов формирования приоритетов.
Рекомендуется использовать принцип:
Primary Action
↓
Secondary Action
↓
Passive Elements
↓
Decorative Elements
Количество акцентных цветов должно быть минимальным.

## 20.9 Цветовая система кнопок
Каждая кнопка должна иметь фиксированный цветовой сценарий.
Например.
Primary.
↓
Основной фирменный цвет.
Secondary.
↓
Нейтральный цвет.
Ghost.
↓
Прозрачный фон.
Danger.
↓
Красный.
Success.
↓
Зелёный.
Использование случайных цветов недопустимо.

## 20.10 Состояния компонентов
Каждый компонент должен иметь документированные состояния.
Например.
Button.
Default.
Hover.
Focus.
Pressed.
Disabled.
Loading.
Success.
Error.
Все состояния используют Design Tokens.

## 20.11 Контраст
Контраст обеспечивает читаемость интерфейса.
Проверяется:
Текст ↔ Фон.
Иконка ↔ Фон.
Border ↔ Surface.
Button ↔ Background.
Badge ↔ Background.
Контраст должен соответствовать требованиям WCAG.

## 20.12 Цвет и эмоции
Хотя восприятие цвета зависит от культуры и контекста, в eCommerce обычно используются следующие ассоциации:

| Цвет | Частые ассоциации |
| --- | --- |
| Синий | Надёжность, стабильность, безопасность |
| Зелёный | Подтверждение, экологичность, успех |
| Красный | Ошибка, срочность, акция |
| Оранжевый | Активность, внимание |
| Жёлтый | Предупреждение, новинка |
| Фиолетовый | Премиальность, креативность |
| Серый | Нейтральность, второстепенная информация |

Цвет не должен использоваться как единственный способ передачи смысла.

## 20.13 Цвет в карточке товара
Рекомендуется использовать цветовые акценты только для действительно важных элементов.
Например.
Цена.
Скидка.
CTA.
Статус наличия.
Badges.
Отзывы.
Все остальные элементы должны иметь нейтральное оформление.

## 20.14 Цвет и скидки
Акционные элементы требуют единообразной системы.
Например.
Старая цена.
↓
Серый.
↓
Перечёркнутый текст.
Новая цена.
↓
Высокий контраст.
Размер скидки.
↓
Badge.
Акция.
↓
Отдельный Accent.
Пользователь должен мгновенно различать обычную цену и акционное предложение.

## 20.15 Dark Mode
Если продукт поддерживает тёмную тему, необходимо определить:
палитру Surface;
палитру Background;
текст;
состояния;
изображения;
иллюстрации;
иконки.
Нельзя получать Dark Mode простым инвертированием цветов.

## 20.16 Brand Colors
Фирменные цвета используются ограниченно.
Основные области применения:
логотип;
Primary CTA;
акцентные элементы;
навигация;
маркетинговые блоки.
Не рекомендуется окрашивать весь интерфейс в фирменный цвет.

## 20.17 Цвет и Accessibility
Цвет не должен быть единственным способом передачи информации.
Например.
Неправильно.
Ошибка отображается только красным цветом.
Правильно.
Ошибка сопровождается:
иконкой;
цветом;
текстом.
Также проверяется восприятие интерфейса пользователями с различными формами нарушения цветового зрения.

## 20.18 Темизация
Color System должна поддерживать:
Light Theme;
Dark Theme;
White Label;
Multi Brand;
Seasonal Themes.
Все темы должны использовать единую систему токенов.

## 20.19 Проверка качества Color System
Перед выпуском интерфейса необходимо проверить:
отсутствие прямых HEX-значений;
использование только токенов;
достаточный контраст;
единое использование семантических цветов;
корректность состояний компонентов;
соответствие брендбуку;
поддержку всех тем оформления.

## 20.20 Типичные ошибки
Использование большого количества акцентных цветов.
Использование цвета как единственного способа передачи смысла.
Недостаточный контраст текста.
Прямое использование HEX-кодов.
Отсутствие семантических токенов.
Несогласованность между Figma и кодом.
Различные оттенки одного и того же цвета в разных компонентах.
Отсутствие Dark Mode.
Отсутствие проверки на дальтонизм.
Использование насыщенных цветов для больших областей интерфейса.

По результатам разработки должны быть подготовлены:

Semantic Color Tokens;
Theme Tokens;
Component Color Rules;
Dark Mode Specification;
Brand Color Guide;
Contrast Compliance Report;

Color Governance Guide;
Color QA Checklist.

### Следующая глава
Глава 21. UI Components Library станет одной из самых объёмных глав Playbook. Она будет представлять собой практически отдельный справочник, содержащий детальный разбор более 120 UI-компонентов (кнопки, поля ввода, карточки товаров, фильтры, модальные окна, навигация, уведомления, формы, рейтинги, бейджи, карусели, таблицы, аккордеоны и др.). Для каждого компонента будут описаны назначение, анатомия, состояния, варианты, UX-рекомендации, accessibility-требования, anti-patterns, аналитические события и чек-листы качества. Это станет основной библиотекой компонентов для всей дизайн-системы eCommerce.
