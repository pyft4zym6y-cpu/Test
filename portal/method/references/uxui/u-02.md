## Глава 5. User Personas

## 5.1 Назначение Personas
Persona — это исследовательская модель типичного представителя определённого сегмента пользователей, построенная на основе реальных данных, а не предположений команды.
Persona не является портретом конкретного человека.
Persona представляет собой модель поведения, отражающую:
цели;
мотивацию;
ограничения;
опыт;
критерии выбора;
процесс принятия решений;
предпочтительные способы взаимодействия с продуктом.
Основная задача Personas — помочь команде принимать решения с позиции пользователя, а не внутренних представлений бизнеса.

## 5.2 Зачем использовать Personas
При отсутствии Personas проектирование обычно строится вокруг внутренних представлений компании.
Например:
Пользователю будет удобно…
Пользователь наверняка понимает…
Пользователь обязательно воспользуется фильтрами…
Подобные утверждения не имеют ценности без исследовательского подтверждения.
Использование Personas позволяет заменить субъективные предположения конкретными моделями поведения.

## 5.3 Когда Personas необходимы
Создание Personas рекомендуется в следующих случаях:
разработка нового интернет-магазина;
полный редизайн;
выход на новый рынок;
запуск нового направления бизнеса;
запуск B2B-направления;
международная экспансия;
создание мобильного приложения;
запуск программы лояльности;
изменение ассортимента;
изменение структуры каталога.

## 5.4 Ограничения Personas
Persona не должна использоваться как абсолютная модель всех пользователей.
Недопустимо:
принимать решения исключительно на основании одной Persona;
создавать десятки Personas без различий;
использовать Personas без исследований;
использовать вымышленные характеристики.
Persona описывает закономерность поведения определённого сегмента пользователей.

## 5.5 Источники построения Personas
Основными источниками информации являются:

### UX Interviews
Позволяют определить:
мотивацию;
критерии выбора;
ожидания;
барьеры.

### Аналитика
Используется для определения:
популярных устройств;
сценариев поведения;
каналов привлечения;
глубины просмотра;
повторных визитов.

### Customer Support
Позволяет определить:
основные вопросы;
причины отказов;
причины возвратов;
непонятные функции.

### CRM
Источник информации о:
повторных покупках;
LTV;
среднем чеке;
жизненном цикле клиента.

### Маркетинговые исследования
Используются для:
сегментации аудитории;
анализа конкурентов;
оценки рынка.

## 5.6 Структура Persona
Каждая Persona должна содержать одинаковый набор разделов.

### Общая информация
название Persona;
сегмент;
описание.

### Демография
При необходимости:
возраст;
семейное положение;
профессия;
доход;
регион.
Следует использовать только характеристики, влияющие на принятие решений.

### Контекст использования
Необходимо определить:
устройство;
место использования;
время использования;
скорость интернета;
уровень цифровой грамотности.

### Цели
Что пользователь хочет получить?
Например:
быстро выбрать подарок;
найти минимальную цену;
купить оригинальный товар;
получить доставку сегодня.

### Мотивация
Почему пользователь покупает?
Например:
экономия времени;
престиж;
безопасность;
качество;
комфорт.

### Pain Points
Что мешает покупке?
Например:
сложная навигация;
отсутствие характеристик;
недостаток фотографий;
непонятная доставка;
недоверие.

### Критерии выбора
Что влияет на решение?
Например:
цена;
бренд;
наличие;
гарантия;
отзывы;
скорость доставки.

### Возражения
Почему пользователь может отказаться?
Например:
дорого;
нет отзывов;
неизвестный бренд;
длительная доставка;
сложный возврат.

### Любимые каналы
Откуда приходит пользователь?
Например:
Google;
Instagram;
TikTok;
YouTube;
Email;
Marketplace.

Пошаговое описание процесса покупки.

## 5.8 Количество Personas
Для большинства eCommerce-проектов достаточно:

#### Малый бизнес
2–4 Personas.

#### Средний бизнес
4–8 Personas.

#### Enterprise
8–15 Personas.
Создание большего количества Personas обычно приводит к дублированию информации.

## 5.9 Типичные ошибки
Создание Personas без исследований.
Использование вымышленных характеристик.
Фокус на возрасте вместо поведения.
Игнорирование бизнес-сегментов.
Создание слишком большого количества Personas.
Отсутствие связи Personas с Customer Journey.
Необновление Personas после изменения рынка.

## 5.10 Использование Personas в проектировании
Persona применяется практически на всех этапах разработки продукта.
При проектировании информационной архитектуры.
При разработке User Flow.
При создании Wireframes.
При подготовке Design System.
При разработке карточки товара.
При проектировании Checkout.
При разработке программы лояльности.
При UX Audit.
При проведении Usability Testing.
Каждое проектное решение должно сопровождаться вопросом:
Для какой Persona принимается данное решение и каким образом оно помогает ей достичь своей цели?
Если ответ отсутствует, решение требует дополнительного обоснования.

## Глава 6. Jobs To Be Done (JTBD)

## 6.1 Что такое Jobs To Be Done
Jobs To Be Done (JTBD) — методология исследования пользователей, рассматривающая покупку не как выбор товара, а как попытку решить определённую жизненную задачу.
Основной принцип JTBD:
Пользователь не покупает товар. Он «нанимает» его для выполнения определённой работы (Job).
Покупатель приобретает не дрель.
Он покупает возможность сделать отверстие.
Не матрас.
А качественный сон.
Не плед.
А ощущение тепла и домашнего комфорта.
Не CRM.
А управляемый процесс продаж.

## 6.2 Почему JTBD важнее классической сегментации
Традиционная сегментация отвечает на вопрос:
Кто покупает?
JTBD отвечает на вопрос:
Почему совершается покупка?
Возраст.
Пол.
Доход.
Город.
Должность.
Очень часто практически не объясняют причины выбора.
Два человека одного возраста могут покупать один и тот же товар совершенно по разным причинам.
Следовательно, интерфейс должен помогать решать задачу пользователя, а не обращаться к его возрастной группе.

## 6.3 Основные принципы JTBD

### Пользователь покупает прогресс
Любая покупка является попыткой перейти из текущего состояния в желаемое.
Например.
Сейчас:
Старый ноутбук тормозит.
Желаемое состояние:
Работа без ожидания.
Покупается не ноутбук.
Покупается повышение производительности.

### Пользователь меняет одно решение на другое
Конкурентом является не только другой интернет-магазин.
Конкурентом может быть:
старая вещь;
аренда;
самостоятельное изготовление;
откладывание покупки;
отказ от покупки вообще.

### Решение принимается в контексте
Один и тот же товар может выполнять разные Jobs.
Например.
Плед.
Job №1
Подарок.
Job №2
Украшение интерьера.
Job №3
Домашний комфорт.
Job №4
Использование на природе.
Интерфейс должен учитывать все основные сценарии использования.

## 6.4 Структура Job
Каждый Job состоит из нескольких компонентов.

### Functional Job
Что необходимо сделать?
Например.
Купить зимнюю куртку.

### Emotional Job
Что хочет чувствовать пользователь?
Например.
Уверенность.
Спокойствие.
Безопасность.
Комфорт.

### Social Job
Как пользователь хочет выглядеть в глазах окружающих?
Например.
Современным.
Профессиональным.
Заботливым.
Статусным.

## 6.5 Forces Diagram
Любое решение о покупке является результатом действия четырех сил.

### Push
Что заставляет искать новое решение?
Например.
Сломалась техника.

### Pull
Что привлекает в новом решении?
Например.
Новая функциональность.

### Anxiety
Что вызывает сомнения?
Например.
Высокая цена.
Неизвестный бренд.

### Habit
Что удерживает от изменений?
Например.
Привычный магазин.
Известный бренд.
Привычная модель.
Во время проектирования интерфейса необходимо уменьшать Anxiety и Habit.
Одновременно усиливать Pull.

## 6.6 Job Stories
Вместо User Stories рекомендуется использовать Job Stories.
Классическая структура.
Когда…
…
Я хочу…
…
Чтобы…
…
Пример.
Когда
я выбираю подарок коллеге,
Я хочу
быстро подобрать готовое решение,
Чтобы
не тратить несколько часов на поиск.
Другой пример.
Когда
я впервые покупаю дорогостоящую технику,
Я хочу
получить максимум информации,
Чтобы
быть уверенным в правильности выбора.

## 6.7 Job Map
Любой Job состоит из последовательности этапов.
Полная структура включает восемь шагов.

### Define
Осознание задачи.
Например.
Необходимо купить новый холодильник.

### Locate
Поиск возможных решений.
Google.
Marketplace.
Рекомендации.

### Prepare
Подготовка.
Сравнение.
Изучение рынка.
Определение бюджета.

### Confirm
Проверка вариантов.
Отзывы.
Видео.
Обзоры.
Характеристики.

### Execute
Покупка.

### Monitor
Отслеживание.
Статус заказа.
Доставка.

### Modify
Изменение решения.
Обмен.
Возврат.
Изменение заказа.

### Conclude
Завершение процесса.
Получение товара.
Оценка покупки.
Повторная покупка.

## 6.8 JTBD и проектирование интернет-магазина
Каждый раздел сайта должен помогать пользователю выполнять Job.

### Главная страница
Помогает понять:
Подходит ли магазин.

### Каталог
Помогает быстро найти направление поиска.

### Фильтрация
Помогает сократить количество вариантов.

### Карточка товара
Помогает принять решение.

### Корзина
Помогает проверить правильность выбора.

### Checkout
Помогает завершить покупку.

### Личный кабинет
Помогает управлять дальнейшим взаимодействием.

## 6.9 JTBD и карточка товара
Карточка должна отвечать на вопросы пользователя именно в том порядке, в котором возникают Jobs.
Например.
Это тот товар?
↓
Подойдет ли он мне?
↓
Можно ли доверять?
↓
Есть ли реальные фотографии?
↓
Есть ли отзывы?
↓
Какие гарантии?
↓
Когда доставят?
↓
Можно ли вернуть?
↓
Стоит ли покупать именно здесь?
Именно последовательность появления информации влияет на скорость принятия решения.

## 6.10 JTBD и навигация
Ошибкой является построение структуры сайта исключительно вокруг ассортимента компании.
Правильная структура должна учитывать задачи пользователей.
Например.
Неправильно:
Каталог
↓
Материалы
↓
Типы
↓
Коллекции
↓
Артикулы
Правильно:
Для дома.
Для офиса.
Для детей.
Для подарка.
Новинки.
Хиты продаж.
Решения по задачам зачастую оказываются более понятными пользователю, чем внутренняя классификация компании.

## 6.11 JTBD и поиск
Поисковая система должна учитывать намерение пользователя.
Запрос:
«Подарок жене»
не обязательно означает поиск товара с таким названием.
Он означает Job.
Следовательно, поиск должен учитывать:
категории;
сценарии использования;
события;
праздники;
поводы;
сегменты пользователей.

## 6.12 JTBD и UX Audit
Во время UX Audit необходимо оценивать не страницы, а успешность выполнения Jobs.
Для каждого основного Job анализируются:
количество шагов;
количество препятствий;
моменты неопределенности;
вероятность ошибок;
вероятность отказа;
скорость достижения результата.
Основной показатель качества UX — не количество элементов интерфейса, а доля пользователей, успешно завершающих свой Job.

## 6.13 Типичные ошибки
Проектирование вокруг структуры компании.
Игнорирование эмоциональных Jobs.
Фокус исключительно на функциональности.
Путаница между товаром и задачей.
Использование демографической сегментации вместо поведенческой.
Построение навигации вокруг внутренних бизнес-процессов.
Разработка карточек товара без учета последовательности возникновения вопросов пользователя.

По результатам JTBD должны быть подготовлены следующие артефакты:

Job Statements;
Job Stories;
Functional Jobs Matrix;
Emotional Jobs Matrix;
Social Jobs Matrix;

## Глава 7. Customer Journey Map (CJM)

## 7.1 Назначение Customer Journey Map
Customer Journey Map (CJM) — это модель полного пути клиента от момента возникновения потребности до повторной покупки и формирования долгосрочных отношений с брендом.
В отличие от User Flow, который описывает взаимодействие с интерфейсом, CJM рассматривает весь клиентский опыт, включая точки контакта, эмоции, ожидания, барьеры и процессы, происходящие вне сайта.
Цель CJM — выявить причины, по которым пользователь прекращает движение к покупке, и определить возможности для улучшения пользовательского опыта.

## 7.2 Основные отличия CJM

| Инструмент | Что описывает |
| --- | --- |
| Persona | Кто пользователь |
| JTBD | Какую задачу он пытается решить |
| User Flow | Как пользователь взаимодействует с интерфейсом |
| Task Flow | Последовательность выполнения одной задачи |
| Customer Journey Map | Полный жизненный цикл клиента |


## 7.3 Принципы построения CJM
Customer Journey строится вокруг действий пользователя, а не процессов компании.
Нельзя начинать карту с момента открытия сайта.
Путь клиента начинается значительно раньше.
Например:
Возникла проблема
↓
Осознание потребности
↓
Поиск вариантов
↓
Сравнение магазинов
↓
Первое посещение сайта
↓
Выбор товара
↓
Покупка
↓
Получение заказа
↓
Использование товара
↓
Повторная покупка
↓
Рекомендация другим пользователям

Самый короткий, но наиболее чувствительный этап.

простое заполнение форм.

### Stage 5. Delivery
После оплаты пользователь продолжает взаимодействовать с компанией.

контакт с поддержкой.

### Stage 6. Usage
Пользователь начинает использовать товар.

Компания должна обеспечить:

поддержку;
обучающие материалы;
контент.

### Stage 7. Loyalty
Формируются повторные покупки.
Используются:

рекомендации;
бонусная программа;
email-маркетинг;
мобильное приложение.

### Stage 8. Advocacy
Пользователь становится адвокатом бренда.
Формируется:
повторное взаимодействие;
отзывы;
UGC;
реферальная программа;
социальные рекомендации.

## Глава 8. Experience Map

## 8.1 Назначение Experience Map
Experience Map (карта пользовательского опыта) — инструмент системного анализа полного опыта взаимодействия человека с определённой задачей независимо от конкретного продукта, бренда или канала.
В отличие от Customer Journey Map, которая описывает взаимодействие клиента с конкретной компанией, Experience Map рассматривает весь жизненный контекст пользователя.
Основная цель Experience Map — понять поведение человека ещё до того, как он становится клиентом.

## 8.2 Отличия Experience Map от Customer Journey Map

| Experience Map | Customer Journey Map |
| --- | --- |
| Описывает опыт человека | Описывает опыт клиента |
| Не зависит от бренда | Связана с конкретной компанией |
| Начинается до поиска решения | Обычно начинается с взаимодействия с брендом |
| Используется для поиска новых возможностей | Используется для оптимизации существующего опыта |
| Помогает находить новые продукты | Помогает улучшать существующие процессы |


## 8.3 Когда использовать Experience Map
Experience Map рекомендуется создавать при:
запуске нового направления бизнеса;
разработке нового интернет-магазина;
выходе на новый рынок;
проектировании новых сервисов;
расширении ассортимента;
поиске новых точек роста;
проведении Discovery.

## 8.4 Структура Experience Map
Каждая карта строится по единому шаблону.

### Контекст
В каком жизненном контексте находится человек?
Например:
Переезд.
Рождение ребёнка.
Начало ремонта.
Подготовка к путешествию.
Покупка автомобиля.

### Цель
Какого результата человек хочет достичь?
Необходимо описывать конечный результат, а не действие.
Например:
Создать комфортный домашний кабинет.
А не:
Купить стол.

### Последовательность действий
Полный путь пользователя.
Например.
Появилась идея
↓
Поиск информации
↓

↓
Поиск вариантов
↓
Сравнение решений
↓
Покупка
↓
Использование
↓
Оценка результата

### Мысли
Какие вопросы возникают?
Например.
Как выбрать?
Какой бренд лучше?
Можно ли доверять магазину?
Стоит ли переплачивать?

### Эмоции
Какие эмоции сопровождают каждый этап?
Необходимо фиксировать:
интерес;
сомнения;
тревогу;
радость;
разочарование.

### Барьеры
Что мешает двигаться дальше?
Например.
Недостаток информации.
Высокая цена.
Большой выбор.
Недоверие.
Сложность доставки.

### Возможности
Каким образом можно улучшить пользовательский опыт?

## 8.9 Отличие Experience Map от User Flow
Experience Map отвечает на вопрос:

## Глава 9. User Flow

## 9.1 Что такое User Flow
User Flow — это формализованная модель последовательности действий пользователя внутри цифрового продукта, направленная на достижение конкретной цели.
User Flow описывает:
действия пользователя;
точки принятия решений;
варианты развития сценариев;
переходы между экранами;
условия выполнения сценария;
успешное завершение задачи;
возможные ошибки и возвраты.
User Flow является одним из основных артефактов UX-проектирования и создаётся до разработки интерфейсов.

## 9.2 Основная задача User Flow
Главная задача User Flow — минимизировать количество действий, необходимых пользователю для достижения цели.
При проектировании оцениваются:
количество шагов;
количество решений;
вероятность ошибок;
вероятность выхода из сценария;
когнитивная нагрузка;
необходимость ввода данных;
количество переходов между страницами.

## 9.3 Когда разрабатывается User Flow
User Flow создаётся:
после UX Research;
после JTBD;
после построения Customer Journey;
после формирования Information Architecture.
Только после этого начинается разработка Wireframes.
Последовательность проектирования должна быть следующей:

↓

↓

↓

↓

↓

↓

↓

↓

## 9.4 Из чего состоит User Flow
Каждый User Flow должен содержать следующие элементы.

### Стартовая точка

Например:

### Действие

Например:

Использовал поиск.

### Решение

Да

Нет
↓

### Экран
Каждый шаг должен соответствовать конкретному экрану или состоянию интерфейса.

### Конечная цель
Например.

Регистрация завершена.
Подписка оформлена.
Возврат создан.

## 9.5 Типы User Flow

### Linear Flow
Самый простой вариант.
Пользователь проходит сценарий без альтернативных путей.
Используется:
регистрация;
подписка;
онбординг.

### Branch Flow
Наиболее распространённый вариант.
Содержит множество решений.
Например.
Выбор способа доставки.
Выбор оплаты.
Выбор варианта товара.

### Conditional Flow
Следующий экран зависит от условий.
Например.

Да
↓
Checkout
Нет
↓
Авторизация

### Loop Flow
Пользователь может неоднократно возвращаться на предыдущие этапы.
Например.
Каталог
↓
Карточка
↓
Каталог
↓
Карточка
↓
Сравнение
↓
Каталог
Для eCommerce именно Loop Flow является наиболее типичным.

### Связь с последующими главами
User Flow определяет последовательность взаимодействия между экранами, но ещё не описывает детальные действия внутри каждого шага. Следующая глава — Task Flow — будет посвящена микроуровню взаимодействия: выполнению одной конкретной задачи (например, применению фильтра, оформлению заказа, поиску товара или сравнению продуктов). Именно Task Flow становится основой для проектирования Wireframes и детальной проработки интерфейсов.
