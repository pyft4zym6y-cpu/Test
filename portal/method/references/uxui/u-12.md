## Глава 40. Design Systems & Enterprise UI Governance

## 40.1 Почему Design System критична для eCommerce
На ранних этапах интернет-магазин может существовать без полноценной дизайн-системы.
Однако при росте продукта появляются десятки проблем:
различные стили кнопок;
разные карточки товаров;
несовместимые формы;
противоречивые паттерны;
разные состояния компонентов;
рост стоимости разработки;
снижение скорости выпуска новых функций.
Design System превращает интерфейс из набора отдельных экранов в единую масштабируемую систему.

## 40.2 Что такое Design System
Design System — это не UI Kit.
Это совокупность:
Design Principles
↓
Design Tokens
↓
Foundations
↓
Components
↓
Patterns
↓
Templates
↓
Documentation
↓
Governance
↓
DesignOps
Все уровни взаимосвязаны.

## 40.3 Цели Design System
Хорошая дизайн-система должна:
обеспечить единообразие интерфейса;
ускорить проектирование;
ускорить разработку;
снизить количество UI-ошибок;
повысить качество UX;
уменьшить стоимость сопровождения;
обеспечить масштабирование продукта.

## 40.25 Enterprise Maturity Model

| Уровень | Характеристика |
| --- | --- |
| Level 1 | Разрозненные UI-компоненты без единых стандартов |
| Level 2 | UI Kit и базовая библиотека компонентов |
| Level 3 | Полноценная Design System с токенами, документацией и Storybook |
| Level 4 | DesignOps, автоматизированная синхронизация Design ↔ Code, централизованное управление |
| Level 5 | Enterprise Design Platform с токенами, мультибрендовой поддержкой, AI-ассистентами и автоматическим контролем качества |

Несогласованность между Figma и кодом.
Отсутствие документации.

Игнорирование Accessibility.
Разработка новых компонентов вместо повторного использования существующих.
Отсутствие процесса версионирования.

## Глава 41. Accessibility (WCAG) & Inclusive Design

## 41.1 Почему Accessibility — это обязательное требование
Accessibility — это способность цифрового продукта быть доступным для максимально широкого круга пользователей независимо от их физических, сенсорных, когнитивных или временных ограничений.
Для eCommerce доступность влияет не только на соответствие требованиям законодательства, но и на:
Conversion Rate;
Customer Satisfaction;
SEO;
Retention;
Brand Trust.
Доступность должна проектироваться с первого дня разработки продукта.

## 41.2 Inclusive Design
Inclusive Design значительно шире Accessibility.
Accessibility отвечает на вопрос:
Может ли пользователь пользоваться системой?
Inclusive Design отвечает на вопрос:
Насколько комфортно пользователь может пользоваться системой?
Интерфейс должен учитывать максимально широкий спектр пользователей.
Например:
нарушения зрения;
нарушения слуха;
моторные ограничения;
когнитивные особенности;
возрастные изменения;
временные ограничения (например, использование одной рукой).

## 41.3 Принципы WCAG
В основе WCAG лежат четыре принципа.
Perceivable
↓
Operable
↓
Understandable
↓
Robust
Любое нарушение хотя бы одного принципа ухудшает доступность продукта.

## 41.4 Perceivable (Воспринимаемость)
Пользователь должен иметь возможность воспринимать информацию.
Необходимо обеспечить:
альтернативный текст для изображений;
субтитры для видео;
достаточный контраст;
масштабирование текста;
визуальные подсказки.
Информация не должна передаваться исключительно цветом.

## 41.5 Operable (Управляемость)
Все элементы интерфейса должны быть доступны без использования мыши.
Поддерживаются:
клавиатурная навигация;
логичный порядок Tab;
видимый Focus;
отсутствие Keyboard Trap;
возможность пропустить повторяющиеся блоки.

## 41.6 Understandable (Понятность)
Интерфейс должен быть предсказуемым.
Необходимо:
использовать понятные названия;
избегать неоднозначных терминов;
одинаково оформлять одинаковые действия;
заранее предупреждать о последствиях важных операций.

## 41.7 Robust (Надёжность)
Интерфейс должен корректно работать:
со Screen Readers;
с различными браузерами;
с Assistive Technologies;
с будущими версиями технологий.
Использование стандартных HTML-элементов предпочтительнее самописных компонентов без необходимости.

## 41.8 Контрастность
Минимальные требования.
Обычный текст.
Минимальный коэффициент контрастности — 4.5:1.
Крупный текст.
Минимум — 3:1.
Не рекомендуется использовать светло-серый текст на белом фоне.

## 41.9 Typography
Рекомендуется:
минимальный читаемый размер текста;
достаточный межстрочный интервал;
ограниченная длина строки;
возможность масштабирования без потери функциональности.
Текст должен оставаться читаемым при увеличении масштаба.

## 41.10 Keyboard Navigation
Пользователь должен иметь возможность выполнить все основные действия только клавиатурой.
Например.
Tab
↓
Shift + Tab
↓
Enter
↓
Space
↓
Esc
↓
Arrow Keys
Нельзя блокировать стандартное поведение клавиатуры без объективной причины.

## 41.11 Focus Management
Каждый интерактивный элемент должен иметь:
видимый Focus;
логичный порядок;
сохранение фокуса после действий;
корректный возврат после закрытия модальных окон.
Пользователь никогда не должен терять текущую позицию.

## 41.12 Forms Accessibility
Все формы должны содержать:
Label.
↓
Helper Text.
↓
Error Message.
↓
ARIA Description.
↓
Autocomplete.
↓
Required Indicator.
Placeholder не заменяет Label.

## 41.13 Images
Все изображения подразделяются.
Информативные.
↓
ALT обязателен.
Декоративные.
↓
ALT пустой.
Не следует использовать одинаковый ALT для всех изображений.

## 41.14 Icons
Если иконка несёт смысл, она должна иметь текстовое описание.
Например.
Удалить.
Поиск.
Избранное.
Корзина.
Иконка без подписи допустима только при очевидном контексте.

## 41.15 Tables
Таблицы должны содержать:
заголовки;
структурированные строки;
корректную разметку;
логичный порядок чтения.
Таблицы не должны использоваться исключительно для построения макета страницы.

## 41.16 Modals
Модальные окна должны:
получать Focus после открытия;
блокировать фон;
закрываться клавишей Esc;
возвращать Focus в исходный элемент после закрытия.

## 41.17 Notifications
Все уведомления должны быть доступны для Screen Reader.
Например.
Ошибка.
↓
Успех.
↓
Предупреждение.
↓
Информационное сообщение.

## 41.18 Screen Readers
Интерфейс необходимо тестировать с использованием Screen Reader.
Проверяются:
структура документа;
порядок чтения;
названия элементов;
ARIA Labels;
ARIA Live Regions.

## 41.19 Mobile Accessibility
Особенности мобильных устройств.
Размер зоны касания.
Минимум 44×44 px.
Поддержка VoiceOver.
Поддержка TalkBack.
Корректная работа при увеличенном размере шрифта.

## 41.20 Accessibility для PDP
Карточка товара должна поддерживать:
альтернативный текст изображений;
описание видео;
доступность галереи с клавиатуры;
понятные характеристики;
корректную работу выбора вариантов.

## 41.21 Accessibility для Checkout
Checkout требует особого внимания.
Необходимо обеспечить:
логичный порядок полей;
понятные ошибки;
автоматическое перемещение Focus к ошибке;
работу Autofill;
совместимость с Screen Readers.

## 41.22 Accessibility Testing
Проверка включает:
ручное тестирование;
автоматическое сканирование;
клавиатурную навигацию;
Screen Reader;
проверку контрастности;
проверку масштабирования;
тестирование на мобильных устройствах.
Автоматические инструменты выявляют только часть возможных проблем.

## 41.23 Accessibility Governance
В компании должны быть определены:
стандарты разработки;
чек-листы;
обязательные проверки;
владельцы процесса;
обучение команды;
регулярные аудиты.
Accessibility не должна зависеть только от энтузиазма отдельных сотрудников.

## 41.24 Analytics
Рекомендуется отслеживать:
использование клавиатурной навигации;
увеличение масштаба;
использование режима высокой контрастности (если доступно);
ошибки доступности;
успешность выполнения ключевых сценариев пользователями вспомогательных технологий (при наличии специализированных исследований).
При этом необходимо соблюдать требования конфиденциальности и не собирать чувствительные данные о состоянии здоровья пользователей.

## 41.25 KPI Accessibility

| KPI | Назначение |
| --- | --- |
| WCAG Compliance Score | Соответствие требованиям WCAG |
| Accessibility Defects | Количество выявленных проблем |
| Keyboard Success Rate | Успешность сценариев без мыши |
| Screen Reader Compatibility | Совместимость со Screen Reader |
| Contrast Compliance | Соответствие требованиям контрастности |
| Accessibility Issue Resolution Time | Скорость устранения проблем |
| Accessibility Audit Score | Результат регулярного аудита |
| Accessible Component Coverage | Доля компонентов, соответствующих стандартам доступности |


## 41.26 Типичные ошибки
Использование Placeholder вместо Label.
Недостаточный контраст текста.
Отсутствие видимого Focus.
Невозможность работы с клавиатуры.
Неправильное использование ARIA.
Отсутствие ALT у изображений.
Использование цвета как единственного способа передачи информации.
Слишком маленькие зоны касания.
Неправильный порядок Tab.
Игнорирование тестирования со Screen Reader.

## 41.27 Accessibility QA Checklist
Перед выпуском необходимо проверить:
все интерактивные элементы доступны с клавиатуры;
Focus отображается корректно;
изображения имеют корректные ALT;
формы содержат Label и понятные сообщения об ошибках;
контрастность соответствует требованиям WCAG;
модальные окна правильно управляют Focus;
интерфейс протестирован с использованием Screen Reader;
поддерживается масштабирование текста;
Accessibility-аудит успешно пройден;
требования законодательства целевых рынков соблюдены.

## Глава 42. Performance Engineering & Core Web Vitals

## 42.1 Производительность как фактор прибыли
Производительность (Performance) — это способность eCommerce-платформы быстро реагировать на действия пользователя, минимизируя задержки при загрузке страниц, взаимодействии с интерфейсом и выполнении операций.
Для интернет-магазина производительность напрямую влияет на:
Conversion Rate;
Bounce Rate;
Average Order Value;
SEO;
Customer Satisfaction;
Revenue.
Каждая лишняя задержка увеличивает вероятность потери пользователя.
Производительность должна рассматриваться как часть пользовательского опыта, а не только как техническая задача.

## 42.3 Core Web Vitals
Core Web Vitals — ключевые пользовательские метрики производительности.
В настоящее время основными являются:
LCP (Largest Contentful Paint);
INP (Interaction to Next Paint);
CLS (Cumulative Layout Shift).
Они отражают восприятие скорости пользователем.

## 42.4 Largest Contentful Paint (LCP)
LCP измеряет время загрузки крупнейшего видимого элемента страницы.
Для eCommerce это обычно:
Hero Banner;
главное изображение товара;
основной заголовок;
первый блок каталога.
Целевое значение:
≤ 2.5 секунды
Основные способы улучшения:
оптимизация изображений;
CDN;
Server Side Rendering;
preload критических ресурсов;
уменьшение времени ответа сервера.

## 42.5 Interaction to Next Paint (INP)
INP измеряет скорость реакции интерфейса на действия пользователя.
Например:
клик;
выбор фильтра;
Add to Cart;
открытие меню;
изменение количества товара.
Целевое значение:
≤ 200 мс
Причины ухудшения:
тяжёлый JavaScript;
длительные вычисления;
блокировка главного потока;
сложные обработчики событий.

## 42.6 Cumulative Layout Shift (CLS)
CLS измеряет неожиданное смещение элементов интерфейса.
Например:
кнопка “Купить” сместилась после загрузки изображения;
баннер появился позже и сдвинул контент вниз.
Целевое значение:
≤ 0.1
Причины:
изображения без фиксированных размеров;
динамические баннеры;
асинхронная реклама;
изменение размеров компонентов после загрузки.

## 42.7 Performance Budget
Для каждого проекта рекомендуется определить Performance Budget.
Например.
HTML.
≤ 100 KB
CSS.
≤ 200 KB
JavaScript.
≤ 300 KB
Hero Image.
≤ 250 KB
Fonts.
≤ 150 KB
Third-party Scripts.
≤ 250 KB
Performance Budget позволяет контролировать рост технического долга.

## 42.8 Rendering Strategies
Современный eCommerce использует несколько стратегий рендеринга.

### CSR
Client Side Rendering.
Преимущества:
простота разработки.
Недостатки:
долгая первая загрузка.

### SSR
Server Side Rendering.
Преимущества:
быстрый First Paint;
лучшее SEO.
Недостатки:
увеличение нагрузки на сервер.

### SSG
Static Site Generation.
Подходит для:
контентных страниц;
категорий с редкими изменениями.

### ISR
Incremental Static Regeneration.
Позволяет обновлять страницы постепенно без полной пересборки проекта.
Особенно эффективен для крупных каталогов.

## 42.9 Image Optimization
Изображения являются крупнейшим источником нагрузки.
Рекомендуется:
современные форматы (AVIF, WebP при наличии поддержки);
адаптивные размеры;
Lazy Loading для некритичных изображений;
preload первого изображения;
CDN;
автоматическое сжатие.

## 42.10 Font Optimization
Шрифты должны:
загружаться быстро;
использовать ограниченное количество начертаний;
поддерживать font-display: swap;
предварительно загружаться только при необходимости.

## 42.11 CSS Optimization
Рекомендуется:
удалять неиспользуемые стили;
разделять критический и некритический CSS;
минимизировать файлы;
использовать кэширование.

## 42.12 JavaScript Optimization
JavaScript чаще всего становится главным источником задержек.
Рекомендуется:
Code Splitting.
↓
Tree Shaking.
↓
Lazy Loading.
↓
Dynamic Import.
↓
Минификация.
↓
Удаление неиспользуемых библиотек.
↓
Оптимизация Third-party Scripts.

## 42.13 API Performance
API должны обеспечивать:
минимальное время ответа;
сжатие данных;
кэширование;
пагинацию;
частичную загрузку данных;
устойчивость к высоким нагрузкам.

## 42.14 Database Performance
Для каталога eCommerce особенно важны:
индексация;
оптимизация SQL-запросов;
кэширование результатов;
репликация;
оптимизация полнотекстового поиска.

## 42.15 CDN
Content Delivery Network позволяет:
уменьшить задержку;
распределить нагрузку;
ускорить загрузку изображений;
ускорить доставку JavaScript и CSS.
CDN рекомендуется использовать для всех публичных ресурсов.

## 42.16 Caching Strategy
Используются несколько уровней кэширования.
Browser Cache
↓
CDN Cache
↓
Application Cache
↓
Database Cache
Стратегия должна учитывать актуальность данных и частоту их изменения.

## 42.17 Lazy Loading
Lazy Loading применяется для:
изображений вне первого экрана;
видео;
второстепенных блоков;
рекомендаций;
отзывов.
Первый экран не должен зависеть от Lazy Loading.

## 42.18 Skeleton Screens
Вместо Spinner рекомендуется использовать Skeleton.
Skeleton:
сохраняет структуру страницы;
уменьшает ощущение ожидания;
снижает вероятность отказа.

## 42.19 Third-party Scripts
Необходимо регулярно анализировать влияние сторонних сервисов.
Например:
аналитика;
онлайн-чаты;
пиксели рекламы;
виджеты отзывов;
A/B-платформы.
Каждый дополнительный скрипт увеличивает время загрузки.

## 42.20 Real User Monitoring (RUM)
RUM измеряет производительность на устройствах реальных пользователей.
Отслеживаются:
LCP;
INP;
CLS;
время загрузки;
ошибки JavaScript;
скорость API.
RUM показывает реальные условия эксплуатации.

## 42.21 Synthetic Monitoring
Synthetic Monitoring выполняет автоматические проверки по заранее заданным сценариям.
Например:
Главная.
↓
Категория.
↓
Карточка товара.
↓
Checkout.
↓
Оплата.
Позволяет обнаруживать проблемы до появления жалоб пользователей.

## 42.22 Analytics
Необходимо отслеживать:
Core Web Vitals;
Time to First Byte (TTFB);
First Contentful Paint (FCP);
Speed Index;
JavaScript Errors;
API Response Time;
Cache Hit Rate;
CDN Hit Rate;
Page Weight;
Third-party Script Load Time.

| KPI | Назначение |
| --- | --- |
| LCP | Скорость отображения основного контента |
| INP | Скорость реакции интерфейса |
| CLS | Стабильность макета |
| TTFB | Время ответа сервера |
| API Response Time | Скорость API |
| Cache Hit Rate | Эффективность кэширования |

| Average Page Weight | Средний вес страницы |

## 42.24 Типичные ошибки
Игнорирование Performance Budget.
Использование изображений большого размера.
Подключение десятков сторонних скриптов без оценки их влияния.
Отсутствие CDN.
Полная загрузка JavaScript при первом открытии страницы.
CLS из-за динамического контента.
Отсутствие кэширования.
Использование Spinner вместо Skeleton.
Отсутствие мониторинга производительности после релиза.

## 42.25 Performance QA Checklist
ДзеркалоПеред выпуском необходимо проверить:
Core Web Vitals соответствуют целевым значениям;
Performance Budget соблюдён;
изображения оптимизированы;
JavaScript разбит на чанки;
CSS минимизирован;
CDN используется для статических ресурсов;
кэширование настроено;
сторонние скрипты не блокируют загрузку;
RUM и Synthetic Monitoring настроены;
производительность протестирована на Desktop и Mobile.
