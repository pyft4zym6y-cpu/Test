## Глава 10. Task Flow

## 10.1 Что такое Task Flow
Task Flow — это модель выполнения одной конкретной пользовательской задачи внутри цифрового продукта.
В отличие от User Flow, который описывает полный путь пользователя через несколько экранов, Task Flow фокусируется исключительно на одной операции.
Примеры задач:
найти товар;
применить фильтр;
изменить количество товаров;
добавить товар в корзину;
оформить заказ;
авторизоваться;
оформить возврат;
оставить отзыв.
Task Flow отвечает на вопрос:
Какие действия должен выполнить пользователь, чтобы решить одну конкретную задачу?

## 10.2 Отличие Task Flow от User Flow

| User Flow | Task Flow |
| --- | --- |
| Описывает полный путь пользователя | Описывает выполнение одной задачи |
| Содержит множество сценариев | Один конкретный сценарий |
| Может включать десятки экранов | Обычно ограничен одной функцией |
| Используется на уровне продукта | Используется на уровне интерфейса |
| Определяет архитектуру взаимодействия | Определяет механику выполнения действия |

Например.
User Flow:
Главная → Категория → Карточка → Корзина → Checkout.
Task Flow:
Добавление товара в корзину.

## 10.3 Цели Task Flow
Каждый Task Flow должен обеспечивать:
минимальное количество действий;
отсутствие неопределённости;
понятную последовательность шагов;
минимальную когнитивную нагрузку;
возможность исправления ошибок;
быстрое завершение задачи.

## 10.4 Правила проектирования
Каждый Task Flow проектируется по единым принципам.

### Один Flow — одна задача
Нельзя объединять несколько различных действий в один Task Flow.
Например.
Неправильно:
Поиск товара + оформление заказа.
Правильно:
Task Flow №1
Поиск.
Task Flow №2
Добавление в корзину.
Task Flow №3
Checkout.

### Один основной сценарий
Для каждой задачи определяется основной путь.
После этого проектируются альтернативные сценарии.

### Минимизация шагов
Каждый дополнительный шаг должен быть обоснован.
При проектировании рекомендуется задавать вопрос:
Можно ли убрать данный шаг без потери функциональности?

### Минимизация решений
Каждое решение увеличивает когнитивную нагрузку.
Если выбор необязателен — его следует автоматизировать.

## 10.5 Структура Task Flow
Каждый Task Flow состоит из следующих элементов.

### Цель
Какую задачу решает пользователь?

### Предусловия
Что должно быть выполнено до начала?
Например.
Пользователь авторизован.
Или
Товар имеется в наличии.

### Основной сценарий
Пошаговое описание.

### Альтернативные сценарии
Например.
Ошибка.
Отмена.
Изменение выбора.
Возврат.

### Исключительные ситуации
Например.
Потеря соединения.
Ошибка оплаты.
Недоступный товар.

### Критерии успешного завершения
Как определить, что задача выполнена?

## 10.12 Проверка качества Task Flow
Каждый Flow оценивается по следующим параметрам.

#### Количество шагов
Чем меньше, тем лучше.

#### Количество экранов
Минимизировать переходы.

#### Количество обязательных полей
Уменьшать.

#### Количество решений
Минимизировать.

#### Вероятность ошибки
Каждая ошибка должна иметь понятное восстановление.

#### Время выполнения
Оптимизировать.

#### Уровень когнитивной нагрузки
Пользователь не должен одновременно анализировать большое количество информации.

## 10.13 Матрица оценки Task Flow
Каждый сценарий рекомендуется оценивать по следующим критериям:

| Критерий | Описание |
| --- | --- |
| Task Completion Rate | Процент пользователей, успешно завершивших задачу |
| Average Completion Time | Среднее время выполнения |
| Error Rate | Количество ошибок |
| Backtracking Rate | Частота возвратов на предыдущие шаги |
| Abandonment Rate | Процент незавершённых задач |
| Cognitive Load | Субъективная сложность выполнения |
| User Satisfaction | Оценка пользователем процесса |

Эти показатели позволяют сравнивать различные варианты реализации одной и той же функции.

## 10.14 Типичные ошибки
Проектирование только успешного сценария.
Игнорирование ошибок пользователя.
Отсутствие возможности отменить действие.
Избыточное количество обязательных полей.
Скрытые системные состояния.
Отсутствие обратной связи.
Невозможность вернуться на предыдущий шаг.
Автоматическое удаление введённых данных при ошибке.
Различное поведение одинаковых элементов в разных частях сайта.

## Глава 11. Information Architecture (IA)

## 11.1 Что такое Information Architecture
Information Architecture (IA) — это система организации, структурирования, классификации и взаимосвязи информации внутри цифрового продукта.
Для eCommerce информационная архитектура определяет:
структуру каталога;
дерево категорий;
принципы навигации;
внутренние взаимосвязи страниц;
логику поиска;
систему фильтрации;
структуру URL;
информационные модели страниц.
До начала проектирования любого интерфейса должна быть разработана IA.
Дизайн без информационной архитектуры приводит к хаотичной навигации, дублированию информации и росту технического долга.

## 11.2 Цели Information Architecture
Качественная IA должна обеспечивать:
быстрое нахождение информации;
предсказуемую навигацию;
минимальную глубину поиска;
масштабируемость каталога;
поддержку SEO;
поддержку фильтрации;
поддержку персонализации;
простоту сопровождения.

## 11.3 Принципы построения IA

### Принцип 1. От пользователя, а не от компании
Структура должна строиться вокруг пользовательской логики.
Неправильно:
Продукция
↓
Серия А
↓
Линейка Х
↓
Коллекция 2026
Правильно:
Для спальни
↓
Пледы
↓
Шерстяные
↓
200×220
Пользователь мыслит задачами, а не внутренней организационной структурой компании.

### Принцип 2. Взаимоисключающие категории
Каждый товар должен иметь очевидное место в структуре.
Если один товар одновременно подходит в несколько категорий, это решается через:
дополнительные категории;
фильтрацию;
теги;
рекомендации.
Не следует создавать дублирующие разделы.

### Принцип 3. Масштабируемость
Структура должна учитывать рост каталога.
Плохая архитектура работает при 500 товарах, но становится неуправляемой при 50 000 SKU.
Перед проектированием необходимо учитывать:
потенциальный рост ассортимента;
новые бренды;
новые рынки;
новые языки;
новые типы товаров.

### Принцип 4. Минимальная глубина
Любой товар должен быть доступен за минимальное количество переходов.
Рекомендуемая глубина:
Главная
↓
Категория
↓
Подкатегория
↓
Карточка
Чем больше уровней, тем выше вероятность потери пользователя.

### Принцип 5. Последовательность
Одинаковые сущности должны иметь одинаковую структуру.
Если один раздел использует фильтрацию слева, остальные категории также должны использовать аналогичную модель.

## 11.4 Основные элементы IA
Информационная архитектура интернет-магазина состоит из нескольких взаимосвязанных уровней.

### Глобальная навигация
Определяет основные разделы сайта.
Например:
Каталог
Акции
Новинки
Бренды
Доставка
Оплата
Блог
Контакты

### Каталог
Каталог является ядром IA.
Основные требования:
логичное деление;
отсутствие пересечений;
поддержка фильтрации;
поддержка SEO;
поддержка поиска.

### Категории
Категория объединяет товары по понятному пользователю признаку.
Категории должны быть:
взаимоисключающими;
понятными;
масштабируемыми;
устойчивыми во времени.

### Подкатегории
Используются только тогда, когда действительно упрощают навигацию.
Не рекомендуется создавать уровни вложенности без необходимости.

### Карточка товара
Конечная точка большинства пользовательских сценариев.
IA определяет:
состав блоков;
последовательность информации;
взаимосвязь с другими страницами.

## Глава 12. Navigation Design

## 12.1 Что такое Navigation Design
Navigation Design — это система проектирования пользовательских маршрутов внутри цифрового продукта, обеспечивающая быстрое, предсказуемое и интуитивное перемещение между разделами сайта.
Если Information Architecture отвечает на вопрос:
Как организована информация?
то Navigation Design отвечает:
Как пользователь будет перемещаться между этой информацией?
Навигация должна минимизировать время поиска, количество ошибок и когнитивную нагрузку.

## 12.2 Цели Navigation Design
Качественная система навигации должна обеспечивать:
быстрое нахождение информации;
понимание текущего местоположения;
понимание структуры сайта;
возможность быстрого перехода;
возможность возврата;
минимальное количество кликов;
предсказуемость поведения.

## 12.3 Принципы Navigation Design

### Принцип 1. Предсказуемость
Пользователь не должен изучать систему навигации.
Она должна работать так, как он ожидает.
Например:
логотип ведёт на главную;
корзина открывает корзину;
хлебные крошки возвращают вверх по структуре;
меню открывается одинаково на всех страницах.

### Принцип 2. Последовательность
Все элементы навигации должны вести себя одинаково.
Недопустимо:
различные стили меню;
разные способы открытия фильтров;
разные состояния активных пунктов.

### Принцип 3. Видимость
Навигация должна быть легко обнаруживаемой.
Не рекомендуется скрывать основные разделы за дополнительными действиями без необходимости.

### Принцип 4. Минимизация выбора
Навигация должна уменьшать количество решений пользователя.
Каждый следующий уровень должен сужать пространство поиска.

### Принцип 5. Обратная связь
Пользователь всегда должен понимать:
где находится;
куда может перейти;
что уже выбрал;
какие действия доступны.

## 12.4 Уровни навигации
Навигация интернет-магазина состоит из нескольких независимых уровней.

### Global Navigation
Главная система навигации сайта.
Обычно содержит:
Каталог;
Акции;
Новинки;
Бренды;
Блог;
Контакты.
Global Navigation должна быть доступна практически на каждой странице.

### Utility Navigation
Содержит сервисные функции.
Например:
Личный кабинет;
Авторизация;
Избранное;
Сравнение;
Корзина;
Поддержка;
Переключение языка;
Переключение валюты.
Utility Navigation должна быть визуально отделена от основной.

### Local Navigation
Навигация внутри конкретного раздела.
Например:
Категория «Ноутбуки»:
Игровые;
Ультрабуки;
Для работы;
MacBook.

### Contextual Navigation
Навигация, основанная на текущем контексте.
Например:
Похожие товары.
Комплектующие.
Совместимые аксессуары.
Покупают вместе.
Просмотренные товары.

### Footer Navigation
Служебная навигация.
Включает:
Доставку;
Оплату;
Возврат;
Политику конфиденциальности;
Пользовательское соглашение;
Вакансии;
Контакты.
Footer не должен использоваться для размещения критически важных сценариев.

## 12.5 Mega Menu
Mega Menu — основной инструмент навигации крупных eCommerce-проектов.

### Когда использовать
Mega Menu рекомендуется использовать, если:
каталог содержит более 300–500 SKU;
существует более 10 категорий первого уровня;
требуется быстрый доступ к большому количеству разделов.

### Структура Mega Menu
Рекомендуемая структура:
Категория
├── Подкатегория
│      ├── Раздел
│      ├── Раздел
│      ├── Раздел
│      └── Раздел
├── Популярные товары
├── Новинки
├── Акции
└── Баннер

### Правила проектирования Mega Menu
Каждая колонка должна содержать логически связанные элементы.
Основные категории должны визуально отличаться от подкатегорий.
Не рекомендуется использовать более 4–5 уровней вложенности.
Не следует перегружать меню графикой.
Баннеры допустимы только при наличии коммерческой ценности.

## 12.6 Breadcrumbs
Breadcrumb Navigation позволяет пользователю понять своё положение в структуре сайта.
Пример.
Главная
↓
Ноутбуки
↓
Игровые ноутбуки
↓
ASUS
↓
ROG Strix G16
Breadcrumbs должны:
соответствовать IA;
быть кликабельными;
отображаться на всех внутренних страницах.
Типичные ошибки:
использование нестандартных названий;
несоответствие структуре каталога;
отсутствие кликабельности.

## 12.7 Навигация каталога
Каталог должен поддерживать несколько способов навигации.
По категориям.
По брендам.
По сценариям использования.
По акциям.
По новинкам.
По подборкам.
По рекомендациям.
По поиску.
Каждый способ должен быть доступен независимо.

## 12.8 Навигация поиска
Поиск является полноценной системой навигации.
Поиск должен поддерживать:
автодополнение;
исправление опечаток;
синонимы;
морфологию;
популярные запросы;
историю поиска;
рекомендации;
быстрый переход в категории.

## 12.9 Навигация мобильной версии
На мобильных устройствах пространство значительно ограничено.
Поэтому рекомендуется использовать:
Bottom Navigation.
Sticky Header.
Sticky Search.
Off-canvas Menu.
Floating CTA.
Основные действия должны находиться в зоне комфортного доступа большого пальца.

## 12.10 Sticky Navigation
Фиксированные элементы значительно сокращают количество прокрутки.
Допустимо фиксировать:
поиск;
категории;
фильтры;
корзину;
CTA;
кнопку покупки.
Не следует фиксировать слишком большое количество элементов одновременно.

## 12.11 Навигация фильтрации
Фильтрация является частью навигационной системы.
Пользователь должен понимать:
какие фильтры применены;
сколько найдено товаров;
как удалить фильтр;
как сбросить все фильтры;
какие фильтры доступны.
Каждое изменение фильтра должно сопровождаться понятной обратной связью.

## 12.12 Навигация карточки товара
Карточка товара также содержит навигационные элементы.
Например:
галерея;
табуляция;
якорные ссылки;
FAQ;
отзывы;
характеристики;
похожие товары;
совместимые товары.
Все переходы должны быть логичными и не разрывать основной сценарий покупки.

## 12.13 Навигация Checkout
Во время оформления заказа рекомендуется использовать упрощённую навигацию.
Следует скрывать элементы, отвлекающие пользователя:
рекламные баннеры;
второстепенное меню;
большие каталоги.
Основной фокус — завершение покупки.

## 12.14 Проверка качества Navigation Design
Каждая система навигации должна оцениваться по следующим критериям:
время поиска товара;
First Click Success Rate;
Navigation Success Rate;
количество возвратов;
использование поиска;
количество тупиковых страниц;
глубина просмотра;
среднее количество переходов;
процент отказов после открытия меню.

## 12.15 Типичные ошибки
Проектирование навигации по организационной структуре компании.
Использование профессиональной терминологии вместо языка пользователя.
Избыточное количество пунктов первого уровня.
Скрытие основных разделов.
Перегруженное Mega Menu.
Отсутствие мобильной оптимизации.
Разные принципы навигации на разных страницах.
Неочевидные названия категорий.
Несогласованность хлебных крошек с информационной архитектурой.
Отсутствие контекстной навигации.

## 12.16 Deliverables
После проектирования Navigation Design должны быть подготовлены:
Navigation Specification;
Navigation Inventory;
Mega Menu Structure;
Mobile Navigation Map;
Breadcrumb Specification;
Navigation Component Library;
Navigation States Guide;
Navigation Validation Report;
Navigation KPI Dashboard;
Navigation UX Checklist.

Taxonomy & Catalog Architecture будет посвящена одной из самых сложных тем в eCommerce: проектированию товарной таксономии, атрибутов, классификаторов, SKU-модели, категорий, характеристик, фасетов и структуры каталога. Эта глава станет фундаментом для фильтрации, поиска, SEO, PIM, ERP и масштабирования ассортимента.

## Глава 13. Taxonomy & Catalog Architecture

## 13.1 Что такое Taxonomy
Taxonomy — это система классификации товаров, определяющая правила их организации, взаимосвязи и представления внутри цифрового продукта.
Для eCommerce таксономия является фундаментом:
каталога;
поиска;
фильтрации;
SEO;
PIM;
ERP;
рекомендаций;
персонализации;
аналитики.
Любая ошибка в таксономии масштабируется на весь интернет-магазин.
Поэтому разработка Taxonomy выполняется до начала наполнения каталога.

## 13.2 Цели товарной таксономии
Качественная Taxonomy должна обеспечивать:
понятную классификацию товаров;
быстрое нахождение продукции;
отсутствие дублирования;
масштабирование ассортимента;
совместимость с PIM;
совместимость с ERP;
поддержку маркетплейсов;
поддержку SEO;
поддержку AI-поиска.

## 13.3 Основные понятия
Перед проектированием необходимо определить единые сущности.

### Product
Коммерческий продукт.
Например:
iPhone 16 Pro.

### SKU
Конкретная товарная единица.
Например.
iPhone 16 Pro
256 GB
Black Titanium

### Category
Группа товаров.
Например.
Смартфоны.

### Subcategory
Подраздел категории.
Например.
Флагманские смартфоны.

### Brand
Производитель.
Apple.
Samsung.
Sony.

### Collection
Маркетинговое объединение товаров.
Например.
Новинки.
Черная пятница.
Летняя коллекция.

### Attribute
Характеристика товара.
Например.
Цвет.
Материал.
Размер.
Вес.

### Attribute Value
Конкретное значение характеристики.
Например.
Черный.
XL.
1000 Вт.

### Facet
Характеристика, используемая для фильтрации.
Не каждый Attribute является Facet.

## 13.4 Архитектура каталога
Каталог строится из нескольких уровней.
Catalog
↓
Department
↓
Category
↓
Subcategory
↓
Product Family
↓
Product
↓
SKU
Каждый уровень имеет собственную бизнес-функцию.

## 13.5 Departments
Самый верхний уровень.
Например.
Электроника.
Дом.
Авто.
Инструмент.
Спорт.
Красота.
Departments используются только при действительно большом ассортименте.

## 13.6 Categories
Категория объединяет товары по основному признаку.
Примеры.
Ноутбуки.
Телевизоры.
Диваны.
Шуруповерты.
Пледы.
Картины по номерам.
Правила.
Категории должны быть:
понятными;
независимыми;
масштабируемыми;
взаимоисключающими.

## 13.7 Subcategories
Подкатегория уточняет категорию.
Например.
Ноутбуки
↓
Игровые
↓
Для работы
↓
Ультрабуки
↓
Трансформеры
Подкатегория должна сокращать область поиска.

## 13.8 Product Family
Используется для объединения похожих товаров.
Например.
MacBook Air M4
↓
13”
↓
15”
↓
Разные цвета
↓
Разные объемы памяти
Product Family позволяет избежать дублирования информации.

## 13.9 SKU Architecture
SKU — минимальная единица учета.
Каждый SKU должен обладать:
уникальным идентификатором;
остатком;
ценой;
штрихкодом;
вариантом;
наличием.
SKU не должен использоваться как самостоятельная карточка товара, если различия между вариантами незначительны.

## 13.10 Product Variants
Варианты товара.
Например.
Размер.
Цвет.
Материал.
Комплектация.
Объем памяти.
Правила.
Варианты должны отображаться внутри одной карточки.
Создание отдельных карточек допускается только при существенных различиях.

## 13.11 Product Attributes
Все характеристики подразделяются на несколько групп.

### Technical
Вес.
Размер.
Материал.
Мощность.
Объем.

### Commercial
Цена.
Скидка.
Акция.
Бонусы.

### Marketing
Новинка.
Хит продаж.
Рекомендуемый.

### Logistics
Вес.
Размер упаковки.
Срок доставки.
Количество на складе.

### SEO
Meta Title.
Meta Description.
Slug.
Canonical.

## 13.12 Правила построения атрибутов
Каждый Attribute должен отвечать следующим требованиям.
Иметь единое название.
Не содержать дублей.
Использовать одинаковые единицы измерения.
Поддерживать фильтрацию.
Поддерживать импорт.
Поддерживать экспорт.
Поддерживать API.
Например.
Неправильно.
Вес
Масса
Вес товара
Weight
Правильно.
Вес

## 13.13 Обязательные атрибуты
Для большинства интернет-магазинов минимальный набор включает:
Название.
SKU.
Категория.
Бренд.
Описание.
Цена.
Фотографии.
Наличие.
Артикул производителя.
Характеристики.
Гарантия.
Доставка.

## 13.14 Taxonomy Governance
Таксономия должна управляться централизованно.
Запрещается:
создавать новые категории без утверждения;
добавлять новые атрибуты без анализа;
изменять названия категорий произвольно;
использовать разные названия одинаковых сущностей.
Необходимо вести:
Taxonomy Registry.
Attribute Dictionary.
Naming Convention.
Classification Rules.

## 13.15 Масштабирование каталога
Перед проектированием необходимо учитывать:
рост ассортимента;
новые бренды;
новые страны;
новые языки;
новые валюты;
новые категории;
новые склады.
Хорошая архитектура не требует перестройки при росте каталога в десять раз.

## 13.16 Типичные ошибки
Создание категорий по внутренней структуре компании.
Использование разных названий одинаковых характеристик.
Смешивание категорий и фильтров.
Создание отдельных карточек для каждого цвета товара.
Избыточное количество уровней вложенности.
Отсутствие стандартизации атрибутов.
Невозможность масштабирования.
Дублирование категорий.
Непоследовательная классификация.
Отсутствие владельца таксономии.

## 13.17 Deliverables
После проектирования Taxonomy должны быть подготовлены:
Taxonomy Specification;
Product Classification Model;
Category Tree;
Product Family Model;
SKU Architecture;
Attribute Dictionary;
Attribute Matrix;
Variant Model;
Naming Convention;
Taxonomy Governance Guide;
Catalog Growth Strategy;
Taxonomy Validation Checklist.
