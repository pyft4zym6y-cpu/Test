## Глава 27. Forms & Data Entry

## 27.1 Роль форм в eCommerce
Формы являются одним из наиболее критичных элементов пользовательского опыта.
Практически каждый ключевой сценарий включает ввод данных:
регистрация;
авторизация;
оформление заказа;
поиск;
подписка;
оформление возврата;
добавление адреса;
оплата;
отзыв;
обращение в поддержку.
Каждое дополнительное поле увеличивает вероятность отказа.
Каждое непонятное поле увеличивает когнитивную нагрузку.
Каждая ошибка увеличивает риск незавершённого сценария.
Главная задача UX — максимально сократить усилия пользователя при вводе данных.

## 27.2 Принципы проектирования форм
Все формы должны соответствовать пяти фундаментальным принципам.

### Минимум полей
Запрашивается только информация, действительно необходимая для выполнения задачи.
Каждое поле должно иметь бизнес-обоснование.
Если поле не используется — его следует удалить.

### Минимум решений
Пользователь не должен принимать лишние решения.
Например, вместо выбора страны вручную можно определить её автоматически и предложить изменить только при необходимости.

### Минимум ошибок
Интерфейс должен предотвращать ошибки, а не только сообщать о них.
Используются:
маски ввода;
ограничения;
автодополнение;
списки выбора;
проверки в реальном времени.

### Прозрачность
Пользователь должен понимать:
зачем нужны данные;
какие поля обязательны;
сколько осталось заполнить;
что произойдёт после отправки формы.

### Последовательность
Все формы продукта используют единые компоненты, правила и поведение.

## 27.3 Архитектура формы
Каждая форма должна состоять из стандартных элементов.
Label
↓
Input
↓
Helper Text
↓
Validation
↓
Error Message
↓
Success State
Отсутствие любого элемента должно быть осознанным решением.

## 27.4 Label
Label всегда отображается отдельно от Placeholder.
Например.
Имя
[____________]
а не
[Введите имя]
После ввода Placeholder исчезает.
Следовательно, пользователь теряет контекст.
Поэтому Placeholder никогда не заменяет Label.

## 27.5 Placeholder
Placeholder используется исключительно как дополнительная подсказка.
Например.
Введите email
или
example@email.com
Placeholder не должен содержать критически важную информацию.

## 27.6 Helper Text
Используется для пояснений.
Например.
Пароль должен содержать минимум 8 символов.
или
Мы никогда не передадим ваш email третьим лицам.

## 27.7 Required Fields
Количество обязательных полей должно быть минимальным.
Рекомендуется использовать:
●
или
(обязательно)
Не следует помечать необязательные поля как обязательные.

## 27.8 Input Types
Для каждого поля необходимо использовать корректный тип.
Например.
Email.
↓
email
Телефон.
↓
tel
Дата.
↓
date
Количество.
↓
number
Поиск.
↓
search
Это улучшает мобильный UX и работу автозаполнения.

## 27.9 Input Masks
Маски используются там, где формат данных заранее известен.
Например.
Телефон.
Дата.
Банковская карта.
ИНН.
Почтовый индекс.
Маска должна помогать пользователю, а не ограничивать его.

## 27.10 Autofill
Формы должны поддерживать:
Browser Autofill.
Apple Autofill.
Google Autofill.
Password Managers.
Saved Addresses.
Saved Cards.
Каждое автоматически заполненное поле повышает вероятность завершения формы.

## 27.11 Validation
Валидация должна происходить максимально рано.
Используются три уровня.

### Inline Validation
Во время ввода.
Наиболее предпочтительный вариант.

### On Blur
После выхода из поля.
Используется для большинства форм.

### On Submit
После отправки.
Используется только для финальной проверки.

## 27.12 Error Messages
Сообщение об ошибке должно содержать:
что произошло;
как исправить ошибку.
Например.
❌ Неправильно.
Ошибка.
✅ Правильно.
Введите корректный адрес электронной почты.

## 27.13 Success Messages
После успешного действия пользователь должен получить подтверждение.
Например.
Адрес успешно сохранён.
Пароль изменён.
Заказ оформлен.
Не следует использовать успех только через изменение цвета элемента.

## 27.14 Password UX
Современные формы должны поддерживать:
показать/скрыть пароль;
проверку сложности;
индикатор надёжности;
вставку из менеджеров паролей;
генерацию пароля (где применимо).
Не рекомендуется требовать чрезмерно сложные комбинации без необходимости.

## 27.15 Multi-step Forms
Если форма длинная, рекомендуется разбивать её на этапы.
Каждый этап должен содержать логически связанные поля.
Пользователь должен видеть прогресс выполнения.

## 27.16 Mobile Forms
На мобильных устройствах необходимо:
использовать подходящую клавиатуру;
увеличивать область касания;
избегать горизонтальной прокрутки;
автоматически переходить между полями при необходимости;
сохранять введённые данные при смене ориентации экрана.

## 27.17 Accessibility
Каждая форма должна поддерживать:
навигацию с клавиатуры;
корректный порядок фокуса;
ARIA-атрибуты;
озвучивание ошибок экранными дикторами;
достаточный контраст;
понятные названия полей.

## 27.18 Международные сценарии
При проектировании необходимо учитывать:
различные форматы адресов;
разные номера телефонов;
различные валюты;
локальные способы оплаты;
особенности имён и фамилий;
разные форматы дат.
Нельзя проектировать форму исключительно под одну страну, если продукт работает международно.

## 27.19 Analytics
Для форм рекомендуется фиксировать:
Form View;
Field Focus;
Field Blur;
Validation Error;
Form Abandonment;
Form Completion;
Time to Complete;
Autofill Usage;
Password Visibility Toggle;
Submit Success;
Submit Failure.

Рекомендуемые показатели.

| --- | --- |
| Form Completion Rate | Процент успешно заполненных форм |
| Form Abandonment Rate | Процент незавершённых форм |
| Average Completion Time | Среднее время заполнения |
| Validation Error Rate | Частота ошибок |
| Autofill Usage | Использование автозаполнения |
| Field Drop-off Rate | Поля, на которых пользователи прекращают заполнение |
| Submit Success Rate | Успешные отправки |
| Submit Failure Rate | Неудачные отправки |


## 27.21 Типичные ошибки
Использование Placeholder вместо Label.
Запрос избыточных данных.
Отсутствие автозаполнения.
Валидация только после отправки формы.
Очистка всех полей после ошибки.
Непонятные сообщения об ошибках.
Использование неподходящих типов клавиатуры на мобильных устройствах.
Слишком длинные формы без разбивки на этапы.
Отсутствие поддержки менеджеров паролей.
Игнорирование требований Accessibility.

## 27.22 Forms QA Checklist
Перед выпуском необходимо проверить:
количество обязательных полей минимально;
все поля имеют Label;
Placeholder используется только как подсказка;
поддерживается Autofill;
ошибки отображаются своевременно;
данные не теряются при ошибках;
корректно работают мобильные клавиатуры;
соблюдены требования Accessibility;
аналитика настроена;
форма протестирована на Desktop, Tablet и Mobile.

## 27.23 Deliverables
По результатам проектирования должны быть подготовлены:

Field Inventory;
Validation Rules;
Error Message Guide;
Autofill Specification;
Input Mask Guide;
Mobile Forms Specification;
Forms Accessibility Guide;
Forms Analytics Specification;
Forms KPI Dashboard;
Forms QA Checklist.

## Глава 28. Authentication & Account Experience

## 28.1 Роль Account Experience
Account Experience — это совокупность пользовательских сценариев, связанных с регистрацией, авторизацией, управлением профилем, безопасностью и персональными данными.
Современный eCommerce не должен заставлять пользователя создавать аккаунт ради совершения покупки.
Аккаунт должен предоставлять дополнительную ценность:
ускорение повторных покупок;
история заказов;
сохранённые адреса;
избранное;
бонусы;
персональные рекомендации;
гарантийные документы;
управление подписками.
Регистрация должна восприниматься как преимущество, а не как обязательство.

## 28.2 Жизненный цикл пользователя
Account Experience проектируется как непрерывный цикл.
Гость
↓
Регистрация
↓
Авторизация
↓
Первый заказ
↓
Повторные покупки
↓
Лояльность
↓
VIP
↓
Повторное вовлечение
Каждый этап имеет собственные UX-сценарии.

## 28.3 Guest User
Гость должен иметь возможность:
просматривать каталог;
использовать поиск;
фильтрацию;
корзину;
Checkout;
оформление заказа.
Регистрация предлагается только тогда, когда действительно создаёт дополнительную ценность.

## 28.4 Регистрация
Современная регистрация должна занимать не более 30–60 секунд.
Минимальный набор полей.
Email
или
Телефон
↓
Пароль
↓
Создать аккаунт
Все остальные данные рекомендуется собирать позже.

## 28.5 Social Login
Поддерживаются.
Google.
Apple.
Facebook (при необходимости).
Microsoft.
Telegram (если соответствует рынку).
Passkeys (при поддержке платформы).
Social Login значительно сокращает количество отказов.

## 28.6 Passwordless Authentication
Современные системы всё чаще используют вход без пароля.
Например.
Magic Link.
↓
Email.
↓
Переход по ссылке.
↓
Авторизация.
или
OTP.
↓
SMS.
↓
Код.
↓
Вход.
Passwordless уменьшает количество проблем с забытыми паролями.

## 28.7 Авторизация
Форма входа должна содержать:
Email / Телефон.
Пароль.
Показать пароль.
Запомнить меня.
Забыли пароль.
Social Login.
Кнопку входа.
Все дополнительные элементы должны быть второстепенными.

## 28.8 Восстановление доступа
Процесс должен быть максимально простым.
Email
↓
Получение ссылки
↓
Создание нового пароля
↓
Авторизация
Пользователь не должен проходить сложные проверки без необходимости.

## 28.9 Session Management
Необходимо поддерживать:
автоматическое продление активной сессии;
безопасный выход;
управление несколькими устройствами;
завершение других сессий;
уведомления о новых входах.

## 28.10 Multi-device Experience
Пользователь должен иметь одинаковый опыт на:
Desktop.
Tablet.
Mobile.
Приложении.
Сохранённые данные синхронизируются между устройствами.

## 28.11 Профиль пользователя
Личный кабинет должен содержать.
Личные данные.

Историю заказов.
↓
Адреса.
↓
Способы оплаты.
↓
Избранное.
↓
Сравнение.
↓
Бонусы.
↓
Подписки.

Настройки уведомлений.
↓
Безопасность.
↓
Поддержку.

## 28.12 История заказов
Каждый заказ должен содержать.
Статус.
Номер.
Дата.
Стоимость.
Товары.
Повторить заказ.
Скачать документы.
Возврат.
Отслеживание.
История заказов должна быть пригодна для повторной покупки одним нажатием.

## 28.13 Saved Addresses
Пользователь должен иметь возможность:
добавить;
изменить;
удалить;

## 28.14 Saved Payment Methods

карт;
электронных кошельков;
любимых способов оплаты.
Пользователь должен иметь возможность удалить любой сохранённый способ оплаты.

## 28.15 Wishlist
Избранное должно работать независимо от устройства.
Поддерживаются:
папки;
совместный доступ;
уведомления о снижении цены;
уведомления о появлении товара.

## 28.16 Loyalty
Личный кабинет отображает:
баланс бонусов;
уровень программы;
историю начислений;
срок действия бонусов;
доступные привилегии.
Информация должна быть понятной без дополнительных расчётов.

## 28.17 Notifications
Пользователь управляет подписками.
Email.
SMS.
Push.
Telegram.
WhatsApp (если поддерживается).

## 28.18 Security

сменить пароль;
включить двухфакторную аутентификацию;
просмотреть историю входов;
завершить активные сессии;

## Глава 29. Personal Account (My Account / Customer Dashboard)

## 29.1 Роль личного кабинета
Личный кабинет — это персональный цифровой центр взаимодействия клиента с компанией после первой покупки.
Во многих интернет-магазинах личный кабинет ограничивается отображением истории заказов.
Это стратегическая ошибка.
Современный Customer Dashboard должен выполнять четыре функции:
управление покупками;
управление персональными данными;
управление отношениями с компанией;
стимулирование повторных продаж.
Личный кабинет является одним из основных инструментов удержания клиентов (Retention).

## 29.2 Цели Personal Account
Современный личный кабинет должен:
сокращать количество обращений в поддержку;
ускорять повторные покупки;
повышать Lifetime Value (LTV);
увеличивать Retention;
повышать удовлетворённость клиентов;
обеспечивать полный self-service.

## 29.6 Order Details
Страница заказа должна содержать:

стоимость;
скидки;

способ оплаты;
адрес доставки;
статус доставки;
трек-номер;
историю изменения статусов;
документы.
Пользователь не должен обращаться в поддержку для получения этой информации.

## 29.7 Repeat Order
Повторная покупка должна выполняться одним действием.
Например.
Повторить заказ
↓
Добавить все товары в корзину
↓
Проверка наличия
↓
Checkout
При отсутствии отдельных товаров необходимо предложить аналоги.

## 29.8 Returns
Раздел возвратов должен содержать:

статус заявок;
инструкции;
адрес возврата;
историю возвратов;
денежные компенсации.
Все этапы должны быть прозрачны.

## 29.9 Wishlist
Избранное должно поддерживать:
несколько списков;
совместный доступ;
уведомления о снижении цены;
уведомления о появлении товара;
быстрый перенос в корзину;
фильтрацию и сортировку.

## 29.10 Compare
Пользователь должен иметь возможность:
просматривать список сравнения;
добавлять товары;
удалять товары;
быстро переходить в карточки товаров;
добавлять выбранный товар в корзину.

## 29.11 Saved Addresses
Поддерживаются:
домашний адрес;
рабочий адрес;
адрес получателя;
самовывоз;
несколько адресов доставки.
Каждый адрес можно:
создать;
изменить;
удалить;
назначить основным.

## 29.12 Payment Methods
Если бизнес-модель допускает хранение платёжных данных, пользователь должен иметь возможность:
добавить способ оплаты;
удалить;
назначить способом по умолчанию;
просмотреть последние операции.
Конфиденциальные данные отображаются только в безопасном формате.

## 29.13 Loyalty Dashboard
Отображаются:

история начислений;
история списаний;
доступный уровень программы;
следующий уровень;
индивидуальные предложения.
Пользователь должен понимать:
сколько бонусов доступно;
когда они истекают;
как их использовать.

## 29.14 Coupons

## 29.24 Типичные ошибки
Личный кабинет содержит только историю заказов.
Отсутствует повторный заказ.
Нет управления возвратами.
Нельзя скачать документы.
Нет центра уведомлений.
Отсутствует управление безопасностью.
Избранное не синхронизируется между устройствами.
Персонализация отсутствует или нерелевантна.
Нет мобильной оптимизации.

документы доступны для скачивания;

аналитика настроена;
Accessibility соблюдена;
интерфейс протестирован на Desktop, Tablet и Mobile.
