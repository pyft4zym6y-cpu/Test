# weexp · Commerce OS™ · Итоговый документ продукта

Полное описание продукта: механика и логика Discovery-портала (разделы 1–10),
логика сайта weexp.agency (раздел 11), дизайн-система (12), карта методики
в репозитории (13), приватность и операционные регламенты (14),
Decision Engine (15). Актуально для версии v6.

---

## 1. Что это и из чего состоит

**Назначение.** Портал переводит «Consulting Discovery Framework v2.0» (Excel,
56 листов, 666 вопросов) в веб-продукт: клиент проходит структурированную
диагностику сам, портал в реальном времени собирает автоматический отчёт по
методике Commerce OS™, консультант в закрытой ветке проверяет, дополняет и
финализирует результат, генерирует КП, план и бюджет.

**Стек.**

| Слой | Технология |
| --- | --- |
| Фронтенд | React 18 + TypeScript + Vite, кастомный CSS (без UI-библиотек) |
| Роутинг | react-router-dom; BrowserRouter на хостинге, HashRouter в артефакте (переключение флагом сборки `__ARTIFACT_BUILD__`) |
| Бэкенд | Supabase: Postgres + Auth (magic-link) + Storage; RLS на каждой таблице |
| Serverless | Две функции Vercel: `/api/fetch` (прокси HTML для скрининга), `/api/ga4` (GA4 Data API) |
| Хостинг | Vercel, отдельный проект с Root Directory = `portal`, домен discovery.weexp.agency |

**Два режима работы.** Определяются автоматически в `src/lib/supabase.ts`:

- **Боевой** — если заданы `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY`:
  вход по magic-link, данные в Postgres, файлы в Storage.
- **ДЕМО** — если переменных нет: всё то же самое, но данные в localStorage
  браузера (ключи `weexp-demo-answers`, `weexp-demo-access`, `weexp-demo-files`,
  `weexp-demo-meta`), пользователь — виртуальный админ `demo@weexp.agency`.
  Сверху жёлтая плашка с кнопками «Заполнить демо-данными» (сид) и «Сбросить».
  Serverless-функции в демо недоступны — кнопки честно сообщают
  «работает на хостинге».

**Данные, зашитые в приложение** (`src/data/`):

| Файл | Содержимое |
| --- | --- |
| `questions.json` | 643 вопроса (P1+P2, вес ≥ 2 из XLSX): id, домен, лист, уровень L1/L2, parent, branch, текст, «зачем спрашиваем», тип, варианты, роль, риск, вес |
| `accesses.json` | 26 позиций доступов: AC-01…AC-20 (системы) + EX-01…EX-06 (интервью/документы/опросы) |
| `routing.json` | 50 правил роутинга R01–R50: триггер → плейбук → deliverable → приоритет P0/P1/P2 |
| `method.ts` | Матрица зрелости (18 доменов с весами), 18 критических разрывов CG с штрафами, полосы Health Score |
| `pains.ts` | 16 болей, 9 целей, 5 групп каналов (35 каналов UA/EU/US), спец-QID |
| `decision.ts` | Чек-лист самооценки (10 утверждений), роли ЛПР, вилки бюджета |
| `rates.ts` | Rate card ~40 позиций: подтверждённые ставки из реальных КП + рыночные вилки 2025 |

## 2. Доступ и роли

**Вход.** Клиент вводит рабочий e-mail → Supabase шлёт magic-link → по клику
сессия создаётся без пароля. Дальше e-mail ищется в таблице `members`
(нижний регистр). Три ветки:

1. e-mail найден → загружается `member` (client_id, имя, роль, is_admin) —
   пользователь попадает на дашборд своего клиента;
2. сессия есть, но e-mail не в `members` → экран «Доступ не подключён»
   с кнопкой перелогина;
3. сессии нет → экран входа.

**Роли.** `member.is_admin = true` открывает пункт «Админ» в шапке и все
консультантские страницы. Обычный участник видит только свой проект.
У вопросов проставлены роли-подсказки (CEO / CFO / Head E-com / CRM /
Маркетинг) — это теги «кому отвечать», не ограничение доступа.

**RLS (безопасность на уровне БД).** Через security-definer функции
`auth_email()`, `my_client_id()`, `is_portal_admin()`:

- клиент читает/пишет **только** строки своего `client_id`;
- админ читает всё, пишет клиентов/участников/report_meta;
- `consultant_notes` — только админ (клиент не видит ни при каких условиях);
- Storage: файлы лежат по пути `clientId/accessId/…`, политика пускает
  только своего клиента и админа.

**Правило безопасности продукта:** пароли не собираются нигде и никогда.
Доступы передаются приглашениями с правами «просмотр», файлами в защищённую
папку или одноразовыми ссылками (Bitwarden Send / 1Password). Это правило
показано клиенту в интерфейсе явно.

## 3. Путь клиента: 7 шагов

Дашборд (`/`) показывает шаги 01–07 со статусами: ✓ выполнен → зелёная
подсветка «следующий» → серый «впереди». Статус вычисляется по данным
(например, шаг 01 готов, когда заполнены название + оффер + ниша).
Идти можно в любом порядке, но подсветка ведёт сверху вниз.

### Шаг 01 · Компания (`/company`, QID `PASSPORT`, JSON)

Паспорт бизнеса: название, **несколько сайтов** (динамические строки),
оффер, ниша (12 вариантов + «Другая» с обязательным полем ввода),
каналы продаж пятью группами — собственные / маркетплейсы Украины /
Европы / США и мира / офлайн и B2B (35 чекбоксов + «другое — впишите»),
география, вилка оборота, размер команды.

### Шаг 02 · Цели (`/goals`, QID `GOALS`, `GOALS-CUSTOM`, `BRIEF-*`)

**Два горизонта.** Тактика · 90 дней (5 целей: остановить падение, закрыть
кассовый разрыв, поднять конверсию за 30 дней, быстрые продажи из базы,
подготовиться к сезону) и Стратегия · 12 месяцев (9 целей: рост UA, Европа,
прибыль, LTV, бренд, систематизация…) + свободное поле. Ниже три вопроса
брифа собственника: что пробовали, кто драйвит, амбиция.

### Шаг 03 · Боли (`/pains`, QID `PAINS`, `PAINS-CUSTOM`)

**Два подблока.** «Тактика · горит прямо сейчас» — 8 пожаров (обвал продаж,
реклама/кабинет встал, ошибки чекаута, кассовый разрыв, блокировка
маркетплейса, сток кончается, ушёл ключевой человек, сезон на носу); у
каждого зашиты **первая помощь на 24–48 часов** и приоритетные доступы.
«Стратегия · болит системно» — 16 хронических болей. Плюс свободное поле.
Трек опросника: `trackFor()` взвешивает листы (тактика ×1.5 — горящие зоны
первыми, цели ×1.2, боли ×1.0). База 10/11/12 всегда первая.

**Тактический контур сквозной:** выбранные пожары дают баннер «🔥 Горит»
на дашборде, блок «Первая помощь · 24–48 часов» в отчёте, баннер
приоритетных доступов на шаге 06, тактические решения DE-T1…T4 первыми в
Decision Engine (тег «🔥 Тактика») и «Волну 0 · Первая помощь · 0–2 недели»
в КП перед волнами программы. Точка Б в КП и отчёте показывает оба
горизонта раздельно — как требует AD-15 («два горизонта обязательны»).

### Шаг 04 · Опросник (`/d/:sheet`, ответы по QID вопроса)

Ядро диагностики: ~26 анкет по доменам. Механика вопроса:

- **Типы ответов** и их рендер:
  - `Да/Нет`, `Да/Нет/Частично`, `Шкала 0-5` — чипсы (варианты подставляются автоматически);
  - `Выбор` — чипсы, один вариант;
  - `Мультивыбор` — чипсы, несколько вариантов (ответ хранится строкой
    `«А | Б | В»`). Одиннадцать вопросов про причины/источники/критерии
    (CO-001 «почему сейчас», PX-003, PX-019, CU-002, MP-002, IN-002, IN-044,
    AI-126, PL-002, PL-006, BI-003) принудительно переведены в мультивыбор
    оверрайдом в `model.ts`;
  - `Число` — поле с inputMode=decimal;
  - `Текст` — textarea;
  - **разбивка**: текстовый/числовой вопрос, у которого варианты — это
    позиции («Сайт %», «Опт %»…), рендерится сеткой отдельных полей на
    каждую позицию; если все позиции в процентах — живой счётчик
    «Сумма: N%» (зелёный при 100±2%, жёлтый с подсказкой иначе); хранение
    «Сайт: 45 | Опт: 20»;
  - **«Другое/Другая/Другой»** в любом чипс-вопросе открывает поле
    «Впишите свой вариант…», хранение «Другое: текст».
- **Ветвление.** Вопросы L2 скрыты, пока не отвечен родитель. `isVisible()`:
  ответ родителя нормализуется (нижний регистр, без кавычек) и сравнивается
  с меткой ветки подстрокой в обе стороны. Для мультивыбора работает
  из коробки — в строке «Падают продажи | Инвестор требует роста» найдутся
  обе метки, и **откроются обе ветки уточнений** (CO-002 и CO-004).
- **Факты.** У каждого вопроса сворачиваемый блок «Факты, цифры, ссылки» —
  свободное поле для доказательств; уходит в экспорт и отчёт консультанта.
- **Сохранение.** Автосохранение с дебаунсом ~0.5–0.7 с: в демо —
  localStorage, в бою — upsert в `answers` (ключ client_id+question_id,
  фиксируется updated_by = e-mail отвечавшего). Плашка «Сохранено ✓».
- Подсказка методики: «Не знаете точно — пишите оценку. "Не знаю / не
  считаем" — тоже ценный ответ» (по методу такой ответ засчитывается как разрыв).

### Шаг 05 · Конкуренты и референсы (`/links`, QID `LINKS`, JSON)

Три списка ссылок с примечаниями: прямые конкуренты, дополнительные
(заменители), референсы «хотим как…». Прямые конкуренты дальше используются
скринингом и PSI.

### Шаг 06 · Файлы и доступы (`/access`)

26 позиций реестра. По каждой: статус (Не выдан / В процессе / Выдан /
Нужна помощь — селект с цветовой индикацией), инструкция «как выдать»
(например GA4: Администратор → Управление доступами → e-mail с ролью
«Наблюдатель»), комментарий и загрузка файлов (Storage/localStorage).
У AC-13 — ссылка на шаблон выгрузки заказов (CSV с нужными колонками).
Счётчик «Выдано: N/26». Вверху — правило «мы никогда не просим пароли».

### Шаг 07 · Решение и команда (`/decision`, QID `DECISION`, JSON)

Заполняет собственник/CEO. Пять блоков:

1. **Своими словами** — причина обращения + три главные проблемы по версии
   владельца (три отдельных поля);
2. **Самооценка** — 10 утверждений («Мы знаем юнит-экономику каждого канала»,
   «Решения принимаются на сверенных цифрах»…), каждое 0–5. При ≥6 ответах
   считается балл: среднее × 20 → 0–100. Дальше он сравнивается с Health
   Score — расхождение подсвечивается консультанту (главный аргумент разговора);
3. **Кто участвует в решении** — карта ЛПР: имя, роль, влияние (принимает /
   влияет / консультирует / исполняет), личный KPI, что важно/чего опасается;
4. **Рамки** — вилка бюджета (6 вариантов от «до $5K» до «более $80K»),
   формат оплаты (транши под результат / фикс), дедлайн решения, сезонность кэша;
5. **Паспорт команды** — роли, имена, часов в неделю на проект, зоны
   ответственности + что на аутсорсе.

## 4. Автоматический отчёт клиента (`/report`)

Собирается на лету из ответов функцией `buildReport()` при каждом открытии.
Порог: пока отвечено < 30 базовых вопросов — экран «Пока мало данных».

### 4.1 Формула Health Score (реализация методики Commerce OS)

**Здоровье домена.** По каждому листу берутся ответы на скорируемые вопросы
(Да/Частично/Нет и их вариации): Да → 0 штрафа, Частично → 0.5, Нет → 1.
`health = 1 − (штрафы / скорируемые)`. Если скорируемых < 3 — домен не
оценивается (честное «мало данных», в карте не показывается). Зоны:
≥ 70% норма (зелёный), ≥ 45% внимание (жёлтый), ниже — критично (красный).

**Score A — взвешенная зрелость.** 18 доменов матрицы, веса в сумме 100
(Sales 8, CRM 8, Operations 8, Marketing 7, Analytics 7, Finance 7,
Strategy 6, Brand 6, SEO 6, Platform 6, Product 5, Customer 5, People 5,
Marketplace 4, Governance 4, Pricing 3, International 3, AI 2). Каждый
домен матрицы усредняет health своих листов; счёт считается только когда
покрыто весов ≥ 30 из 100, иначе null.

**Score B — фундамент без критических разрывов.** 18 контрольных разрывов
(CG) с ручной привязкой к вопросам и штрафами: «Нет единого источника
правды» −10 (AN-003), «Не считается юнит-экономика» −10 (FI-002), «Нет
retention-контура» −8 (CR-004), «Нет управленческого P&L» −7 (FI-001) и т.д.
Разрыв срабатывает **только** на прямой ответ «Нет» на контрольный вопрос —
не на молчание. `ScoreB = max(0, 100 − Σ штрафов)`; null, пока ни один
контрольный вопрос не отвечен.

**Итог:** `Health Score = 0.6 × ScoreA + 0.4 × (ScoreB или ScoreA)`.
Полосы интерпретации: ≥80 «Зрелая система», 60–79 «Управляемый бизнес,
точки роста локальны», 40–59 «Работающий бизнес без управляемости»,
<40 «Системные пробелы в фундаменте» — с рекомендуемым действием.

### 4.2 Состав отчёта

Обложка (паспорт, цели, % заполнения) → кольцо Health Score с формулой и
болями-чипсами → карта здоровья по блокам (полосы с зонами) → карточки
критических разрывов (штраф, вопрос-доказательство) → блок «Методика:
граница факта и допущения» → реестр рисков (топ-12 из текстов риска
вопросов, severity = штраф × вес вопроса) → рекомендации (правила роутинга)
→ деньги → подпись версии.

**Роутинг рекомендаций.** Правило срабатывает, если его триггер совпал
с названием выбранной боли (подстрочно) **или** точно совпал с одним из
выбранных вариантов ответов. Мультивыбор разбивается на отдельные
варианты по « | » — каждый выбранный триггер активирует своё правило.
Сортировка P0 → P1 → P2.

### 4.3 Слой консультанта в отчёте (из `report_meta`)

Пока консультант не публиковал финал, отчёт подписан «предварительный
диагноз, автоматическая версия». После публикации меняются: бейдж
«✓ Проверено консультантом weexp», заголовок «финальная картина», первым
блоком — резюме консультанта, риски фильтруются по списку скрытых, и
появляются (если консультант их включил):

- **Деньги** — «Консервативно вы недополучаете ≈X млн ₴/год» + водопад
  вкладов рычагов (полосы) + дата/период baseline;
- **Скорость** — таблица PageSpeed вы/конкуренты (Score, LCP, CLS);
- **Витрина** — полосы % соответствия голд-стандарту вы/конкуренты +
  список «что чинить в первую очередь».

Кнопка «Скачать PDF» = window.print() с print-стилями.

## 5. Консультантская ветка (только админ)

### 5.1 `/admin` — клиенты

Таблица клиентов (ответов L1, доступов выдано), создание клиента,
приглашение участника (e-mail + имя + роль), кнопка «Приглашение 📋» —
копирует готовый текст письма со ссылкой и порядком шагов. Ссылка
«Открыть →» ведёт в карточку клиента.

### 5.2 `/admin/c/:clientId` — карточка клиента

Одиннадцать блоков сверху вниз.

**Публикация.** Textarea резюме (клиент увидит первым блоком), кнопка
«Опубликовать финальную версию» / «Вернуть в черновик» (статус в
`report_meta.status`), ссылки «Сгенерировать КП», «Экспорт для ЕКП (CSV)».
CSV: ID; Домен; Вопрос; ОТВЕТ КЛИЕНТА; Факты; Кто; Когда — разделитель «;»,
BOM для Excel. Скрипт `portal/scripts/fill_ekp.py` (openpyxl) находит ID
вопроса в первой колонке любого листа книги, колонку «ОТВЕТ/ВІДПОВІДЬ»
по заголовку (fallback — колонка 8) и заполняет книгу, не трогая исходник;
факты дописываются в скобках; несовпавшие ID перечисляются в консоли.

**Деньги · baseline на 8 рычагов (AD-13 → AD-04).** Модель выручки:

```
Выручка/мес = НОВАЯ + ПОВТОРНАЯ
НОВАЯ      = трафик × CR% × чек × оплата% × выкуп%
ПОВТОРНАЯ  = база × повторные_за_мес% × заказов_на_повторного × чек × оплата% × выкуп%
```

По каждому рычагу: факт, цель, источник (GA4 / CRM / Выгрузка заказов /
Кабинет площадки / Оценка клиента) + подсказка, откуда брать. Сверху —
дата снятия и период усреднения. Защита от фантазий: цель CR обрезается
3× факта, повторные ≤ 80%, оплата/выкуп ≤ 100%, пустая цель = факт.

**Расчёт цепной атрибуцией:** рычаги подставляются в целевое значение
последовательно; вклад рычага i = выручка(1..i цель) − выручка(1..i−1 цель).
По построению Σ вкладов = потенциал — на экране контроль «Σ вкладов =
потенциал ✓/✗». Итоги: полный потенциал ₴/год, консервативно ×0.55,
промедление = консервативно/12. «Показать в отчёте клиента» кладёт всё
в `report_meta.money` (вместе с рычагами и водопадом).

**⇓ Подтянуть из GA4** — вызывает `/api/ga4`: заполняет трафик, CR (и чек,
если пуст) фактами за 90 дней с источником «GA4». Если ключи не настроены
или это демо — понятная ошибка с инструкцией.

**Выгрузка заказов · разбор.** CSV разбирается **в браузере, никуда не
отправляется**. Алгоритм: авто-детект разделителя (`;`/`,`), колонки по
алиасам (дата: order_date/дата/…; сумма: total_uah/сумма/…; клиент, канал,
статус — опционально), парс дат в двух форматах, заказы со статусом
возврат/отмена исключаются из выручки. Считается: выручка и заказы/мес
(средняя за последние 3 полных месяца — последний месяц отбрасывается как
неполный), средний чек, активная база (уникальные покупатели), повторные
(первая покупка каждого клиента фиксируется; всё после её месяца —
повторное): % базы/мес, заказов на повторного, % выручки от повторных,
концентрация топ-10% клиентов (⚠ если >50%), % возвратов (⚠ если >15%),
разбивка выручки по каналам. Кнопка «Подставить факт в baseline» заполняет
чек/базу/повторные/заказы-на-повторного с источником «Выгрузка заказов»
и проставляет дату/период.

**ЛПР, рамки, команда.** Сводка шага 07 + бейдж «самооценка N vs Health
Score M» (жёлтый при расхождении ≥15 — точка входа в разговор).

**Вопросы к интервью · противоречия.** 12 правил вида «ответ A заявляет
зрелость, ответ B отрицает её условие»:

| Правило | A | B | Вопрос |
| --- | --- | --- | --- |
| C1 | GV-003 «По данным» | AN-003 «Нет» | Решения «по данным» без единого источника правды — по каким данным? |

Сработавшие показываются как готовые вопросы к интервью с доказательствами

**L0 · PageSpeed.** Кнопка гоняет Google PSI API (mobile) по сайтам клиента

**Скрининг страниц.** Через `/api/fetch` качается HTML тех же целей, затем
DOMParser и **30 проверок против голд-стандарта** в трёх группах:

- *SEO*: title 15–70, description 50–170, canonical, ровно один H1,
  нет случайного noindex, OG-теги, Schema.org Organization/WebSite,
  Product/Offer, BreadcrumbList, hreflang;
- *UX*: viewport, favicon, поиск по сайту, кликабельный телефон tel:,
  обнаружимая корзина, цены на странице, отзывы/рейтинг, доставка/оплата

- *Техника*: HTTPS, charset, ALT у ≥70% картинок, lazy-load, lang,

Каждому сайту — % пройденных (голд-стандарт = 100%), матрица ✓/✗ по всем
проверкам и сайтам. Сайт с бот-защитой помечается «HTTP 403 (бот-защита?)»
— честный «не удалось проверить», не ложное «всё плохо». Результат в
`report_meta.screen` → отчёт клиента.

## 6. Serverless API

**`GET /api/fetch?url=…`** — качает страницу с браузерным User-Agent
(таймаут 12 с, редиректы, до 400 КБ), возвращает `{status, finalUrl, html}`.
Нужна, потому что браузер не может скачать чужой сайт напрямую (CORS).
Кэш на edge 1 час. Ошибки не роняют запрос — `{status: 0, error}`.

**`GET /api/ga4`** — авторизация сервисным аккаунтом Google (JWT RS256
подписывается ключом из env, меняется на access token), запрос GA4 Data API
`runReport` за 90 дней: sessions, transactions, purchaseRevenue → отдаёт
сессии/мес, заказы/мес, выручку/мес, CR%, средний чек. Требует env-переменных
`GA4_PROPERTY_ID`, `GA4_SA_EMAIL`, `GA4_SA_KEY`; сервисный аккаунт
добавляется в GA4 клиента «Наблюдателем». Без настройки возвращает
инструкцию, а не 500.

## 9. Известные ограничения (осознанные)

- **Email-напоминания** — нужен почтовый сервис (Resend); пока приглашение
  копируется кнопкой, magic-link шлёт Supabase.
- **Скрининг/GA4 в демо-режиме** не работают (нет serverless) — кнопки
  сообщают об этом явно.
- **Сайты с жёсткой бот-защитой** (Cloudflare и т.п.) не отдают HTML —
  скрининг честно помечает; остаются PSI и ручной разбор.
- **Кросс-ролевые противоречия** ловятся только между разными вопросами:
  на один вопрос хранится один ответ (последний перезаписывает), «спор»
  двух ролей по одному вопросу не фиксируется.
- **Гант** — черновик-заготовка, не полная книга на 735 задач; бюджет —
  смета по rate card, не финмодель.
- Деньги показываются клиенту **только** после ручного действия
  консультанта — автоматический отчёт цифр не обещает (принцип методики).

## 11. Сайт weexp.agency: логика калькуляторов

Сайт — витрина и верх воронки: главная (боли → Commerce OS™ → продукты →
кейсы), страницы продуктов/кейсов/подхода, демо «OS» и два калькулятора.
Деплой — тот же репозиторий, корневой проект Vercel, домен weexp.agency.

### 11.1 Калькулятор разрыва (`/calculator`)

Мастер из 8 шагов: ніша → оборот → середній чек → конверсія → повторні →
трафік (% органіки) → CRM (% виручки з email) → маржа. У каждой ниши —
бенчмарки (CR цель, повторные цель); ответы клампятся в разумные границы
(CR 0.1–15%, повторные 0–80%, маржа 5–90%).

**Модель — та же цепная, что в портале** (упрощённая до двух рычагов):

```
R = оборот × 12
crFactor  = clamp(CR_цель / CR_факт, 1..3)
repFactor = clamp((1 − повт_факт) / (1 − повт_цель), 1..1.6)
Полный потенциал = R × (crFactor × repFactor − 1)
Консервативно    = 0.55 × полный
```

Плюс «Профиль здоровья» по зонам (органика против цели 35% трафика, email
против 20% выручки, маржа) и потери маржи. Результат сразу, CTA на аудит.
Важно: сайт считает по бенчмаркам ниши (ориентир), портал — по данным
клиента (факт) — это разные классы цифр, и оба честно подписаны.

### 11.2 Калькулятор оценки проекта (`/estimate`)

Тёмная секция `#calculator-section`, акцент `#FF5656`. Входы: услуга
(дизайн / розробка / дизайн+розробка), слайдер страниц 1–30, чекбоксы
контент и SEO, срочность. Формулы (в $):

```
base    = дизайн 399 · розробка 199 · обидва 499
perPage = 100 · 100 · 200
total   = max(base, base + (pages − 1) × perPage)
        + (контент? pages × 50) + (SEO? pages × 50)
        + (до 7 днів? pages × 100 · до 14 днів? pages × 25)
Агентство  = 8000 + (pages − 1) × (обидва? 1000 : 400)
Фрілансер  = 3000 + (pages − 1) × (обидва? 500 : 200)
```

Три карточки цен: агентство / фрилансер / «З weexp» (градиентная,
розово-оранжевая) — контраст в пользу weexp виден сразу; CTA в /contact.

## 15. Decision Engine (v6): из диагностики — в решения

Слой поверх отчёта, переводящий систему из «диагностической» в
«предиктивно-решающую». Первоисточник — `method/references/decision_engine.md`
и `method/references/ontology.md`; код — `src/lib/engine.ts` + `src/data/engine.ts`.

**Движок решений.** 12 IF-правил над ответами, рычагами baseline и замерами:
`IF выручка из email < 10% AND сегментации нет AND база > 1000 THEN
«Построить CRM-контур» · Impact 9/10 · Сложность 3/10 · 30 дней · PB-08`.
Ранжирование по Impact/Difficulty; квадранты Quick win / Стратегическое /
Поддерживающее; ROI-класс High/Medium/Long-term. **Каждое решение объяснимо**:
разворачиваемая трасса «почему» со сработавшими условиями, фактическими
значениями и кодами вопросов — правило без трассы в выдачу не попадает.

**Confidence Score.** Доверие к выводам 0–100: заполненность (до +40),
доступы (до +15), baseline из данных систем (до +20), внешние замеры (+8),
бриф ЛПР (+7), финал (+10), минус 3 за каждое противоречие (до −15).
Показывается консультанту с разложением по факторам и клиенту одной строкой.
Отчёт на 120 ответах и на 620 больше не выглядит одинаково.

**Evidence Levels.** Достоверность каждого факта: E0 догадка · E1 со слов ·
E2 документ · E3 данные системы · E4 несколько источников (соответствие
шкале метода 25/50/75/100). Бейджи у каждого рычага baseline: CR «со слов»
и CR «из GA4» — разные факты, и это видно.

**Причинно-следственные цепочки.** 6 цепочек «симптом → корневые причины
(с контрольными вопросами) → бизнес-влияние → рычаг»: активируются болями
клиента, корни подтверждаются ответами; неподтверждённые уходят в вопросы
к интервью. Плюс граф зависимостей метрик (SEO→Трафик, CRM→Повторные→LTV→CAC…).

**Зрелость процессов L1–L5.** Лестницы по 8 доменам (CRM: L1 «базе не
пишут» → … → L5 «predictive»): текущий уровень из health домена + описание
следующего уровня. Уровень виден и в карте здоровья отчёта (чип L2/5).

**Деньги решений.** Цена бездействия по каждому критическому разрыву
(потенциал распределён пропорционально штрафам) — в карточках разрывов;
прогноз 12 месяцев «без изменений vs с программой (+N%)» — в отчёте и админке.

**Гипотезы (Continuous Consulting).** Редактируемый реестр в
`report_meta.hypotheses`: гипотеза · доказательство · уверенность
25/50/75/100 · способ проверки · владелец · дедлайн · статус; стартовый
набор генерируется из топ-решений; сверка — XX-01. Learning Loop описан
в методике: подтверждения/отклонения правят Impact правил, эффекты
пополняют источники эталонов, ставки — cost base.

**Зависимости плейбуков.** PB_PREREQS (ERP после карты интеграций,
Amazon EU после юнит-экономики и PIM…) — движок подсвечивает порядок и
требует включить пререквизит, если он вне scope.
