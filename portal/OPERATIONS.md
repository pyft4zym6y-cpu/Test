# Операционный регламент · Discovery Portal

Правила эксплуатации сервиса для команды weexp. Пара к `SERVICE_GUIDE.md`
(механика) и `PRIVACY`-странице портала (обещания клиенту — этот регламент
обеспечивает их выполнение).

## 1. SLA консультанта

| Событие | Обязательство |
| --- | --- |
| Клиент приглашён | Первый контакт и проверка входа — в день приглашения |
| Клиент прошёл шаги 01–03 (боли/цели) | Просмотр и комментарий — 1 рабочий день |
| Опросник заполнен ≥ 60% + выданы AC-01/AC-13 | Разбор выгрузки, baseline, черновик резюме — 3 рабочих дня |
| Все шаги + интервью проведены | Публикация финальной версии + КП — 5 рабочих дней |
| Вопрос клиента в любом канале | Ответ — 1 рабочий день |

Диагностика без движения 7 дней → напоминание клиенту (пока вручную,
текст — кнопкой «Приглашение 📋»); 30 дней → звонок владельцу проекта.

## 2. Данные: хранение, выгрузка, удаление

- **Срок хранения:** период сотрудничества + 12 месяцев (сверка XX-01),
  затем удаление. Обещание зафиксировано на странице /privacy.
- **Запрос клиента на выгрузку:** «Экспорт для ЕКП (CSV)» из карточки
  клиента + файлы из Storage — отдать в течение 5 рабочих дней.
- **Запрос на удаление:** выполнить за 14 дней. Порядок: удалить клиента
  в Supabase (каскад снесёт members/answers/access_status/report_meta/notes)
  → удалить папку `clientId/` в Storage → подтвердить письменно. Резервные
  копии Supabase выбывают по циклу ротации (см. ниже) — сказать об этом
  клиенту честно.
- **Кому можно давать is_admin:** только сотрудникам weexp с NDA. Каждый
  админ видит все проекты — раздача клиентам запрещена.

## 3. Бэкапы и восстановление

- Supabase Pro делает ежедневные бэкапы автоматически (ротация 7 дней);
  на Free-плане бэкапов нет — **не держать боевых клиентов на Free**.
- Раз в месяц — ручной экспорт: SQL-дамп из Supabase Dashboard + выгрузка
  Storage, в защищённую папку weexp. Ответственный — владелец портала.
- Код и методика (`portal/method/`) версионируются в GitHub — точка
  восстановления всего продукта: `git clone` + `schema.sql` + env-переменные.

## 4. Инциденты

| Симптом | Действия |
| --- | --- |
| Портал не открывается | Vercel Dashboard → Deployments: смотреть последний деплой, откат кнопкой «Rollback» на предыдущий |
| Не приходят magic-link | Supabase → Auth → Logs; проверить rate limit (Free: 4 письма/час) и спам-папку клиента |
| Клиент видит чужие данные | P1: немедленно отключить деплой (Vercel → Pause), проверить RLS-политики по schema.sql, зафиксировать масштаб, уведомить затронутых |
| Утечка доступа админа | Удалить строку в members, инвалидировать сессии (Supabase → Auth → пользователь → Sign out), сменить ключи при необходимости |
| Ошибка в расчётах отчёта | Не публиковать финал; чинить в коде — формулы в `lib/report.ts` / `lib/consultant.ts`, править только с прогоном Playwright-теста |

Любой инцидент с данными клиента → запись: дата, что случилось, кого
коснулось, что сделано, как предотвращаем повтор.

## 5. Релизы

1. Изменения — в ветке, сборка `npm run build` (сайт и портал!) обязана
   проходить без ошибок TypeScript.
2. Прогнать Playwright-сценарий демо (сид → шаги → админ → финал → КП).
3. После изменения `schema.sql` — прогнать его в Supabase SQL Editor
   (скрипт идемпотентный) **до** пуша в main.
4. Push в main → Vercel деплоит автоматически. Проверить прод руками:
   вход, дашборд, отчёт.
5. Изменилась методика → сначала первоисточник в `portal/method/`,
   потом выжимки в `src/data/`.

## 6. Онбординг нового консультанта

1. Прочитать `SERVICE_GUIDE.md` (механика) и `method/METHOD.md` (методика).
2. Пройти демо-режим целиком: сид → все 7 шагов → карточка клиента →
   финал → КП.
3. Добавить в members с is_admin=true (делает владелец портала).
4. Первые два проекта — в паре с действующим консультантом; публикация
   финала и отправка КП — только после ревью старшего.
