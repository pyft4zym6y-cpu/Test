# 08 · Качество и тестирование

> Заземлено на проверку репозитория. **Честный раздел:** пробелы показаны как пробелы.

## Автоматизированные тесты — отсутствуют

**Факт:** в репозитории **ноль тестов**.
- Нет `*.test.ts` / `*.spec.ts` / `__tests__` вне `node_modules`.
- Нет `vitest.config` / `jest.config`.
- Нет `test`-скрипта ни в одном `package.json`.
- `@playwright/test` есть в dev-зависимостях корня, но spec-файлов нет; Playwright в
  движке используется как рантайм обхода, не как тест-харнес.

**Покрытие: 0%.** Это осознанный текущий статус на стадии активной разработки. Митигация
и приоритет — в реестре рисков (раздел 15) и дорожной карте (раздел 16).

## Что заменяет тесты сейчас (компенсирующие контроли)

| Контроль | Где | Что даёт |
|----------|-----|----------|
| **TypeScript `strict`** везде | все tsconfig | Статическая проверка типов на сборке |
| **Typecheck-гейт** | `worker`: `npm run typecheck`; портал: `tsc && vite build` | Сборка падает при ошибке типов |
| **Self-QA протокол аудита** | `worker/src/qa.ts` | Внутренняя проверка полноты/консистентности вывода прогона |
| **Гейт достижимости** | `pipeline.ts` | Останавливает прогон честно, если сайт недоступен — не выдумывает |
| **Fail-safe деградация** | все линзы (try/catch) | Ошибка одной линзы не рушит прогон; нет ключа → деградация, не фабрикация |
| **Верификация «факт vs оценка»** | методология | Измеримое ≠ оценочное; см. G-02 ниже |
| **Ручная визуальная проверка** | процесс | PDF-рендеры проверяются глазами перед выдачей |

## G-02 · Верификация выводов аудита (как гарантируется отсутствие выдумок)

Ключевое качество продукта — **не выдумывать данные**. Механизмы:
1. Детерминированный слой строит отчёты из измеренных сигналов обхода; AI лишь обогащает
   нарратив, а не заменяет факты.
2. Неизмеримое явно помечается «оценка / нужен доступ / данные/дослідження».
3. Worst-case + **сверка одной метрики из ≥2 источников** (раздел 09) — расхождение
   показывается, а не скрывается.
4. Гейт достижимости: без реального сайта/скриншотов прогон не порождает находок.

Это методологический контроль качества — предмет проверки: воспроизвести прогон и
убедиться, что каждая цифра прослеживается до источника.

## Типизация и статические проверки

- `strict: true` во всех tsconfig; корневой — строжайший (`noUnusedLocals`,
  `noUnusedParameters`, `noFallthroughCasesInSwitch`); портал — `noUnusedLocals`.
- **Линтер/форматтер отсутствуют** (нет ESLint/Prettier) — пробел, в беклоге.
- На момент проверки `worker` и `portal` проходят `tsc --noEmit` **чисто** (ранее
  упоминавшиеся ошибки типов Supabase в портале **не воспроизводятся** в текущем дереве).

## CI/CD — отсутствует

- **Нет `.github/`**, нет GitHub Actions, нет других пайплайнов.
- Деплой — config-as-code, но **ручной** (`render.yaml autoDeploy:false`).
- Нет автоматического гейта (typecheck/тесты) перед деплоем.

## Пентест / сканирование зависимостей

- Формальных результатов SAST/DAST/пентеста нет (E-06 — нужно провести).
- Есть встроенные скиллы для этого (`.claude/skills/` содержит strix-пентест и др.) — можно
  запустить как часть подготовки к аудиту.
- Напоминание: **сам продукт не пентестит клиентов** (см. раздел 05) — снимает только
  внешние заголовки безопасности.

## Приоритетные рекомендации QA (для аудитора и владельца)

1. Ввести тест-раннер (vitest) и покрыть **чистые детерминированные функции** первыми:
   `money.ts`, `portalEngine.ts` (Health Score), `auditTiers.ts` хелперы, `xlsx.ts`/`zip.ts`.
2. Добавить CI (`.github/workflows`) с гейтом typecheck (+ тесты по мере появления).
3. Ввести ESLint + Prettier.
4. Прогнать сканер зависимостей (`npm audit`) и SAST на `portal/api/*` (SSRF S-5).
