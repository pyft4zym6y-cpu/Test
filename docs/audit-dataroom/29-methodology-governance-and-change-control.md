Закрывает замечания №7, №8. Методология — это IP (раздел 09), и её изменение меняет
результат аудита. Поэтому изменения управляются и версионируются.

## Что считается «изменением методологии»

Любое изменение, влияющее на результат: вопросы (`questions.json`), скоринг/веса
(`method.ts`), бенчмарки/пороги (раздел 28, `crawl.ts` checks), тиры (`auditTiers.ts`),
промпты, модель по умолчанию. При таком изменении **обязательно** поднимается
`METHODOLOGY_VERSION` (`worker/src/version.ts`) — уже реализовано.

## Процесс (Propose → Review → Test → Approve → Version → Deploy → Monitor)

1. **Propose** — Change Request (см. поля ниже).
2. **Review** — второй человек (не автор) оценивает влияние.
3. **Test** — прогнать **golden regression** (раздел 21) + eval-метрики (раздел 22); измерить
   изменение Audit Reliability Score (раздел 20).
4. **Approve** — владелец методологии утверждает (separation of duties, раздел 31).
5. **Version** — поднять `METHODOLOGY_VERSION`; записать в changelog.
6. **Deploy** — задеплоить (раздел 07).
7. **Monitor** — следить за метриками на реальных прогонах.

**Гейт:** изменение не мёржится, если golden-regression падает или ARS падает ниже порога
(практика: PR, меняющий промпт/модель/скоринг, гейтится eval-прогоном — Langfuse/Braintrust,
2026).

## Change Request (поля)

`Change ID | что меняется | почему | инициатор | reviewer | затронутые аудиты/модули |
ожидаемое влияние | результат golden/eval | approval | дата деплоя | новая METHODOLOGY_VERSION`.

## Обратная совместимость

Старые Run Records хранят свою `methodologyVersion` — результаты остаются интерпретируемыми
в контексте своей версии. Не переписывать задним числом.
