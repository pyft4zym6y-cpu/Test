## 26.3 · DSAR workflow (Art. 15–22)

- **Срок: 1 календарный месяц** от получения, бесплатно. Продление +2 мес для сложных — с
  уведомлением заявителя в первый месяц.
- Шаги: канал приёма (`hello@weexp.agency`) → верификация личности → поиск по ВСЕМ системам
  (Supabase, bucket, `results/` на движке, логи субпроцессоров, бэкапы) → редакция данных
  третьих лиц → выдача в доступном формате → ответ → журнал.
- Заявленный экспорт CSV + удаление за 14 дней (PrivacyPage) — формализовать как процедуру.

## 26.4 · Breach notification (Art. 33/34)

- **Art. 33 (регулятору): ≤72ч** с момента осознания, если breach вероятно несёт риск.
  Часы стартуют с осознания, не с конца расследования; допускается поэтапное уведомление.
- **Содержание:** природа breach; категории и примерное число субъектов/записей; контакт DPO;
  вероятные последствия; принятые меры.
- **Art. 34 (субъектам):** при **высоком** риске, без промедления, простым языком.
- Вести **внутренний реестр всех breach** (включая нерепортируемые — с обоснованием, Art.33(5)).
  Пересекается с журналом инцидентов (раздел 24).

## 26.5 · Retention schedule + классификация данных

**Retention** (feeds RoPA(f)): `категория → цель → основание → срок → триггер/метод удаления`.
Критично: определить ретеншн `results/<id>/` на движке (сейчас ⛔, D-04).
**Классификация:** Public / Internal / Confidential / Restricted-PII → правила хранения/
шифрования/доступа на каждый уровень (drives какие контролы где применяются).
