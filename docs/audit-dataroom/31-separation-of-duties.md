# 31 · Separation of Duties (Producer → Reviewer → Approver)

> **Версия:** 0.1 · **Владелец:** PO / SEC · **Проверяющий:** [Заполнить] · **Дата:** 2026-08-19 ·
> **Следующий пересмотр:** ежеквартально · **Статус:** 📝 (поля в коде ✅, процесс 📝)

Закрывает замечание №17. Система не должна сама производить и сама утверждать критические
выводы. Классический four-eyes / maker-checker, применённый к AI-аудиту. Источники:
en.wikipedia.org/wiki/Maker-checker, ISO 27001 A.5.3, arXiv:2606.20615 (producer-reviewer
AI-SDLC, 2026), EU AI Act Art.14 (human oversight).

## Три роли

| Роль | Кто/что | Права | Не может |
|------|---------|-------|----------|
| **Producer** | движок (`pipeline.ts`) + LLM-нарратив | производит черновые находки/отчёты | утверждать, мёржить |
| **Reviewer** | независимый оценщик: LLM-судья (иного семейства) и/или человек-аналитик | проверяет против спеки/доказательств/golden | редактировать (только фиксирует замечания) |
| **Approver** | человек с полномочиями | утверждает выдачу клиенту | — |

Принцип из исследования: «producer mode cannot access merge tools; reviewer mode cannot
access edit tools» — разграничивать в правах/тулинге, не только в политике.

## Реализация

- Поле `review` в Audit Run Record (`runrecord.ts`): `reviewer`/`approver`/`status`
  (produced → reviewed → approved/rejected) — **уже есть в коде**.
- Процесс: перед выдачей клиенту отчёт проходит review (человек/LLM-судья) и approval;
  идентичности пишутся в Run Record → это же входит в Audit Reliability Score (humanValidation,
  раздел 20).
- Для инженерии: PR-ревью обязателен (никто не мёржит+деплоит свой критический код без
  второго — раздел 29, SOC 2 change management).
