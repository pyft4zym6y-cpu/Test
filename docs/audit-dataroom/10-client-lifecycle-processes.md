# 10 · Клиентский жизненный цикл и процессы

> Как устроены операционные процессы. Заземлено на портал (страницы), движок
> (пайплайн) и заявленные регламенты (`portal/OPERATIONS.md`, `SERVICE_GUIDE.md`).

## I-01 · Карта клиентского процесса (end-to-end)

```
Продажа/КП → Онбординг клиента → Сбор данных (опросник + доступы) →
  Запуск аудита (движок) → Контроль качества → Выдача отчётов →
  (опц.) Внедрение/сопровождение → Закрытие проекта / удаление данных
```

| Этап | Где в системе | Артефакт |
|------|---------------|----------|
| Продажа / КП | `KpPage` (генерация КП) | КП (PDF/DOCX) |
| Онбординг | `AdminPage` (создание клиента/логина), инвайт на e-mail | Доступ в портал |
| Определение глубины | `AuditIntakePage` (T1–T4 + блоки) | Перечень требований |
| Сбор данных | опросник (`DomainPage`), `AccessPage` (доступы/файлы), `ConnectorsPage` | `answers`, `access_status`, `files` |
| Запуск аудита | `AuditRunnerPage` → движок `POST /audit` | Прогон в очереди |
| Производство | `pipeline.ts` (обход→анализ→сборка→рендер) | ~35+ отчётов |
| Контроль качества | self-QA (`qa.ts`) + ручная визуальная проверка | Проверенный пакет |
| Выдача | `pack.zip` (чистый клиентский) / `report_meta` / ReportPage | Пакет клиенту |

## I-02 · Процесс приёма доступов (как собираются/хранятся)

- **Принцип «без паролей»:** доступ выдаётся инвайтом на e-mail с правами «просмотр» или
  одноразовой ссылкой (Bitwarden Send / 1Password). Портал хранит только *статус*.
- **Файлы** (P&L, выгрузки) — в приватный bucket `uploads` (RLS по клиенту).
- **Выгрузка заказов (AC-13)** — парсится в браузере, не отправляется; в бэкенд идут агрегаты.
- **Инструкции «для чайников»** и шаблоны — приложены к каждому требованию в `AuditIntakePage`.
- **Worst-case:** если доступа нет — есть запасной путь (скриншоты/Web Archive/внешние
  источники) со сверкой; см. раздел 09.

## I-03 · Процесс производства отчёта

1. Оператор запускает прогон (тир, сайт, конкуренты, опц. резервный PDF).
2. Очередь движка (1 аудит за раз) выполняет `runAudit`.
3. Гейт достижимости; ~30 линз; AI-обогащение при наличии ключа.
4. Группировка ~26 файлов → 5 тем + флагман + КП.
5. Ручная визуальная проверка PDF перед выдачей.
6. Выдача: `pack.zip` клиенту, `pack-internal.zip` внутренне.

## I-04 · Обращение с данными клиента (📝 требует формализации)

Заявлено (PrivacyPage): хранение на срок сотрудничества + 12 мес; удаление в течение 14
дней по письменному запросу; экспорт CSV по запросу. **Пробел:** нет формального
регламента приёма→хранения→удаления с ответственными и сроками по каждой категории данных
(включая `results/<id>/` на хосте движка). Владелец: DPO. Каркас — в разделе 11.

## I-05 · Поддержка и эскалация (⛔ нужно подготовить)

Нет документированного процесса приёма обращений, SLA и эскалации. Требуется описать:
каналы (e-mail `hello@weexp.agency`), время реакции, уровни эскалации, журнал инцидентов.
Владелец: OPS. Связано с планом реагирования на инциденты (раздел 15, E-05).
